# 28. Phase 3P: Payment gateway backend

Phase 3P makes payments real: the native payments API and the hosted test checkout, the test card and wallet tables with the real-card safety rule, gateways, methods and flows stored in the database and editable, notifications rendered from each gateway's definition and delivered through the webhook engine, after-payment operations, and Stripe, PayPal and SSLCommerz emulated at their real paths on the provider port. The Payments screens and Settings > Payments switch to live data ([11](11-roadmap.md#phase-3p-payment-gateway-about-2-weeks), [17](17-payments.md)).

## Goal and done-when

**Done when** (from [11](11-roadmap.md#phase-3p-payment-gateway-about-2-weeks)): apps using the official Stripe SDK, PayPal Orders and SSLCommerz complete a payment, receive and verify the IPN or webhook, validate the order, and handle a decline and a refund, all offline. In full:

- every Phase 3P item in [PROGRESS.md](PROGRESS.md) is ticked and the Phase 3P criteria of [PY](acceptance/08-payments.md) have passing tests that name them;
- the done-when check runs in CI against a release binary with outbound traffic blocked (PY-01.3);
- the live UI suite shows the Payments screens, the test checkout page, Payments > Gateways, Methods and Flows, Settings > Payments and the Overview's Payments tile with real data and no failing calls.

## As built

- **W1 (flows and methods):** the new `sendmock-payments` crate holds the domain rules with no serde: `PaymentStepType` (the catalogue's nine steps, which decide and which show a field), the label variables and `find_unknown_variables`, `check_payment_flow` and `check_payment_method` (the mock's `validate-payment-flow.ts` and `validate-payment-method.ts` with the same messages and order, the test values checked being those the method's flow asks for), the test card ranges, the Luhn check and the single-step edits. Migration `0023` adds `payment_definitions` (kind, key, the definition as JSON), read through `PaymentDefinitionRepository`; a row exists only for an edited built-in (so Reset deletes it) or a custom flow, method or gateway. The built-in flows, methods, gateways, step catalogue and label variables are exported from the mock's fixtures to `crates/sendmock-ops/builtin/payment-*.json` by `web/scripts/export-builtin-definitions.ts`, whose repository test fails when they drift. `sendmock-ops/src/payments/` serves the 17 operations of `/payments/flows` (list, create, show, update, delete, reset, add, update and remove one step), `/payments/step-types`, `/payments/flow-variables` and `/payments/methods` (list, create, show, update, delete, reset): a flow reports how many methods use it, a method the gateways offering it (built-in gateways and stored ones; the gateway operations come in W2) and `payment_count` 0 until payments exist (W3); a step added with only its type takes the catalogue's labels; a flow's key and a method's key and flow are fixed after creation; deleting a built-in is `409 builtin_flow` or `builtin_method`, a flow in use `409 flow_in_use`, a method a gateway offers `409 method_offered` (the contract's rule; the mock checked payments). Tests: `payment_flows_api.rs`, `payment_methods_api.rs`, the store test, unit tests for the rules and the shipped JSON, and contract samples. W1 was pushed together with W2, because the Methods screen also reads the gateways and the live UI suite fails on any unanswered call.
- **W2a (gateways):** W2 was split into W2a (the gateway definitions) and W2b (the preview, which needs a payment and the template engine). `check_new_gateway` and `check_payment_gateway` join the domain crate (the mock's `validate-payment-gateway.ts`); the operations serve `/payments/gateways` (list, create from a built-in or blank, show, update, delete, reset) and the credential reveal (no MCP tool, `--reveal` in the CLI, as for SMS providers). Credentials reuse the SMS provider credential type and its masking: answers show `••••` and the last 4, a secret sent back masked or empty keeps its value. A blank gateway starts from Native and offers cards; a change offering a method that does not exist is refused; deleting a built-in is `409 builtin_gateway`. Gateways reuse the W1 storage (`payment_definitions`, kind `gateway`), and flows, methods and gateways now share `payment_definition_store` (load the built-ins with their stored edits, save, delete) through the `PaymentDefinition` trait. The contract's `PaymentEventType` was an `Extract<...>` over template literals that the OpenAPI generator could not resolve, so `event_names` required every app event; it is now the explicit list of the eleven `payment.*` and `checkout.*` events, and the spec was regenerated. Tests: `payment_gateways_api.rs` (masking, reveal, a masked secret kept on save, copy and blank creation, reset, unknown methods, a method a gateway offers cannot be deleted), domain unit tests and contract samples.
- **W3a (payments and checkouts):** the contract has no direct `POST /payments`: payments are made through a hosted checkout, so W3 and W4 meet. W3 is split into W3a (storage, list, detail, test values, checkout creation and the checkout session) and W3b (completing a checkout: the flow run, outcomes, redirects); W3a comes before W2b, whose preview renders against a payment. Migration `0024` adds `payments` (the payment as a JSON document, with `provider`, `method_key`, `status` and `currency` as columns for the list filters and the counts), read through `PaymentRepository`; `reset` deletes payments. `POST /payments/checkout` takes any gateway, custom ones included (unknown is `400` on `provider`), the currency from the request or Settings > Payments (three capital letters, amounts in minor units above 0; the new `money` module of the domain crate knows the zero-decimal currencies), the gateway's ids as its API names them (`cs_test_...` and `pi_...` for Stripe, `TXN...` and `VAL...` for SSLCommerz, a `reference` for a custom gateway), the shop's success, fail and cancel URLs and `checkout_url` at this instance's `/pay/{paymentId}`, a "created" timeline entry and the `payment.created` event. `GET /payments` is newest first with `status` (one or several), `provider` and `currency` filters and a cursor; `GET /payments/{paymentId}` the detail; `GET /payments/test-cards` the enabled methods; `GET /checkout-sessions/{sessionId}` (the session id is the payment id) the gateway's enabled methods in its order, the flows they run and the state read from the payment. Gateways and methods now count their payments, and a method with payments cannot be deleted (`409 method_in_use`). The automatic outcome profile waits for W3b, which simulates the outcome. Tests: `payment_checkouts_api.rs`, the store tests and contract samples.
- **W3b (completing a checkout):** `POST /checkout-sessions/{sessionId}/complete` (CLI `sendmock payments checkout complete <sessionId> <action>`, MCP `sendmock_checkout_complete`) answers the checkout session. An open checkout takes `pay`, `decline`, `cancel`, `delay` and `require_three_ds`; one waiting on 3-D Secure takes `three_ds_approve`, `three_ds_fail` and `cancel`; anything else is `409 checkout_closed`. `pay` picks the method named in the request (else the first offered method whose flow fits what was sent) and runs its flow in the domain crate's `run_payment_flow`, one step at a time against the method's test values: the first refused step is a `422 validation_failed` that changes nothing, so a real card number (Luhn-valid but not a test card) is kept in no table, log, event or answer (the operation is not in the API request log, and the CVC and name on the card are not even read). Only brand, last 4 and expiry of a card are kept, a wallet number is masked (first 5, `****`, last 2) and a voucher code shows its last 4. The contract gained `422` on this endpoint, as 17-payments already described. State changes live in `PaymentChange` (succeed, decline, cancel, 3-D Secure, dispute, delay, then save and publish), which W6's Simulate will reuse; a finished checkout closes its page and sends the customer to the success, fail or cancel URL with the gateway's redirect fields rendered by the template engine (`build_gateway_context` gives templates `payment`, `event`, `redirect` and `merchant`; success-only fields are left out otherwise). The outcome profile in Settings > Payments now settles new checkouts at once (`auto_success`, `auto_decline`, `random` with the success rate). `payment.succeeded`, `payment.failed`, `payment.canceled`, `payment.dispute_opened` and `checkout.completed` are published on the bus after the payment is stored; the gateway's own notifications wait for W5. Tests: `checkout_completion_api.rs`, the flow runner's unit tests and a contract sample.
- **W2b (the gateway preview):** `POST /payments/gateways/{gatewayKey}/preview` (CLI `sendmock payments gateways preview <gatewayKey>`, MCP `sendmock_payment_gateway_preview`, read-only) renders the gateway sent (saved or not; a masked secret borrows the stored value) against the chosen payment, else the gateway's newest, else the newest of any gateway, else answers with no payment. The redirect fields (success-only ones left out for `fail` and `cancel`) and the notification for the event (none when the gateway names no event for it) are rendered by `GatewayPartRenderer`, the same code the checkout redirect uses; the body comes first, so headers can sign it. Secrets are masked in the preview's `merchant` and in its reference, every problem is named by its part (`Redirect field status`, `Header stripe-signature`, `Notification body`) with its severity, and the reference reuses the SMS provider reference builder, now `build_template_reference` with the gateway's field descriptions. The template function `stripe_signature(secret)` writes a real `Stripe-Signature` (`t=...,v1=` HMAC-SHA256 of `<timestamp>.<body>`), so W5's Stripe notifications verify with Stripe's libraries; the other functions (`uuid`, `random_hex`, `now_iso`) were already in the engine, so `minijinja` needed nothing new. Creating or updating a gateway is refused with `400` while a template has an error (an unknown function or filter, unbalanced braces), checked without a payment so every template is checked; an undefined value is only a warning. Tests: `payment_gateway_preview_api.rs`, the signature unit test and contract samples.
- **W4 (the checkout page live):** W3a and W3b built the checkout's endpoints, and the binary already serves every app route (a path without a file extension) with the embedded UI's `index.html`, so `/pay/{sessionId}` needed no Rust change. W4 proves the page against a real binary in the live UI suite: `web/tests/live/checkout-page.spec.ts` creates checkouts through `POST /payments/checkout` and opens the `checkout_url` it answers, then pays a Stripe checkout with a test card (redirect to the success URL, `payment.succeeded` and `checkout.completed` on the bus), refuses a real card on the page before anything is sent, approves and fails 3-D Secure, declines with a reason, delays and cancels from the test controls, shows PayPal's approve button, runs bKash's number, OTP and PIN steps inside SSLCommerz's grouped methods with the POST return, shows a paid checkout as closed (and `409` from the API), and pays from the keyboard. `checkout-accessibility.spec.ts` scans the Stripe, PayPal and SSLCommerz pages with axe in light and dark; the theme is set before the page loads and the scan is repeated until it settles, because text colours switch just after the first paint. The page's expired state waits for W6's `expire`, and its notifications for W5.
- **W5a (gateway notifications):** W5 was split into W5a (the gateway's own notifications) and W5b (the payment templates in the webhook template catalogue and webhook rules on payment events, PY-08.1 and PY-08.2). `PaymentChange::save` now renders, for each event it fires, the gateway's notification with `GatewayPartRenderer::render_notification` (the redirect outcome read from the event: `payment.failed` is fail, `payment.canceled` and `checkout.expired` cancel, the rest success) and queues it to the gateway's notification endpoint with the new `enqueue_rendered_delivery`, which takes the endpoint's retry policy, so retries, the delivery log and replay come from the Phase 3 engine. Nothing is queued when the gateway has no endpoint, the endpoint is disabled or deleted, or the gateway names no event for it. A provider's notification carries its own signature (`Stripe-Signature`, PayPal's transmission headers, SSLCommerz's `verify_sign`), so migration `0025` adds `is_signed` to `webhook_deliveries` (1 by default): the dispatcher adds the endpoint's Standard Webhooks headers only to signed rows, and a gateway's notification is signed only for Native, as the mock does. A replay as sent keeps the original's choice; a replay rendered again is `409 gateway_notification`, because the endpoint's template is not the gateway's (resend from the payment instead). The payment lists each notification (delivery, native event, the provider's event name, status and status code, read again from the latest attempt when the payment is shown) and a `notification_sent` timeline entry. `POST /payments/{paymentId}/notify` (CLI `sendmock payments notify <paymentId>`, MCP `sendmock_payment_notify`) renders the last notified event again under a new event id; nothing sent yet, or nothing to send it to, is `409 nothing_to_resend`. Tests: `payment_notifications_api.rs` (Stripe's signed notifications, an SSLCommerz IPN retried after a 500, Native's Standard Webhooks headers, notify, replay) and a contract sample.
- **W5b (payment templates and rules):** seven built-in webhook templates join the catalogue in a new `payment-provider` category ("Payment gateways" in the gallery): `stripe.event`, `paypal.webhook`, `paypal.ipn`, `sslcommerz.ipn`, `bkash.callback`, `razorpay.webhook` and `paddle.webhook`, defined in the mock's `payment-template-definitions.ts` and exported to the binary with the others. They read the payment event's `data`, which is now the payment without its timeline and notifications plus `amount_major` (it was the summary), so a rule on a payment event can send any of them; the rule subscriber records the payment as the delivery's subject. The new `payment_event(provider)` filter names a native event in the provider's words, and gives the status its payload object has after the event (`stripe_status`, `paypal_status`, `razorpay_status`, `paddle_status`); its table is the mock's `payment-provider-event-names.ts`, exported to `crates/sendmock-core/src/template/payment-event-names.json`, which the core filter reads. The signing schemes moved into the `sendmock-payments` domain crate (`sign_stripe_payload`, `sign_razorpay_payload`, `sign_paddle_payload`, `sign_sslcommerz_fields`, each tested against values computed independently). Header templates now render with `SignedBodyFunctions`, so `stripe_signature(secret)`, `razorpay_signature(secret)` and `paddle_signature(secret)` sign the rendered body for real; `sslcommerz_verify_sign(store_password, fields)` is a body field, so it takes the signed fields as a map (the mock's helpers keep the right shape only). `POST /webhooks/templates/{templateId}/render` takes `payment_id` and renders against the event the payment's latest state stands for; with no message a payment event renders against a sample Stripe payment shared with the mock. The mock's `date` filter learned `%s` and `%b`. Tests: `payment_templates_api.rs` renders each template against a real payment and checks it against a fixture in `tests/fixtures/payment_webhooks/` (a documented example from the provider's docs and the JSON Schema it must pass, as Phase 3 did for Twilio and Vonage) and recomputes each signature; a rule on `payment.succeeded` queues a Stripe event with the payment as subject. PY-08.1 has its test but stays open for the `subscription.*` events (Phase 4) and W6's events.
- **W6 (Simulate):** `POST /payments/{paymentId}/simulate` (CLI `sendmock payments simulate <paymentId> <action>`, MCP `sendmock_payment_simulate`) runs only what the payment's status allows, as the mock's `listSimulateActions` does: an open payment takes `succeed`, `decline` and, while its page is open, `expire`; an authorized one `capture` and `void`; a paid or partly refunded one `refund` and `dispute`; a disputed one `resolve_dispute`; anything else is `409 action_not_allowed` ("A succeeded payment cannot do capture"). A refund takes the amount asked for or all that is left, refusing zero or more than is left with `422 validation_failed`; the payment is `partially_refunded` until nothing is left. `expire` closes the page without a redirect and fires `checkout.expired` (the page then says "This checkout expired"); a lost dispute returns the captured amount. The steps live in `payment_settlement.rs` as more `PaymentChange` methods, so each fires its events (`payment.refunded`, `payment.partially_refunded`, `payment.dispute_closed` and `checkout.expired` joined the event types) and queues the gateway's notifications through `save`, as the checkout does. The contract gained `400` and `422` on this endpoint. Nothing in the API makes an authorized payment yet: Stripe's `capture_method: manual` in W7 will, so `capture` and `void` are tested on a payment stored as authorized and PY-07.1 waits for W7. Tests: `payment_simulate_api.rs` (refunds, disputes, capture and void, expiry, succeed and decline, the `409` and `404`), a live UI test of the expired page and contract samples.
- **W7a (Stripe's API):** the Stripe adapter (`answer_stripe_request` in `sendmock-ops/src/stripe/`) serves Stripe's API in code from the `stripe` gateway while it is enabled, beside Twilio Verify in the provider runtime: under `/providers/stripe/v1/...` and, on the provider port, at `/v1/payment_intents`, `/v1/checkout/sessions` and `/v1/refunds` (or any path with `Host: api.stripe.com`). Routes: PaymentIntents (create with `confirm=true`, retrieve, confirm, capture with `amount_to_capture`, cancel with `cancellation_reason`), Checkout Sessions in `payment` mode (create from `price_data` line items, retrieve, `line_items`, expire) and Refunds (create from `payment_intent` or `charge`, retrieve); any other path is Stripe's "Unrecognized request URL" `404`. Answers carry `Request-Id` and echo `Stripe-Version`; ids follow the payment's (`pi_`, `cs_test_`, and `ch_`, `pm_` derived from the intent; refunds `re_`). Any `sk_test_` key works, no key or a live key is Stripe's `401`, and the key, the gateway's secrets and any card data sent are masked in the request log. Test PaymentMethods and tokens (`find_stripe_test_card_number` in the domain crate) become a test card that `pay_with_test_card` runs through the card method's flow, so the outcome is the method's table; declines answer `402` `card_error` with Stripe's `code` and `decline_code` (`describe_stripe_card_decline`) and the PaymentIntent in `requires_payment_method` with `last_payment_error`, and it can be confirmed again (a later success clears the failure); a 3-D Secure card answers `requires_action` with `next_action.redirect_to_url` at the payment's `/pay/{paymentId}` page. A Checkout Session is a payment made by `start_provider_payment` with a checkout page: `{CHECKOUT_SESSION_ID}` is filled in its URLs before the outcome profile runs, its status is `open` until paid (`complete`) or expired or canceled (`expired`), and `payment_intent` is set once a card was used. Manual capture is the payment's new `capture_method` (`automatic` or `manual`, required in the contract, also taken by `POST /payments/checkout`; documents stored earlier read as `automatic`): paying a manual payment, on the page, through Simulate or Stripe's confirm, makes it `authorized` and fires the new `payment.authorized` (Stripe's `payment_intent.amount_capturable_updated`), and capture takes all or part of it; the mock does the same. Stripe-only state (the attached PaymentMethod, the intent's own metadata and cancellation, the session's `client_reference_id` and `expires_at`, refunds) lives in `payment_provider_objects` (migration `0026`, deleted with its payment), read through `PaymentProviderObjectRepository`; a payment is found by a provider id with `PaymentRepository::find_payment_by_provider_id`. Tests: `stripe_payment_intents_api.rs` (shapes, errors, every test card, 3-D Secure, a dispute, a retry after a decline, raw cards refused and not logged, manual capture and partial capture, cancel and void, the provider port's real path), `stripe_checkout_sessions_api.rs`, `stripe_refunds_api.rs`, the manual capture checkout in `payment_simulate_api.rs` (which no longer fakes an authorized payment), the store and unit tests, and the mock's manual capture test; PY-04.1, PY-04.2 and PY-07.1 ticked. Lists, updates, Customers and Prices are left for later; W7b renders the webhook events as Stripe's objects and runs the official SDKs.
- **W7b (Stripe's webhook events):** the Stripe gateway's notification is now Stripe's Event (`evt_` id shared with the delivery, `api_version` `2025-03-31.basil`, `livemode`, `pending_webhooks`, `request`, `type`) with `data.object` from `event.object`, a new value in every gateway template's context (`GatewayRenderOptions::event_object`). `build_provider_event_object` (in `payments/provider_event_object.rs`) looks the builder up by the gateway's key, and Stripe's `describe_stripe_event_object` picks the object by the event's name: the Checkout Session and PaymentIntent from W7a's builders, and the new Charge (`stripe_charge_object.rs`, no `refunds` list) and Dispute (`stripe_dispute_object.rs`, `dp_`, due a week after it opened). Notifications are rendered while a payment change is saved, before the Stripe adapter used to store its own state, so a `payment_intent.canceled` event lacked the `cancellation_reason` just sent: `PaymentChange` now keeps provider objects (`keep_provider_object`, used through `keep_stripe_object`) and stores them with the payment, and the event builder reads a kept object before a stored one. The mock builds the same objects (`web/src/mocks/payments/stripe/`), the fixture's Stripe body changed and was exported, and `event.object` joined the gateway field descriptions. The official SDKs run in the new "Stripe SDKs" workflow (also called by Release build): `examples/payments/stripe-node/done-when.js` pays a Checkout Session on the page, receives `checkout.session.completed` and `payment_intent.succeeded` through `constructEvent`, handles `pm_card_chargeDeclined` as a `StripeCardError` and `payment_intent.payment_failed`, and writes the deliveries that `stripe-php/verify.php` and `stripe-python/verify.py` verify. `scripts/acceptance.ts` now reads `examples/` (`done-when.js`, `verify.php`, `verify.py`). Tests: `stripe_webhook_events_api.rs` (each event's object equals the retrieve, the decline's last error, the cancellation reason, the refund's Charge and the Dispute), the object builders' unit tests, the mock's `build-stripe-event-object.test.ts`, and the preview and notification tests updated; the notification test fixture moved to `tests/support/payment_notification_fixture.rs`. PY-04.3 and PY-04.4 ticked and PY-04 accepted.
- **W8a (PayPal's Orders v2 and refunds):** the PayPal adapter (`answer_paypal_request` in `sendmock-ops/src/paypal/`) serves PayPal's REST API from the `paypal` gateway while it is enabled, after Stripe's in the provider runtime: `POST /v1/oauth2/token`, Orders (create, retrieve, capture) and the Payments API's captures (retrieve, refund) and refunds (retrieve), as decided in the W8 design note. An order is a payment made by `start_provider_payment` with `capture_method` `manual` and `fail_url` set to `return_url`, so the checkout page's approval authorizes it (`APPROVED`, with `payer` and `payment_source.paypal` as the sandbox buyer `TESTPAYER01`) and a decline there is answered at capture as `422 INSTRUMENT_DECLINED`. Captures and refunds get 17-character ids, a capture carries `seller_receivable_breakdown` with a test fee of 3.49% plus 49 minor units, and the order's `purchase_units[0].payments` lists its captures and refunds. ## Design notes

- **Crate:** the domain goes into a new `sendmock-payments` crate (layer 2): money and currencies (`MoneyAmount` value object in minor units), the test instrument tables and the real-card check, the flow step catalogue and the flow runner (the checkout's state machine as a Strategy per step type), and the provider signing schemes. Operations live in `sendmock-ops/src/payments/`, storage in `sendmock-store` (`PaymentFlowRepository`, `PaymentMethodRepository`, `PaymentGatewayRepository`, `PaymentRepository`).
- **Built-ins as data:** the shipped flows, methods and gateways are JSON in `crates/sendmock-ops/builtin/`, generated from the same source as the mock's fixtures so both ship identical definitions; a database row exists only for an edited built-in (its whole definition, so Reset deletes the row) or a custom item, as SMS providers do ([22](22-configurable-providers.md)).
- **Real cards never stored:** the real-card refusal happens before anything is written: the request log stores a redacted body for payment requests and the error names no digits (PY-01.1); a stored method keeps brand, last 4 and expiry only (PY-01.2).
- **Notifications are deliveries:** a gateway's notification is a webhook delivery to its notification endpoint, rendered from the gateway's body and header templates when it is queued (as W4c of Phase 3 renders endpoint requests), so retries, the log, replay and `notify` (resend) come from the Phase 3 engine.
- **PayPal on the provider port (W8):** W8 is split into W8a (Orders v2 and refunds, PY-05.1), W8b (webhooks with PayPal's transmission headers and `verify-webhook-signature`, PY-05.2) and W8c (the classic IPN with the `_notify-validate` postback, PY-05.3). PayPal's REST API is served in code by the PayPal adapter (`paypal_api_adapter.rs`) beside Stripe's, from the `paypal` gateway while it is enabled: on the provider port at `/v1/oauth2/token`, `/v2/checkout/orders` and `/v2/payments/...` (and with `Host: api-m.sandbox.paypal.com` or `api-m.paypal.com`), and under `/providers/paypal/...`. Decisions for W8a:
  - `POST /v1/oauth2/token` takes any client id and secret pair with `grant_type=client_credentials`, as each PayPal app has its own, and answers PayPal's token (`A21AA...`, `Bearer`, `expires_in` 32400, `app_id`). API calls take any Bearer token or the Basic pair; none is PayPal's `401 AUTHENTICATION_FAILURE`. The secret and tokens are masked in the request log.
  - Requests and answers are JSON; errors are PayPal's (`name`, `message`, `debug_id`, `details` with `field`, `location`, `issue` and `description`, and an `information_link`), and every answer carries `Paypal-Debug-Id`. `Prefer: return=representation` answers the whole order; the default (`return=minimal`) answers `id`, `status` and `links` on create, as PayPal does.
  - An order is a payment with a checkout page, as a Stripe Checkout Session is. `intent` `CAPTURE` is served; `AUTHORIZE` answers `400 INVALID_REQUEST` (`INVALID_PARAMETER_VALUE` on `/intent`) until a later workstream adds authorizations. One purchase unit is served: its `amount` (`value` as a decimal text, checked for the currency's decimals), `items`, `reference_id`, `description`, `custom_id` and `invoice_id`; more answer `INVALID_PARAMETER_VALUE`. `return_url` and `cancel_url` come from `payment_source.paypal.experience_context` (the order is then `PAYER_ACTION_REQUIRED` with a `payer-action` link) or the older `application_context` (`CREATED` with an `approve` link); either link is this instance's `/pay/{paymentId}`.
  - The payer approving on the checkout page is the payment being authorized, so an order is made with `capture_method` `manual`: an approved order is `APPROVED` and `POST /v2/checkout/orders/{id}/capture` captures it (`COMPLETED`, with a capture in `purchase_units[0].payments.captures` and its `seller_receivable_breakdown`). A decline on the page sends the payer back to `return_url` without `PayerID`, and the capture then answers `422 INSTRUMENT_DECLINED`, which is where a PayPal app meets a decline. Capturing before approval is `422 ORDER_NOT_APPROVED`, twice is `422 ORDER_ALREADY_CAPTURED`, an unknown id is `404 RESOURCE_NOT_FOUND` (`INVALID_RESOURCE_ID`).
  - `GET /v2/payments/captures/{captureId}`, `POST /v2/payments/captures/{captureId}/refund` (all that is left, or `amount`; more than is left is `422 REFUND_AMOUNT_EXCEEDED`, nothing left `422 CAPTURE_FULLY_REFUNDED`, a disputed capture `422 TRANSACTION_REFUSED`) and `GET /v2/payments/refunds/{refundId}`. Capture and refund ids are PayPal's 17 capitals and digits.
  - The order's own fields (intent, purchase unit ids, URLs, whether a payment source was sent), its capture and its refunds are kept in `payment_provider_objects` (`order`, `capture`, `refund`), read and written through the same helpers as Stripe's, which move to `payments/provider_object_store.rs` now that two adapters use them. Updating an order (`PATCH`), `PayPal-Request-Id` idempotency and the Payments API v1 are left for later.
  - Decisions for W8b and W8c: PayPal signs a webhook with its private key (`SHA256withRSA` over `<transmission id>|<transmission time>|<webhook id>|<CRC32 of the body>`) and apps check it by calling `POST /v1/notifications/verify-webhook-signature`, and it checks an IPN by the app posting the message back; both checks ask PayPal whether it sent exactly this. SendMock answers them the same way, from the delivery log: a message is genuine when a delivery SendMock queued carries it, so no key, certificate or new dependency is needed, and a delivery removed by retention no longer verifies, as PayPal's checks fail for messages it no longer knows.
  - W8b, the webhook event: the built-in PayPal gateway's notification is PayPal's event as PayPal sends it: `id` (`WH-` and the native event's id, so retries keep it), `event_version` `1.0`, `create_time`, `resource_type` and `summary` (read from the event with the `payment_event` filter's new `paypal_resource_type` and `paypal_summary` tables), `resource_version` `2.0`, `event_type` and `resource`. Gateway templates read the resource as `event.object`, built in code by PayPal's event object builder as the API answers it, so a webhook and a retrieve never disagree: the order for `CHECKOUT.ORDER.*`, the capture for `PAYMENT.CAPTURE.COMPLETED` and `PAYMENT.CAPTURE.DENIED` (a declined order has no capture, so it is described as a `DECLINED` capture with an id derived from the order), the newest refund for `PAYMENT.CAPTURE.REFUNDED`, and the dispute for `CUSTOMER.DISPUTE.*` (the Customer Disputes API's `dispute_id`, `reason` in PayPal's words, `status` `OPEN` or `RESOLVED`, `dispute_outcome` once resolved, `dispute_amount` and `disputed_transactions` naming the capture). A capture now carries `supplementary_data.related_ids.order_id`, as PayPal's does. The headers are `PAYPAL-TRANSMISSION-ID`, `-TIME`, `-SIG` (344 characters, the length of PayPal's RSA signature), `PAYPAL-CERT-URL` (PayPal's sandbox certificate address; SendMock does not serve it, so apps verify with the API, as PayPal recommends) and `PAYPAL-AUTH-ALGO` `SHA256withRSA`. The gateway names no event for `payment.authorized` and `payment.canceled`: Orders with `intent` `CAPTURE` (the only intent served) send `CHECKOUT.ORDER.APPROVED` on approval and nothing for an approval cancelled on the page, never authorization events. The mock builds the same resources, with their main fields, for its preview and notifications.
  - W8b, the check: `POST /v1/notifications/verify-webhook-signature` (any Bearer token or the Basic pair, as the other calls) needs `auth_algo`, `cert_url`, `transmission_id`, `transmission_sig`, `transmission_time`, `webhook_id` and `webhook_event` (one missing is PayPal's `400` with `MISSING_REQUIRED_PARAMETER`). It answers `{"verification_status": "SUCCESS"}` when a delivery SendMock queued has that `PAYPAL-TRANSMISSION-ID` (any case), the same time, signature, certificate address and algorithm headers, was queued to the endpoint whose id is `webhook_id` (the webhook id an app configures is its notification endpoint's id, shown in Webhooks > Endpoints), and has a body equal to `webhook_event` as JSON (so key order and spacing do not matter, as SDKs parse and serialize the event again); anything else is `FAILURE`. It works for the gateway's notifications and for the `paypal.webhook` template on any endpoint. The delivery is found with a new `WebhookDeliveryRepository` query on the stored request text, newest first.
  - W8c, the IPN: `POST /cgi-bin/webscr` on the provider port (and with `Host` `ipnpb.paypal.com`, `ipnpb.sandbox.paypal.com`, `www.paypal.com` or `www.sandbox.paypal.com`) and under `/providers/paypal/cgi-bin/webscr`, with no authentication, answers `text/plain` `VERIFIED` when the body is `cmd=_notify-validate` followed by the fields of a form delivery SendMock queued, in the same order with the same values (compared after decoding, because PayPal's own sample code decodes and encodes each value again), and `INVALID` otherwise, as PayPal does. The delivery is found by the message's `ipn_track_id`, else its `verify_sign`, else its `txn_id`; a message with none of them is `INVALID`. IPNs come from the `paypal.ipn` template on an endpoint with a webhook rule on payment events, or from a gateway whose notification is a form.
- **SSLCommerz on the provider port (W9):** W9 is split into W9a (session init, the IPN and the success, fail and cancel POSTs with a real `verify_sign`, and the order validation API, PY-06.1 to PY-06.4) and W9b (refund and the transaction query, PY-06.5). The SSLCommerz adapter (`sslcommerz_api_adapter.rs`) serves SSLCommerz's v4 API from the `sslcommerz` gateway while it is enabled: on the provider port at `/gwprocess/v4/api.php` and `/validator/api/...` (and with `Host` `sandbox.sslcommerz.com` or `securepay.sslcommerz.com`), and under `/providers/sslcommerz/...`. The shapes follow SSLCommerz's v4 developer docs and its official PHP, Node and Python libraries. Decisions for W9a:
  - Credentials: every call carries `store_id` and `store_passwd`, which must equal the gateway's credentials. Session init answers a wrong pair with `200` and `{"status": "FAILED", "failedreason": "Store Credential Error Or Store is De-active", ...}` (the success fields empty), as SSLCommerz does; the validation API answers it with `{"APIConnect": "FAILED"}`.
  - Session init (`POST /gwprocess/v4/api.php`, form fields): `total_amount`, `currency`, `tran_id`, `success_url`, `fail_url` and `cancel_url` are required, and a missing or invalid one is `status` `FAILED` with `failedreason` naming it (`Invalid Information! 'tran_id' is missing.`). The customer and product fields are optional, because a test should not have to fill a shipping address: `cus_name`, `cus_email` and `cus_phone` become the payment's customer, `product_name` its line item, and `value_a` to `value_d` are kept in the metadata and returned as SSLCommerz returns them. The app's `tran_id` becomes the payment's reference, and a 32-character `sessionkey` is made. The answer is `status` `SUCCESS` with `sessionkey`, `GatewayPageURL` (this instance's checkout page), `gw` (the gateway's methods by SSLCommerz's groups), `store_name`, and SSLCommerz's other fields empty. `ipn_url` is accepted but the IPN goes to the gateway's notification endpoint, as SSLCommerz sends it to the IPN URL set in the merchant panel.
  - The transaction: one document built from the payment (`sslcommerz_transaction.rs`) is what the IPN, the redirect POSTs and the validation API all carry, so they always agree: `status`, `tran_date` (Dhaka time, `YYYY-MM-DD HH:MM:SS`), `tran_id`, `val_id` (only once paid), `amount`, `store_amount`, `currency`, `bank_tran_id`, `card_type`, `card_no`, `card_issuer`, `card_brand`, `card_issuer_country`, `card_issuer_country_code`, `currency_type`, `currency_amount`, `currency_rate`, `base_fair`, `value_a` to `value_d`, `risk_level`, `risk_title`, and `verify_key` listing those fields. Gateway templates read it as `event.object`, and the redirect fields read it too, with `status` the outcome's name (`VALID`, `FAILED`, `CANCELLED`).
  - `verify_sign`: `sslcommerz_verify_sign(store_password, fields)` now signs only the fields its `verify_key` names when the fields carry one, as an app's check reads them, and gateway templates can call it. The `sslcommerz` gateway's IPN body and redirect fields send the whole transaction with a real `verify_sign` made with `merchant.store_passwd`.
  - Order validation (`GET /validator/api/validationserverAPI.php?val_id=&store_id=&store_passwd=&format=json`): the transaction plus `APIConnect` `DONE`, `validated_on` and `gw_version`; `status` is `VALID` the first time and `VALIDATED` after, as SSLCommerz marks a validated order. A `val_id` that names no paid payment (unknown, altered, or of a payment that failed) is `{"status": "INVALID_TRANSACTION", "APIConnect": "DONE"}`; no `val_id` is `{"APIConnect": "INVALID_REQUEST"}`. Only JSON is answered.
  - Decisions for W9b: refunds and transaction queries share `GET /validator/api/merchantTransIDvalidationAPI.php`, told apart by their fields as SSLCommerz tells them apart: `refund_ref_id` asks a refund's status, `bank_tran_id` with `refund_amount` and `refund_remarks` (and an optional `refe_id`) starts a refund, `sessionkey` queries a transaction by its session, `tran_id` by the app's id. Wrong store credentials are `{"APIConnect": "FAILED"}` and a request with none of those fields, or a refund missing one, `{"APIConnect": "INVALID_REQUEST"}`. Every SSLCommerz payment now gets its `bank_tran_id` when it is made (in `provider_ids`), so a refund finds its payment.
  - A refund answers `APIConnect` `DONE`, `bank_tran_id`, `trans_id`, `refund_ref_id` (13 hexadecimal characters), `status` `success` and an empty `errorReason`, and refunds the payment at once (firing `payment.refunded` or `payment.partially_refunded` and the gateway's `REFUNDED` IPN); SSLCommerz may answer `processing` first, which SendMock skips. A refund SSLCommerz would refuse is `status` `failed` with `errorReason`: an unknown `bank_tran_id`, a payment that is not paid or already fully refunded, or an amount that is not a valid amount or is more than is left. The refund's status by `refund_ref_id` answers `bank_tran_id`, `tran_id`, `refund_ref_id`, `initiated_on`, `refunded_on`, `status` `refunded` and `errorReason`; an unknown one is `status` `failed`.
  - The query by `sessionkey` answers the transaction with `sessionkey`, `APIConnect`, `validated_on` and `gw_version`, its `status` `PENDING` before the payment is made, `VALID` or `VALIDATED` once paid, `FAILED`, `CANCELLED` or `EXPIRED`. The query by `tran_id` answers `APIConnect`, `no_of_trans_found` and `element`, the list of those transactions; SendMock lists the newest payment with that `tran_id`, so `no_of_trans_found` is 0 or 1. An unknown session key is `status` `INVALID_TRANSACTION`.
- **Custom gateways' wire APIs (W10c):** a custom gateway has no provider docs SendMock could copy, and its definition describes the checkout, the redirect and the notification, not an API. So every custom gateway shares one small API, served in code by the custom gateway adapter (`custom_gateway_api_adapter.rs`) after SSLCommerz's in the provider runtime, as the [payments plan](17-payments.md#gateways-and-payment-methods-configurable) and the [Add a payment gateway guide](../wiki/advanced/payment-gateway.md) promise: session init answers the checkout URL, and validation answers from the payment.
  - It answers only under `/providers/<gatewayKey>/...` (on the API port and the provider port), only for a custom gateway (built-ins without an adapter, bKash and Native, keep the native `404`, since bKash's real API is not this one) and only while it is enabled. Other paths under the prefix get the native `404`.
  - Session init: `POST /providers/<gatewayKey>/checkout`, a JSON body or a form. `amount` (required) is in major units, as text or a JSON number, checked for the currency's decimals; `currency` defaults to Settings > Payments; `reference` is the app's order id (else the gateway's own, `UPAY-...`) and becomes `payment.reference` in the gateway's templates, as SSLCommerz's `tran_id` does; `success_url`, `fail_url` and `cancel_url` are where the redirect goes; `customer_email`, `customer_name`, `description` (one line item) and `metadata` (a JSON object, or `metadata[key]` form fields) are optional. It answers `201` with `payment_id`, `reference`, `status`, `amount` (major units, as text), `currency` and `checkout_url`. The outcome profile applies as to every checkout.
  - Validation: `GET /providers/<gatewayKey>/payments/{paymentReference}` (the payment id or the `reference`, the newest of that gateway when several share it) answers `200` with the gateway's notification body rendered for the payment as it is now, in the notification's content type, so it says what the notification says: the event is the one the payment's status stands for (`payment.created` while open, `payment.authorized`, `payment.succeeded`, `payment.failed`, `payment.canceled`, `payment.refunded`, `payment.partially_refunded`, `payment.dispute_opened`) and `event.name` is the gateway's name for it, empty when it names none. Signature headers are not sent, as validation answers come over the app's own request.
  - Credentials: providers send them in too many ways to require any one, so none is required, but each gateway credential the request names (a body or query field, or a header, of the credential's name; header names ignore case) must equal its value, else `401`. Secrets are masked in the request log.
  - Errors are JSON `{"error": {"code", "message", "field"}}`: `400 invalid_request` (a missing or bad field), `401 invalid_credentials`, `404 payment_not_found`, and `500 template_error` with the problems when the notification cannot be rendered.
  - Tests: `custom_gateway_api.rs` (init in JSON and form with the checkout URL, the amount and field checks, a wrong credential, a paid checkout redirecting and notifying from the definition, validation before and after paying by id and by reference, an unknown payment, a disabled custom gateway and bKash not served), naming PY-12.3.

- **Stripe on the provider port (W7):** W7 is split into W7a (the wire API) and W7b (the webhook events in Stripe's object shapes, checked with the official SDKs in CI). Stripe is a payment gateway, not an SMS provider, so its API is served in code by the Stripe adapter (`stripe_api_adapter.rs`) beside Twilio Verify, from the `stripe` gateway while it is enabled, at `/v1/...` on the provider port (and `api.stripe.com`) and under `/providers/stripe/v1/...`. Decisions:
  - Any test key is accepted (`Authorization: Bearer sk_test_...` or Basic with the key as the user name), because each Stripe account has its own test keys; no key is Stripe's `401`, and a live key (`sk_live_`, `rk_live_`) is refused with Stripe's `401` so it is never kept. The key is masked in the request log.
  - Requests are Stripe's form encoding with bracketed keys (`line_items[0][price_data][unit_amount]`, `metadata[order_id]`, `payment_method_types[]` and `payment_method_types[0]`); answers are Stripe's objects and errors (`{"error": {"type", "code", "decline_code", "message", "param", "doc_url"}}`) with a `Request-Id` header.
  - W7a serves Checkout Sessions (create in `payment` mode with `price_data` line items, retrieve, expire, list line items), PaymentIntents (create, retrieve, confirm, capture with `amount_to_capture`, cancel) and Refunds (create, retrieve). Lists, updates, Customers, Prices and other modes answer Stripe's errors until a later workstream adds them. A Checkout Session is a payment with a checkout page, as a native checkout is: its `url` is this instance's `/pay/{paymentId}`, and `{CHECKOUT_SESSION_ID}` in `success_url` is filled in as Stripe does.
  - Cards are Stripe's test PaymentMethods and tokens (`pm_card_visa`, `pm_card_visa_chargeDeclinedInsufficientFunds`, `tok_chargeDeclined`, ...), mapped to the test card numbers of Stripe's docs and run through the card method's flow and test card table, so an edited table applies to the API too. Raw card numbers are refused as Stripe refuses them, and kept nowhere. Declines answer `402` with Stripe's `code` and `decline_code` (`card_declined` with `generic_decline` or `insufficient_funds`; `expired_card`, `incorrect_cvc`; 3-D Secure failure is `payment_intent_authentication_failure`) and leave the PaymentIntent in `requires_payment_method` with `last_payment_error`, so it can be confirmed again.
  - Manual capture belongs to the payment, not only to Stripe: the payment gains `capture_method` (`automatic` or `manual`, also taken by `POST /payments/checkout`), a manual payment that is paid becomes `authorized` and fires the new `payment.authorized` event, and capture (whole or part) and void finish it (PY-07.1).
  - Stripe-only state (the attached PaymentMethod, refunds with their `re_` ids, the session's mode and `client_reference_id`) is kept by the adapter in a `payment_provider_objects` table (migration `0026`), keyed by the provider's id and linked to the payment, so the payment model stays provider-neutral and PayPal and SSLCommerz can keep their captures and refunds there too.
  - W7b sends Stripe's webhook events as Stripe sends them: an Event with the native event's `evt_` id (so the delivery log and the app see the same id), `object: "event"`, `api_version` (`2025-03-31.basil`), `created`, `data.object`, `livemode: false`, `pending_webhooks: 1`, `request` (`id` and `idempotency_key`, both `null`) and `type`. `data.object` is the object the event is about, exactly as the API answers it, so a webhook and a retrieve never disagree: the Checkout Session for `checkout.session.*`, the PaymentIntent for `payment_intent.*`, the Charge for `charge.refunded` (`ch_`, `amount_captured`, `amount_refunded`, `captured`, `refunded`, `payment_intent`, `payment_method_details.card`), and the Dispute for `charge.dispute.*` (`dp_`, `amount`, `charge`, `payment_intent`, `reason`, `status` `needs_response` while open, then `won` or `lost`). The Charge has no `refunds` list, as Stripe stopped including it in API version `2022-11-15`.
  - Gateway templates read that object as `event.object`. It is built in code by the provider's event object builder, looked up by the payment's provider (Stripe's is the only one; it is `null` for every other gateway), and the built-in Stripe gateway's notification body is `"data": {"object": {{ event.object | json }}}` inside the Event, so the body stays an editable template. The mock builds the same objects, with their main fields, for its preview and notifications.
  - The official SDKs prove it in CI: `examples/payments/stripe-node/` uses the `stripe` Node SDK pointed at SendMock to create a Checkout Session, pay it through the checkout page's API, receive `checkout.session.completed` and `payment_intent.succeeded` with `stripe.webhooks.constructEvent`, then confirm a PaymentIntent with `pm_card_chargeDeclined`, handle the `StripeCardError` and receive `payment_intent.payment_failed`. It saves every delivery it received, and `stripe-php/verify.php` (`\Stripe\Webhook::constructEvent`) and `stripe-python/verify.py` (`stripe.Webhook.construct_event`) verify the same bytes. The new "Stripe SDKs" workflow runs them against a release binary on changes to the payment code or the examples and before every release, as "Webhook handler" does; `scripts/acceptance.ts` reads `examples/` too, so these scripts prove PY-04.3 and PY-04.4.

# 28. Phase 3P: Payment gateway backend

Phase 3P makes payments real: the native payments API and the hosted test checkout, the test card and wallet tables with the real-card safety rule, gateways, methods and flows stored in the database and editable, notifications rendered from each gateway's definition and delivered through the webhook engine, after-payment operations, and Stripe, PayPal and SSLCommerz emulated at their real paths on the provider port. The Payments screens and Settings > Payments switch to live data ([11](11-roadmap.md#phase-3p-payment-gateway-about-2-weeks), [17](17-payments.md)).

## Goal and done-when

**Done when** (from [11](11-roadmap.md#phase-3p-payment-gateway-about-2-weeks)): apps using the official Stripe SDK, PayPal Orders and SSLCommerz complete a payment, receive and verify the IPN or webhook, validate the order, and handle a decline and a refund, all offline. In full:

- every Phase 3P item in [PROGRESS.md](PROGRESS.md) is ticked and the Phase 3P criteria of [PY](acceptance/08-payments.md) have passing tests that name them;
- the done-when check runs in CI against a release binary with outbound traffic blocked (PY-01.3);
- the live UI suite shows the Payments screens, the test checkout page, Payments > Gateways, Methods and Flows, Settings > Payments and the Overview's Payments tile with real data and no failing calls.

## As built

- **W1 (flows and methods):** the new `sendmock-payments` crate holds the domain rules with no serde: `PaymentStepType` (the catalogue's nine steps, which decide and which show a field), the label variables and `find_unknown_variables`, `check_payment_flow` and `check_payment_method` (the mock's `validate-payment-flow.ts` and `validate-payment-method.ts` with the same messages and order, the test values checked being those the method's flow asks for), the test card ranges, the Luhn check and the single-step edits. Migration `0023` adds `payment_definitions` (kind, key, the definition as JSON), read through `PaymentDefinitionRepository`; a row exists only for an edited built-in (so Reset deletes it) or a custom flow, method or gateway. The built-in flows, methods, gateways, step catalogue and label variables are exported from the mock's fixtures to `crates/sendmock-ops/builtin/payment-*.json` by `web/scripts/export-builtin-definitions.ts`, whose repository test fails when they drift. `sendmock-ops/src/payments/` serves the 17 operations of `/payments/flows` (list, create, show, update, delete, reset, add, update and remove one step), `/payments/step-types`, `/payments/flow-variables` and `/payments/methods` (list, create, show, update, delete, reset): a flow reports how many methods use it, a method the gateways offering it (built-in gateways and stored ones; the gateway operations come in W2) and `payment_count` 0 until payments exist (W3); a step added with only its type takes the catalogue's labels; a flow's key and a method's key and flow are fixed after creation; deleting a built-in is `409 builtin_flow` or `builtin_method`, a flow in use `409 flow_in_use`, a method a gateway offers `409 method_offered` (the contract's rule; the mock checked payments). Tests: `payment_flows_api.rs`, `payment_methods_api.rs`, the store test, unit tests for the rules and the shipped JSON, and contract samples. W1 was pushed together with W2, because the Methods screen also reads the gateways and the live UI suite fails on any unanswered call.
- **W2a (gateways):** W2 was split into W2a (the gateway definitions) and W2b (the preview, which needs a payment and the template engine). `check_new_gateway` and `check_payment_gateway` join the domain crate (the mock's `validate-payment-gateway.ts`); the operations serve `/payments/gateways` (list, create from a built-in or blank, show, update, delete, reset) and the credential reveal (no MCP tool, `--reveal` in the CLI, as for SMS providers). Credentials reuse the SMS provider credential type and its masking: answers show `••••` and the last 4, a secret sent back masked or empty keeps its value. A blank gateway starts from Native and offers cards; a change offering a method that does not exist is refused; deleting a built-in is `409 builtin_gateway`. Gateways reuse the W1 storage (`payment_definitions`, kind `gateway`), and flows, methods and gateways now share `payment_definition_store` (load the built-ins with their stored edits, save, delete) through the `PaymentDefinition` trait. The contract's `PaymentEventType` was an `Extract<...>` over template literals that the OpenAPI generator could not resolve, so `event_names` required every app event; it is now the explicit list of the eleven `payment.*` and `checkout.*` events, and the spec was regenerated. Tests: `payment_gateways_api.rs` (masking, reveal, a masked secret kept on save, copy and blank creation, reset, unknown methods, a method a gateway offers cannot be deleted), domain unit tests and contract samples.
- **W3a (payments and checkouts):** the contract has no direct `POST /payments`: payments are made through a hosted checkout, so W3 and W4 meet. W3 is split into W3a (storage, list, detail, test values, checkout creation and the checkout session) and W3b (completing a checkout: the flow run, outcomes, redirects); W3a comes before W2b, whose preview renders against a payment. Migration `0024` adds `payments` (the payment as a JSON document, with `provider`, `method_key`, `status` and `currency` as columns for the list filters and the counts), read through `PaymentRepository`; `reset` deletes payments. `POST /payments/checkout` takes any gateway, custom ones included (unknown is `400` on `provider`), the currency from the request or Settings > Payments (three capital letters, amounts in minor units above 0; the new `money` module of the domain crate knows the zero-decimal currencies), the gateway's ids as its API names them (`cs_test_...` and `pi_...` for Stripe, `TXN...` and `VAL...` for SSLCommerz, a `reference` for a custom gateway), the shop's success, fail and cancel URLs and `checkout_url` at this instance's `/pay/{paymentId}`, a "created" timeline entry and the `payment.created` event. `GET /payments` is newest first with `status` (one or several), `provider` and `currency` filters and a cursor; `GET /payments/{paymentId}` the detail; `GET /payments/test-cards` the enabled methods; `GET /checkout-sessions/{sessionId}` (the session id is the payment id) the gateway's enabled methods in its order, the flows they run and the state read from the payment. Gateways and methods now count their payments, and a method with payments cannot be deleted (`409 method_in_use`). The automatic outcome profile waits for W3b, which simulates the outcome. Tests: `payment_checkouts_api.rs`, the store tests and contract samples.
- **W3b (completing a checkout):** `POST /checkout-sessions/{sessionId}/complete` (CLI `sendmock payments checkout complete <sessionId> <action>`, MCP `sendmock_checkout_complete`) answers the checkout session. An open checkout takes `pay`, `decline`, `cancel`, `delay` and `require_three_ds`; one waiting on 3-D Secure takes `three_ds_approve`, `three_ds_fail` and `cancel`; anything else is `409 checkout_closed`. `pay` picks the method named in the request (else the first offered method whose flow fits what was sent) and runs its flow in the domain crate's `run_payment_flow`, one step at a time against the method's test values: the first refused step is a `422 validation_failed` that changes nothing, so a real card number (Luhn-valid but not a test card) is kept in no table, log, event or answer (the operation is not in the API request log, and the CVC and name on the card are not even read). Only brand, last 4 and expiry of a card are kept, a wallet number is masked (first 5, `****`, last 2) and a voucher code shows its last 4. The contract gained `422` on this endpoint, as 17-payments already described. State changes live in `PaymentChange` (succeed, decline, cancel, 3-D Secure, dispute, delay, then save and publish), which W6's Simulate will reuse; a finished checkout closes its page and sends the customer to the success, fail or cancel URL with the gateway's redirect fields rendered by the template engine (`build_gateway_context` gives templates `payment`, `event`, `redirect` and `merchant`; success-only fields are left out otherwise). The outcome profile in Settings > Payments now settles new checkouts at once (`auto_success`, `auto_decline`, `random` with the success rate). `payment.succeeded`, `payment.failed`, `payment.canceled`, `payment.dispute_opened` and `checkout.completed` are published on the bus after the payment is stored; the gateway's own notifications wait for W5. Tests: `checkout_completion_api.rs`, the flow runner's unit tests and a contract sample.
- **W2b (the gateway preview):** `POST /payments/gateways/{gatewayKey}/preview` (CLI `sendmock payments gateways preview <gatewayKey>`, MCP `sendmock_payment_gateway_preview`, read-only) renders the gateway sent (saved or not; a masked secret borrows the stored value) against the chosen payment, else the gateway's newest, else the newest of any gateway, else answers with no payment. The redirect fields (success-only ones left out for `fail` and `cancel`) and the notification for the event (none when the gateway names no event for it) are rendered by `GatewayPartRenderer`, the same code the checkout redirect uses; the body comes first, so headers can sign it. Secrets are masked in the preview's `merchant` and in its reference, every problem is named by its part (`Redirect field status`, `Header stripe-signature`, `Notification body`) with its severity, and the reference reuses the SMS provider reference builder, now `build_template_reference` with the gateway's field descriptions. The template function `stripe_signature(secret)` writes a real `Stripe-Signature` (`t=...,v1=` HMAC-SHA256 of `<timestamp>.<body>`), so W5's Stripe notifications verify with Stripe's libraries; the other functions (`uuid`, `random_hex`, `now_iso`) were already in the engine, so `minijinja` needed nothing new. Creating or updating a gateway is refused with `400` while a template has an error (an unknown function or filter, unbalanced braces), checked without a payment so every template is checked; an undefined value is only a warning. Tests: `payment_gateway_preview_api.rs`, the signature unit test and contract samples.

## Design notes

- **Crate:** the domain goes into a new `sendmock-payments` crate (layer 2): money and currencies (`MoneyAmount` value object in minor units), the test instrument tables and the real-card check, the flow step catalogue and the flow runner (the checkout's state machine as a Strategy per step type), and the provider signing schemes. Operations live in `sendmock-ops/src/payments/`, storage in `sendmock-store` (`PaymentFlowRepository`, `PaymentMethodRepository`, `PaymentGatewayRepository`, `PaymentRepository`).
- **Built-ins as data:** the shipped flows, methods and gateways are JSON in `crates/sendmock-ops/builtin/`, generated from the same source as the mock's fixtures so both ship identical definitions; a database row exists only for an edited built-in (its whole definition, so Reset deletes the row) or a custom item, as SMS providers do ([22](22-configurable-providers.md)).
- **Real cards never stored:** the real-card refusal happens before anything is written: the request log stores a redacted body for payment requests and the error names no digits (PY-01.1); a stored method keeps brand, last 4 and expiry only (PY-01.2).
- **Notifications are deliveries:** a gateway's notification is a webhook delivery to its notification endpoint, rendered from the gateway's body and header templates when it is queued (as W4c of Phase 3 renders endpoint requests), so retries, the log, replay and `notify` (resend) come from the Phase 3 engine.
- **Provider port:** Stripe, PayPal and SSLCommerz are provider adapters (Adapter pattern) registered in the provider registry beside Twilio and Vonage, at their real paths and under `/providers/<key>/...`.

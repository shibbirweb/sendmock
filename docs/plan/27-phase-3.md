# 27. Phase 3: Webhooks backend

Phase 3 makes webhooks real: endpoints and rules subscribe to SendMock's events, a persistent queue delivers them signed with Standard Webhooks and retries with backoff, payloads are rendered from templates and variables with `minijinja`, and every delivery can be sent by hand, replayed, edited and saved. It also brings the email delivery outcomes and opened events, the Twilio-style SMS reply webhook, the full seed file, and switches the Webhook screens and the Overview to live data ([11](11-roadmap.md#phase-3-webhooks-backend-about-2-3-weeks)).

## Goal and done-when

**Done when** (from [11](11-roadmap.md#phase-3-webhooks-backend-about-2-3-weeks)): a rule forwards every `*@inbound.local` email to a local Express handler, the delivery log shows the request and response, and a failed delivery retries, then succeeds after the handler is fixed and the delivery replayed. In full:

- every Phase 3 item in [PROGRESS.md](PROGRESS.md) is ticked and the criteria below have passing tests that name them;
- the Express done-when check runs in CI against a release binary;
- the live UI suite shows Webhooks (overview, endpoints, rules, deliveries, composer, templates, variables, saved) and the Overview with real data and no failing calls.

## As built

Notes are added here as each workstream lands.

- **W1 (endpoints and signing):** migration `0010` adds `webhook_endpoints`; `WebhookEndpointRepository` keeps the name, URL, enabled state, the request settings as one JSON document owned by the operations layer, the signing secret, and the previous secret with its expiry. Operations in `sendmock-ops/src/webhooks/`: list, create, show, update (only the sent keys, then the whole endpoint is checked again), delete, reveal secret (CLI with `--reveal`, no MCP tool) and rotate secret (overlap of 1, 24 or 168 hours, as the Security tab offers). Validation matches the edit sheet's rules (`web/src/lib/webhooks/validate-webhook-endpoint.ts`): a name, an http(s) URL or a templated one, a valid Fields or Raw body, timeout 1 to 60 s, 1 to 10 attempts, retry delays 1 s to 24 h. The view masks the secret (`whsec_••••` and the last four characters) and shows `previous_secret_expires_at` only while the old secret still signs; `success_rate`, `delivery_count_24h` and `success_history` stay empty until W2 records deliveries. In `sendmock-webhooks`: the `WebhookSecret` value object (`whsec_` and base64, generated from the `RandomSource`, masked `Debug`) and Standard Webhooks signing (`sign_payload`, `build_signed_headers` with space-separated signatures during an overlap), checked against the spec's published example. WH-01.1, WH-01.3, WH-01.5 and WH-01.8 are proven at the API; they are ticked when the CLI, MCP, seed and live screens land (W9, W10). WH-04 is ticked when deliveries carry the headers (W2) and the official libraries verify them (W11). Test send and the request preview moved to W6 and W5.
- **W2 (delivery engine):** migration `0011` adds `webhook_deliveries`, one row per attempt, which is also the persistent queue (`WebhookDeliveryRepository`: due rows, claiming a pending row or a due retry, finishing an attempt, cancel, putting `in_flight` rows back on start). `RetrySchedule` in `sendmock-webhooks` decides each attempt: `2xx` succeeds, `5xx`, timeouts and connection errors retry with the backoff (the last delay repeats) up to `max_attempts`, `4xx` only when `retry_on_client_errors` is on; the last allowed attempt is `exhausted`. In `sendmock-ops/src/webhooks/`: `enqueue_webhook_delivery` stores the first attempt with the rendered native request (the event envelope as JSON with the endpoint's method and static headers; templates come in W4 and W5) and wakes the dispatcher; `run_due_deliveries` claims up to the concurrency limit (8 in the binary) and sends them together through the `WebhookSender` trait, signing each attempt with Standard Webhooks headers plus `webhook-attempt`; `run_webhook_dispatcher` is the background loop the binary runs until shutdown. Every attempt publishes `webhook.delivered`; `failed` without a retry and `exhausted` also publish `webhook.failed`. Operations: deliveries list (comma-separated `status`, where `failed` also finds `exhausted`), detail with every attempt and the email or SMS behind it, cancel (the event's latest attempt, `409 not_retrying` when nothing is left to cancel) and `wait/webhook` (endpoint by id or name, newest finished attempt). The binary's `HttpWebhookSender` uses the endpoint's timeout and records the answer up to 64 KB. Proven at the operation level: WH-03.2 to WH-03.6, WH-03.9 (cancel), WH-04.1 (with the reference signer), WH-04.2, WH-04.3 and the webhook part of PL-03.1. WH-03.1 is ticked when rules fire from ingest (W3), the UI criteria (WH-03.7 to WH-03.9) with the live screens (W10), and WH-04.1's official libraries in W11.
- **W3 (rules and events):** migration `0012` adds `webhook_rules`, ordered by `position`; `WebhookRuleRepository` lists, creates, edits, moves (`up` or `down`, swapping with the neighbour) and deletes rules, and deleting an endpoint deletes its rules. In `sendmock-webhooks`: `rule_filter` with `FilterExpression` (`all`, `any`, `not`, conditions), `RuleOperator` (`equals`, `contains`, `starts_with` and `matches` ignore case, `matches` is an anchored glob, `regex` is case-sensitive, `exists`) and `RuleMessage`, the fields a rule reads (email `from`, `to`, `cc`, `subject`, `body` with HTML tags stripped, `header:<name>`, `has_attachment`, `tag`; SMS `from`, `to`, `body`, `status`, `api`). Operations in `sendmock-ops/src/webhooks/`: list, create, show, update, delete, move and preview (the last 50 emails and SMS that would match an unsaved rule). Validation matches the builder: a name, an existing endpoint, at least one event a rule can listen to (`webhook.delivered` is not one, so a rule cannot loop on itself), a known field, a value unless `exists`, a header name, a valid regex. `run_webhook_rule_subscriber` listens on the event bus and, for each event, queues one delivery per enabled rule on an enabled endpoint that listens to the event and whose filter matches, in rule order; the binary runs it beside the dispatcher. The due queue is read in insertion order (`rowid`), since ULIDs made in the same millisecond do not sort. Proven at the API: WH-02.1 to WH-02.5 and WH-03.1 (an ingested email reaches the queue through a rule); they are ticked with the CLI, MCP, seed and live screens (W9, W10), and WH-02.6 with the live rules screen. The Webhooks list queries in the UI now wait until the binary serves them, so a live screen that reads another screen's list (Endpoints reads templates) no longer calls a path that is not there yet.
- **W4a (template engine):** `sendmock-core/src/template/` now renders with `minijinja` behind the same `render_template` (lenient, as before) plus `render_template_in_mode` for strict rendering; the provider definitions pass their fixture tests unchanged. Lenient mode uses `minijinja`'s chainable undefined (missing values render empty, even several levels deep) and warns, as the UI preview does, for each `{{ path }}` the context does not have unless `default` or `required` follows; strict mode uses semi-strict undefined, so `{% if %}` checks and `default` still work but printing a missing value stops the render with "Undefined variable: <path>" at its line and column. Unknown functions and filters and an unbalanced `{{` are found before rendering, at their place. Limits: 200,000 instructions of fuel per render ("The template ran too long and was stopped"), 1 MB of output, no loader (so `include` and `import` find nothing) and no environment access. Functions: `uuid`, `uuid7`, `ulid`, `now`, `now_iso`, `now_unix`, `timestamp`, `timestamp_ms`, `random_int`, `random_float`, `random_bool`, `random_string` (with `charset`), `random_hex`, `random_otp`, `random_choice` and `random_phone` (US numbers in the fictional `555-01XX` range). Filters: the `minijinja` built-ins for case, length, lists and `replace`, and SendMock's `default` (also for empty text), `required`, `capitalize`, `squish`, `truncate(n, end)`, `slice(start, end)`, `regex_replace`, `regex_extract`, `contains`, `slugify`, `pad_left`, `pad_right`, `number_format`, `urlencode` (as JavaScript's `encodeURIComponent`, so form bodies match the preview), `base64_encode`, `base64_decode`, `hex_encode`, `escape_html`, `strip_html`, `json`, `tojson`, `fromjson`, `pick`, `omit`, `md5`, `sha1`, `sha256`, `sha512`, `hmac_sha256` and `hmac_sha1` (hex, or Base64 with `encoding="base64"`), `date(format, tz)` (UTC or an offset such as `+05:30`), `date_add`, `unix`, `e164`, `phone_country` and `phone_national` (a calling code table of 30 countries). Values print as text, `true` and `false`, or compact JSON; inside a JSON string they are escaped unless `json` or `tojson` wrote them. The provider signature helpers (`twilio_signature` and the others the template reference lists) stay with the provider templates (W5, W8). WH-07.3 and WH-07.7 have table-driven tests; WH-07.7 is ticked, WH-07.3 waits for the Phase 4 fake data and aliases.

- **W4b (variables):** migration `0013` adds `webhook_variables` (a null `endpoint_id` is a global variable; a name is unique per scope) and `WebhookVariableRepository`; deleting an endpoint deletes its own variables. Operations in `sendmock-ops/src/webhooks/`: list (with `endpoint_id`), create, update (the whole variable, as the sheet sends it), delete, regenerate (`409 not_fixed_random` for anything but a Fixed random variable) and preview. Checks match the variable sheet (`web/src/lib/webhooks/validate-webhook-variable.ts`): a lowercase name unique in its scope, a value that fits the kind, Per send or Fixed for a random variable, an existing endpoint for an endpoint variable, and a Dynamic, Random or Computed value that renders. Secrets are masked (`••••` and the last four characters) in every answer, and an empty secret on an edit keeps the stored one. A Fixed random variable gets its value when saved, keeps it through edits that leave the generator alone, and gets a new one on Regenerate. `resolve_template_variables` gives a render its `vars`: send-time values win over an endpoint's variables, which win over global ones; fixed kinds resolve first, then Dynamic and Random expressions (evaluated with `evaluate_template_expression`, a new core function that keeps the value's type, so a number stays a number), then Computed templates, which read the values before them. A variable that cannot resolve is reported as `vars.<name>: <problem>`. The preview resolves against the latest email as an `email.received` event (or a built-in sample) with the global variables as `vars`. `SENDMOCK_VAR_*` stays in Phase 4. Proven: WH-07.1, WH-07.2 (without the environment), WH-07.4 (Fixed), and the API part of WH-07.11 to WH-07.13; they are ticked with the CLI, MCP and live Variables screen (W10).
- **W4c (rendering endpoint requests):** `enqueue_webhook_delivery` now renders each endpoint's request when a delivery is queued, through the same `render_delivery_request` the preview uses, so the preview shows what is sent. The context is the event (`event`, `data`, `email` or `sms`) plus `endpoint` (name, URL), `delivery` (id, attempt 1, trigger), `rule` (id and name, null for a manual send), `sendmock` (version, `http_url`), `request_id` (a ULID made once per delivery) and `vars` from `resolve_template_variables` with the endpoint's own variables. The URL renders and must still be an http(s) URL; query params are rendered and URL-encoded onto it; headers render over `user-agent` and the body's `content-type`, and a header that renders a line break is an error. Bodies: None; Fields as nested JSON (`user.email` makes `{"user": {"email": ...}}`) with each value typed, where a value that does not fit its type is an error, or as a form body; Raw with the endpoint's content type, values escaped inside a JSON body so a quote in a subject keeps it valid, and a warning when the result is not JSON; Template still sends the native envelope until W5. A strict render error stores the delivery as `render_failed` with the errors as `<source>: <message>`, with no request and no due time, so it is never sent or retried and does not publish `webhook.failed` (a rule on that event could loop); lenient mode renders missing values empty and logs the warnings. Retries send the stored request, so per-send random values stay the same and the next send gets new ones. `POST /webhooks/endpoints/preview` (CLI `sendmock webhook render`, MCP `sendmock_webhook_render`; this is the plan's `/webhooks/render`) renders the sent settings, or with `endpoint_id` alone the saved endpoint as stored (the contract's `endpoint` is now optional, so the documented `sendmock webhook render --endpoint-id <endpointId>` works), against the latest email or the built-in sample, a chosen email or SMS (a captured HTTP request answers 404 until the HTTP catcher), with send-time `variables`, and answers the problems with their source, line and column. Secret variable values (four characters or more) show as `••••••` in the preview and in the stored sent request; the request in the queue keeps them, since it is what is sent. Proven: WH-07.5 (ticked), WH-07.4 per send, WH-07.6 for JSON and form, WH-07.8 at the API (ticked with the live screens, W10). WH-07.6 also named multipart bodies, which neither the contract nor the request editor offers; on 2026-10-30 multipart (with file fields) moved to Phase 4 as WH-07.16, next to the SendGrid Inbound Parse and Mailgun routes formats that send it, and WH-07.6 now covers JSON and form.
- **W5a (template catalogue and storage):** the 18 built-in templates come from two exported files: `webhook-template-catalogue.json` (name, service, category, events, description, required variables; new in `export-builtin-definitions.ts`) and the existing `webhook-templates.json` (method, content type, header and body templates, doc link, verified date). Migration `0014` adds `webhook_templates` (custom templates, and edited built-ins as `source = builtin` rows that replace the shipped shape until Reset to default deletes them) and `webhook_template_revisions` (the last 20 saves of each). Operations: list (built-ins first, then custom ones in the order made), show (with `used_by_endpoint_count`), create (a blank custom template starting as native JSON, id `custom.<slug>` made unique with `_2`, `_3`), clone (`Copy of <name>.`), update (the request shape always, name, description, events and required variables only for custom templates; an edited built-in becomes Modified), delete (custom only, `409 read_only_template` otherwise, `409 template_in_use` while endpoints use it unless `?endpoints=detach`; W5b makes those endpoints detached with a copy, as [06](06-api.md) and [13](13-webhook-templates.md) say), revisions (newest first), restore (as a new save), render and reset (`409 not_modified` unless edited). A save is refused with the new `422` error (`OperationError::Unprocessable`, code `template_invalid`) when the draft has the wrong shape (the editor's rules: POST, PUT, PATCH or GET, a content type, valid header names, a body unless GET) or does not render against the sample of its first event. Rendering (`render_template_request`) renders the body first (values escaped inside a JSON body) and then the headers, which read a form body's fields as `body_fields`, so `twilio_signature(endpoint.url, body_fields, ...)` signs what is sent. `WebhookTemplateFunctions` adds the provider helpers to the standard functions for templates and endpoint requests: `twilio_signature` is real; `mailgun_signature`, `svix_signature` and `stripe_signature` have the provider's shape and are signed for real with the email providers (Phase 4, WH-06.2). The core engine gains the `sendgrid_event`, `ses_type` and `resend_type` filters. A preview with no message renders against the latest email for email templates, or a built-in sample of the template's first event type (SMS, HTTP capture, webhook failure). Proven at the API: every built-in renders without errors against its sample and a real email or SMS (WH-08.1, for the first declared event), the detail and preview (WH-08.4), create and clone (WH-09.1), revisions and refusal (WH-09.5), delete with detach (WH-09.6), editing with the draft preview (WH-09.7), Modified and reset (WH-09.8) and custom details (WH-09.9). They are ticked with the live Templates screens (W10); WH-08.1 also needs a real event of every declared type, which comes as the other events are built.
- **W5b (templates on endpoints):** migration `0015` adds `webhook_endpoints.detached_template`, a detached endpoint's own copy of its template's request shape (NULL while linked). Endpoint create and update choose the copy (`choose_detached_template`): none while linked, the earlier copy while the endpoint stays detached from the same template (even after that template is deleted), otherwise the template as it is now; an unknown `template_id` is refused with 400. `render_delivery_request` resolves the endpoint's template in Template mode (`EndpointTemplate`: the shipped native shape, a draft, or a missing template, which is a `body` error) for the queue and the preview, which uses the stored copy when `endpoint_id` names an endpoint detached from the same template and previews against a sample of the template's first event. A draft renders with `render_template_request` after the endpoint's extra fields are folded in (`fold_endpoint_overrides`: before the last `}` of a JSON body, `&name=value` on a form body); its problems, header ones included, are tagged `body` as in the mock, so `header.<n>` keeps pointing at the endpoint's own headers. Headers layer as the defaults (`user-agent`, `content-type`), then the template's (lowercased), then the endpoint's. The native shape is still sent as the event's own JSON; extra fields are rendered as text onto its root object. Deleting a template with `?endpoints=detach` keeps the endpoints on that template id, `detached`, with a copy (the registry's `endpoints` text now says so). `POST /webhooks/endpoints/{endpointId}/save-as-template` (CLI `sendmock webhook endpoint save-as-template`, MCP `sendmock_webhook_endpoint_save_as_template`) saves the endpoint's template (its copy while detached) with its headers and extra fields folded in, as a custom template with the base template's service, events and required variables and the description `Saved from the endpoint "<name>".`. ## Design notes

- **Crates:** the domain lives in `sendmock-webhooks` (layer 2): `endpoint`, `signing` (Standard Webhooks, `WebhookSecret`), `retry_policy` (Strategy), `rule_filter` (filter operators as Strategies), `delivery_plan`, `payload` (Builder for requests). Storage is `WebhookEndpointRepository`, `WebhookRuleRepository`, `WebhookDeliveryRepository`, `WebhookTemplateRepository` and `WebhookVariableRepository` in `sendmock-store`; operations in `sendmock-ops/src/webhooks/`.
- **Queue:** a delivery row is the queue entry (`status`, `attempt`, `next_attempt_at`). One dispatcher task in the binary claims due rows, sends them through the `WebhookSender` trait, records the attempt and schedules the next from the retry policy; on start it picks up rows left `queued` or `retrying`, so a restart loses nothing. Tests drive the policy with the `Clock` trait and a recording sender.
- **Delivery rows:** one `webhook_deliveries` row per attempt, as the deliveries log shows them. A row starts `pending` (or `render_failed`, never sent), becomes `in_flight`, then ends `succeeded`, `failed` or `exhausted`. A `failed` row whose retry is still due carries `next_attempt_at`; when it comes due, the dispatcher clears it and inserts the next attempt's row with the same `event_id` (so `webhook-id` stays the same, WH-04.2). The last allowed attempt ends `exhausted`; a `4xx` that is not retried ends `failed` without a next attempt. Both fire `webhook.failed`. Cancel turns a `pending` row, or a `failed` row with a retry due, into `cancelled`. On start, rows left `in_flight` go back to `pending`.
- **Stored request:** a row keeps the rendered request without signature headers; the sender adds `webhook-id`, `webhook-timestamp`, `webhook-signature` (both secrets during a rotation overlap) and `webhook-attempt` for each attempt, and the row records the request as sent.
- **Events:** rules subscribe to the existing event bus; the dispatcher never reads email or SMS tables, it renders from the event payload, so webhooks stay a subscriber like WebSocket and SSE.
- **One template engine:** [22](22-configurable-providers.md) asks provider definitions and webhooks to share one engine. Phase 2 built a small engine in `sendmock-core` for provider definitions; W4 replaces its internals with a `minijinja` environment carrying SendMock's filters (`json`, `urlencode`, `lower`, `upper`, ...) and functions (`uuid`, `random_hex`, `now_iso`, ...), behind the same function signatures, so the provider runtime is untouched and its fixture tests are the regression check. JSON-context escaping stays as built in Phase 2.
- **Status callbacks** of Phase 2 move onto a persistent queue in W8a and gain retries like webhooks (SM-08.3), keeping the provider's format and signature. The queue is the per-message `sms_callback_attempts` table, not `webhook_deliveries`: a callback has no endpoint and no Standard Webhooks signature, and the mock shows callbacks only in the message detail, never in the deliveries log or the metrics (owner's choice, 2026-11-05). Each attempt keeps the request rendered for the first one, so a retry sends the same body and `X-Twilio-Signature`.
- **Reply webhook failures (W8c):** every call an inbound message makes (the reply webhook, its fallback, each `<Redirect>` and `action` fetch) is stored in `sms_reply_webhook_attempts` with the request, the response or error, Twilio's error code and the TwiML verbs read from it; the latest run's outcome is the `reply_webhook` column on the message (target, outcome, last status code, the primary's error code, `used_fallback`, reply count), which resend replaces. Errors follow Twilio's docs (checked 2026-11-05): a non-`2xx` answer or no answer within 15 s is 11200, a refused or reset connection 11205, an answer that is not a `<Response>` document 12100, and a content type Twilio does not read 12300. Twilio reads `text/xml`, `application/xml` and `text/html` as TwiML and sends a `text/plain` body back to the sender as the reply, so SendMock does the same (the plan said only the two XML types; the owner was told on 2026-11-05). When the first request fails and a fallback URL is set, the fallback gets the same request plus `ErrorCode` and `ErrorUrl`; `<Redirect>` and `action` fetches have no fallback, and nothing is retried. `POST /sms/{smsId}/reply-webhook/resend` runs the webhook again in the request (so it answers with the new attempts), with the format the message was simulated with; an outbound message is `409 outbound_sms`, a number without a reply webhook `409 no_reply_webhook`. The contract's `TwimlVerb` gains `action` and `method` on `Message` and `method` on `Redirect`, so the drawer shows where the next fetch went.
- **Outcome rules for email** reuse the SMS outcome rule design (`/outcome-rules/sms` in Phase 2): pattern rules evaluated before magic addresses, then the profile.

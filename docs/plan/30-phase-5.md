# 30. Phase 5: Distribution and 1.0 stable

Phase 5 puts SendMock on every channel people install developer tools from, holds the binary to its size and speed budgets, finishes the docs, and cuts the first stable release: the install scripts, the Docker stable tags and hardening, the Scoop bucket, the npm wrapper and `cargo install`, our signed APT and YUM repository, WinGet, Chocolatey, AUR, COPR and Nixpkgs, the catch-all catcher port, the performance budgets, `sendmock --demo`, the Claude Code plugin with the MCP registry listing and skill evals, the remaining acceptance criteria, the complete versioned docs with the Deeper pages, and `1.0.0` ([11](11-roadmap.md#phase-5-distribution-and-10-polish-about-1-2-weeks)).

## Goal and done-when

**Done when** (from [11](11-roadmap.md#phase-5-distribution-and-10-polish-about-1-2-weeks)): `v1.0.0` installs and runs via each channel on macOS, Linux and Windows, meeting the success criteria in [01](01-vision.md#success-criteria-for-v10). In full:

- every Phase 5 item in [PROGRESS.md](PROGRESS.md) is ticked, and every feature in [acceptance/](acceptance/README.md) is `Accepted` (or has a recorded reason to leave a criterion for after 1.0);
- the Install channels workflow (W11) installs the published `1.0.0` through every channel in [09](09-distribution.md#package-channels-by-stage-decided-2026-10-27) on the operating systems that channel serves, and runs the release test cases 2 to 8 against what it installed;
- the performance budgets pass in CI on the release build;
- the website serves the 1.0 docs at `/`, the `develop` docs at `/next/`, and `main` is the default branch.

What only the owner can do is listed in [Owner steps](#owner-steps): accounts, tokens, the trademark check, merging #48 and running the release workflows. Everything else is built and proven in CI before those steps, so a release only has to run what is already tested.

## Design notes

- **Same patterns as before:** a channel is one more publish step in `release.yml`, written from `SHA256SUMS` by a script in `scripts/release/` with unit tests beside it (as `homebrew-formula.ts` is), installed in CI from the files the release is about to publish before anything is published, and pushed only when the owner's token for that channel is set (`HAS_<CHANNEL>_TOKEN`, as Homebrew does). No channel's script downloads from the internet in a test: a local HTTP server (`python3 -m http.server`, on every runner image) serves the tested archives, and the scripts and manifests take the download base URL as an input.
- **Install scripts (W1):**
  - `scripts/install/install.sh` (POSIX `sh`, no `bash`-only syntax, checked with `shellcheck --shell=sh` already on the runner images) finds the target from `uname -s` and `uname -m` (Darwin `arm64`/`x86_64`, Linux `x86_64`/`aarch64` to the musl targets; anything else stops with the supported list), downloads the archive and `SHA256SUMS` from `releases/latest/download/` (stable) or `releases/download/beta/` (beta, the rolling pre-release), checks the archive's line with `sha256sum` or `shasum -a 256`, unpacks it into a temporary folder and moves `sendmock` into the install folder (`$HOME/.local/bin` unless `--install-dir` or `SENDMOCK_INSTALL_DIR`). When that folder is not on `PATH` it appends one `export PATH=...` line, marked with a comment, to the profile of the user's shell (`~/.zshrc`, `~/.bashrc`, `~/.config/fish/conf.d/sendmock.fish`, else `~/.profile`), once; `--no-modify-path` skips that. Options: `--channel stable|beta` (or `SENDMOCK_CHANNEL`), `--install-dir`, `--no-modify-path`, `--help`; `SENDMOCK_DOWNLOAD_BASE_URL` replaces the GitHub address (tests and mirrors). It prints what it did and the next command (`sendmock`).
  - `scripts/install/install.ps1` does the same on Windows: the target from `$env:PROCESSOR_ARCHITECTURE` (`AMD64`, `ARM64`), `Get-FileHash`, `Expand-Archive`, the install folder `$env:LOCALAPPDATA\Programs\sendmock`, and the user `Path` set through `[Environment]::SetEnvironmentVariable` (read by every new shell). Parameters `-Channel`, `-InstallDir`, `-NoModifyPath`; since `irm ... | iex` takes no arguments, the beta is `& ([scriptblock]::Create((irm <url>))) -Channel beta`, or `$env:SENDMOCK_CHANNEL = "beta"` before the one-liner.
  - Tests: `scripts/install/install.test.ts` (Bun test, Linux and macOS) runs `install.sh` against a temporary folder served as `file://` with a fake archive: the stable and beta paths, a checksum mismatch stops with nothing installed, an unknown channel, an unsupported system, the profile line written once and not with `--no-modify-path`. In `release.yml` each test job runs release test case 9 (the install script for its platform, stable and `--channel beta`, from a local server holding the tested archive) and then checks `sendmock version` in a new login shell (`bash -lc`, `zsh -ic` on macOS, a new `pwsh` reading the user `Path` on Windows) (DS-01.5, DS-03.2). `publish` attaches both scripts to every release, so `releases/latest/download/install.sh` is the stable's and `releases/download/beta/install.sh` the beta's.
  - The install page's commands are already these URLs; its beta lines gain the `--channel beta` forms, and the existing install page test checks they match the scripts' options.
- **Docker (W2):**
  - Tags: `plan` gives a stable `latest X.Y.Z X.Y X` (the major tag was missing), a beta `beta X.Y.Z-beta.N`, and `edge` stays on every `develop` push (DS-02.4). The tag list moves from shell into `release-decisions.ts` (`decideDockerTags(version, channel)`) with unit tests, so `0.x` releases tag `0` too, as SemVer allows.
  - `-debug` variants: a `debug` stage in the `Dockerfile` copies the same binary onto `gcr.io/distroless/static-debian12:debug` (busybox shell, same non-root user and paths); `docker-edge.yml` builds both stages per platform and joins each tag with `-debug` (`edge-debug`, `beta-debug`, `1-debug`). `scripts/docker-image-test.sh` runs against both, and checks the debug image has `/busybox/sh` and the plain one has no shell.
  - `/templates`: the image sets `SENDMOCK_TEMPLATES_DIR=/templates` and creates the folder, so a mounted folder of template files loads with no flag (a missing or empty folder is already fine). The image test mounts a `sendmock.toml`, a seed file and a template file and reads each back through the API (DS-02.3).
  - After the push, `docker-edge.yml` checks what it published: `cosign verify` with the workflow's certificate identity, the SBOM and provenance attestations present (`docker buildx imagetools inspect --format '{{json .SBOM}}'` and `.Provenance`), and the compressed size under 25 MB from the manifest (DS-02.5).
  - `examples/docker/compose.yaml` (the app, SendMock with a seed file, the provider port, `depends_on: condition: service_healthy`) and `.github/workflows/docker-examples.yml` (the Compose example up and an email and an SMS read back; a job with SendMock as a `services:` container exactly as the docs show, sending over SMTP with `curl` and over the API) run the documented examples on every pull request that touches them and before every release (DS-02.6). The docs' snippets are read from these files by the docs test, so they cannot drift.
  - The image carries `LABEL io.modelcontextprotocol.server.name="io.github.shibbirweb/sendmock"` for the registry (W9).
- **Scoop, npm and cargo (W3a), Testcontainers (W3b):**
  - Scoop: `scoop-manifest.ts` writes `sendmock.json` (or `sendmock-beta.json`) with `version`, `architecture.64bit` and `arm64` URLs and hashes from `SHA256SUMS`, `bin: sendmock.exe`, `checkver` and `autoupdate` on the GitHub release; `publish` pushes it to `shibbirweb/scoop-bucket` (`bucket/`) with `SCOOP_BUCKET_TOKEN`. The Windows test jobs install Scoop and run `scoop install <manifest>` with the URLs on the local server, then `sendmock version` in a new shell.
  - npm: the esbuild pattern, which works with every package manager because it needs no install script: `sendmock` holds a small `bin/sendmock.js` launcher and lists `@sendmock/<os>-<cpu>` packages (`darwin-arm64`, `darwin-x64`, `linux-x64`, `linux-arm64`, `win32-x64`, `win32-arm64`) as `optionalDependencies`, each with `os` and `cpu` set and only the binary inside, so the package manager installs the one that fits. The launcher finds that package's binary and runs it with the arguments, the exit code and the signals passed through; with none installed it says which package is missing. `npm-packages.ts` writes the seven `package.json` files from the version, and the launcher has unit tests. `package.json` carries `mcpName` for the MCP registry (W9). `publish` publishes them with npm trusted publishing (GitHub OIDC, no token kept) under the `beta` or `latest` dist-tag. The test jobs `npm pack` the launcher and the platform's package, install both tarballs into a temporary project with `npm install`, and run `npx sendmock version` (npm is used here only as users use it; the repository stays on Bun).
  - `cargo install sendmock` (stable only): every crate gets `description`, `license`, `repository` and the `version` from the workspace, and the `sendmock` crate's package includes the built `web/dist` and the skill (`include` in its `Cargo.toml`, with the release check's `build.rs` guard). A CI job builds the UI and runs `cargo publish --workspace --dry-run --locked`, which packages and builds every crate as crates.io would; `stable-publish` runs the real publish with crates.io trusted publishing. Before the first publish the owner checks the crate names are free (`cargo search`).
  - W3b, the Testcontainers modules (built and tested in Phase 2, DS-06), under the names they already have: Node `sendmock-testcontainers` on npm and Python `sendmock-testcontainers` on PyPI (both with trusted publishing), .NET `SendMock.Testcontainers` on NuGet (`NUGET_API_KEY`), Java `io.github.shibbirweb:sendmock-testcontainers` on Maven Central (`MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_TOKEN` and `MAVEN_SIGNING_KEY`), and Go through a `testcontainers/go/vX.Y.Z` tag, as Go modules in a subfolder need. Each module's version and default image tag come from the version files (`scripts/version.ts` writes them), and `testcontainers.yml` packages each as its registry would and loads the package.
    - **First beta (0.1.0-beta.1):** Maven Central rejected the Java module's bundle ("Bundle has content that does NOT have a .pom file") although it held the `.pom`; the Java module ships with the next beta, after the deployment's details on central.sonatype.com and a local bundle (`-DskipPublishing=true`) show the cause ([#219](https://github.com/shibbirweb/sendmock/issues/219)). npm refused the release too (`EOTP`: `NPM_TOKEN` needs a one-time password), so the Node module and the `npx sendmock` packages also ship with the next beta, published through npm trusted publishing ([#220](https://github.com/shibbirweb/sendmock/issues/220)).
- **Our APT and YUM repository (W4):** a static repository on the GitHub Pages site under `/packages/`, rebuilt by every website deploy from the newest stable and the newest beta release's `.deb` and `.rpm` assets (so no state is kept between deploys, and the newest of each channel is what `apt upgrade` sees):
  - `scripts/release/package-repository.sh` takes a folder of packages per component and writes `/packages/apt/` (`dists/stable` and `dists/beta`, `main` for `amd64` and `arm64`, through `apt-ftparchive`, `InRelease` and `Release.gpg` signed with `gpg`) and `/packages/rpm/<stable|beta>/` (`createrepo_c`, `repomd.xml.asc` signed), plus `/packages/sendmock.gpg` (the public key) and `sendmock-stable.repo` and `sendmock-beta.repo` files. The key is `PACKAGES_GPG_PRIVATE_KEY` (the owner makes it once, steps in the runbook); without it the website builds without `/packages/`.
  - Test (`linux-packages` in `release.yml`): a throwaway key made in the job, a repository built from the tested packages and a copy re-versioned one patch higher, served locally; in `debian:stable-slim` the documented steps (key into `/etc/apt/keyrings`, the `sources` line, `apt install sendmock`), then the higher version swapped in and `apt upgrade` moves to it; the same with `dnf` in `fedora` (DS-03.3). The install page shows the steps as numbered blocks.
- **WinGet, Chocolatey, AUR, COPR, Nixpkgs (W5):** stable only for WinGet, Chocolatey, COPR and Nixpkgs; AUR has `sendmock-bin` and `sendmock-beta-bin` ([16](16-website-and-releases.md#what-each-channel-publishes)). Each has a writer script with unit tests and a CI install:
  - W5a, WinGet: `winget-manifests.ts` writes the three manifests (`version`, `installer` with `InstallerType: zip`, `NestedInstallerType: portable`, `NestedInstallerFiles` and `PortableCommandAlias: sendmock` per architecture, `defaultLocale`) for `shibbirweb.sendmock`; the Windows x64 test job runs `winget validate` and `winget install --manifest` against the local server (local manifests turned on with `winget settings --enable LocalManifestFiles`). `stable-publish` submits them with `wingetcreate submit` and `WINGET_TOKEN`. Chocolatey: `chocolatey-package.ts` writes `sendmock.nuspec` and `tools/chocolateyinstall.ps1` (`Install-ChocolateyZipPackage` with both architectures' URLs and checksums); the Windows job runs `choco pack` and `choco install sendmock --source .` and `sendmock version`; `stable-publish` pushes with `CHOCOLATEY_API_KEY`, and the runbook notes moderation takes days.
  - W5b, AUR: `aur-package.ts` writes `PKGBUILD` and `.SRCINFO` for `sendmock-bin` and `sendmock-beta-bin` (`x86_64` and `aarch64` sources from the release archives, `provides`/`conflicts` with each other); a job in `archlinux:base-devel` runs `makepkg` as a non-root user against the local server and `pacman -U`, then `sendmock version`; `publish` pushes to `aur.archlinux.org` over SSH with `AUR_SSH_PRIVATE_KEY`. COPR: `packaging/copr/sendmock.spec` repackages the release archive as a binary RPM; a job in `fedora` runs `rpmbuild -ba` with the local archive and installs the result; `stable-publish` builds the SRPM and runs `copr-cli build shibbirweb/sendmock` with `COPR_CONFIG`. Nixpkgs: `packaging/nix/package.nix` (`stdenvNoCC.mkDerivation` installing the release binary per platform, `meta.mainProgram`, licences) with `nix-hashes.ts` writing its hashes from `SHA256SUMS`; a job in `nixos/nix` runs `nix-build` with the sources pointed at the local files and runs the result. Nixpkgs takes a pull request to `NixOS/nixpkgs`, which the owner opens once with this file; after that nixpkgs' update bot follows new releases, so the release workflow does not push there.
- **The catch-all port (W6):** `--catcher-addr <addr>` (`SENDMOCK_CATCHER_ADDR`, `catcher_addr` in `sendmock.toml`; off by default, `127.0.0.1:8030` in the docs, `0.0.0.0` when given in Docker with port `8030` exposed) starts one more listener whose every request, at any method and path, is captured as `/catch/<bin>/...` would be: the first path segment names the bin and the rest is the path, and a request at `/` goes to the bin `default`. It reuses `catch_routes.rs`'s capture function, so presets, response rules, delay and failure rates, `http.captured` and `wait/http` behave the same. `--ready-json` and `GET /info` gain `catcher_url` (null when off), and the HTTP screen's catch URL box shows the port form beside the path form when it is on. Tests: `catcher_port.rs` (any path and method captured into the right bin, `/` into `default`, a rule's reply, the listener off by default, `127.0.0.1` by default), a CLI flag test, the `/info` contract sample, and the live UI test showing the port URL (HC-01.4).
- **Performance budgets (W7):** `scripts/performance-budget.ts` runs against a release binary on the CI's Linux x64 runner and measures: the binary's size (`x86_64-unknown-linux-musl`), cold start (spawn with `--ready-json` and port `0` until the JSON line, median of 10 with `--db memory`), idle memory (`VmRSS` from `/proc/<pid>/status` 5 seconds after ready, with no traffic), and SMTP ingest (10 connections sending 2,000 small messages in total with the built-in submission client, the time until `GET /api/v1/emails` counts them all). Limits live in `scripts/performance/budgets.json` (20 MB, 200 ms, 30 MB, 500 messages a second); an override is an entry beside the limit with a higher value and a `reason`, so it shows in review, and the script refuses an override without a reason. It prints a table and writes it to the job summary; any metric over its limit fails the job (DS-07.1, DS-07.2). It runs in `ci.yml` as "Performance budgets" on pull requests (one release build, cached) and in `release.yml` against the tested archive. Unit tests cover the budget file rules and the comparison.
- **`sendmock --demo` (W8):** `sendmock serve --demo` (`SENDMOCK_DEMO=1`) fills a fresh instance with the same sample data the website demo shows, through the operations real traffic uses, so every screen has something to look at. `web/src/mocks/demo/build-demo-steps.ts` turns the Stage A fixtures (seeded, so the output is stable) into operation calls, and `export-builtin-definitions.ts` writes them to `crates/sendmock-ops/builtin/demo-data.json`: catcher bins, webhook endpoints (pointed at SendMock's own `/catch/demo-...` bins, so their deliveries stay on the machine) and rules, the outbound emails, the SMS conversations, a verification and an HTTP sample, and card checkouts paid, declined and left open. A step can save its answer and later steps read it (`{{saved.<name>.<field>}}`, and `{{http_address}}`), filled by the scenario runner's placeholder code. `load_demo_data` in the operations runs each step through the registry; it loads only into an instance with no emails, SMS or webhook endpoints, and the binary calls it after the background tasks start, so the rule subscriber sees the events. Criteria PL-09 below.
- **Plugin, MCP registry and evals (W9, split into W9a to W9c):**
  - W9a, Claude Code plugin: `plugin/` holds `.claude-plugin/plugin.json` (name `sendmock`, version from the version files, description, author, homepage, repository, licence, keywords), `skills/sendmock/` (a copy of `skill/sendmock/` written by `bun scripts/plugin-skill.ts sync` and checked for drift by `bun scripts/plugin-skill.ts check` in CI, since an installed plugin is copied into a cache and cannot reach outside its folder) and `.mcp.json` (`sendmock` running `sendmock mcp`, the same entry `sendmock ai install --target claude-code` writes, which reaches the running instance). The repository root gets `.claude-plugin/marketplace.json` (marketplace `sendmock`, one entry with `source: ./plugin`), so `/plugin marketplace add shibbirweb/sendmock` and `/plugin install sendmock@sendmock` work. A new CI job installs Claude Code (no API key needed), runs `claude plugin validate --strict` on the plugin and on the marketplace, adds the checkout as a marketplace, installs `sendmock@sendmock` and reads `claude plugin details sendmock` for the skill and the MCP server; it then checks the installed skill is byte for byte the output of `sendmock ai skill` from the binary built in the same run. `scripts/version.ts` keeps `plugin.json`'s version in step; a unit test checks the manifests' fields and that the marketplace entry and the plugin agree (AI-05.5).
  - W9b, MCP registry: `server.json` at the root on the `2025-12-11` schema (the current one in the registry's docs on 2026-11-06); name `io.github.shibbirweb/sendmock`, title, description (at most 100 characters), repository, website, and two packages: npm `sendmock` (`npx -y sendmock mcp`, ownership proved by `mcpName` in the launcher's `package.json`) and the OCI image `ghcr.io/shibbirweb/sendmock:<version>` (`docker run -i --rm` with `mcp --server http://host.docker.internal:8025`, ownership proved by the image's `io.modelcontextprotocol.server.name` label), each with the environment variables `sendmock mcp` reads (`SENDMOCK_SERVER`, `SENDMOCK_TOKEN` as a secret, `SENDMOCK_MCP_TOOLSETS`). `scripts/version.ts` writes the server's version, the npm package's version and the image tag. CI validates it with the registry's own `mcp-publisher validate` (changed while designing it: the publisher's validator checks the schema and the registry's rules through the registry, so no schema is vendored), downloaded pinned to a release and checked against its Sigstore bundle with `cosign verify-blob`, and `scripts/release/mcp-server-json.test.ts` checks what the registry cannot know: the name matches the Docker label and the npm `mcpName`, every package is on a registry the official registry allows, and the versions and image tag follow the workspace version. The new `mcp-registry` job in `release.yml` runs for a stable after the npm and Docker publish: it downloads and checks `mcp-publisher` the same way, then `mcp-publisher login github-oidc` and `mcp-publisher publish` (no token kept) (AI-05.6).
  - W9c, skill evals (changed while designing it, 2026-11-06: Claude Code now ships `claude plugin eval`, so the evals use its case format instead of a TOML format and runner of our own): `plugin/evals/<case>/` holds `prompt.md` (the task in a user's words, `max_turns`, `timeout_seconds`) and `graders/*.md` (the skill fired, the right MCP tools were called, the reply carries what was asked for), plus two files of our own beside them that `claude plugin eval` ignores: `seed.toml` (the state to start from) and `sendmock-eval.json` (`before`: the traffic the app sends before the agent starts, such as a Twilio send on the provider path; `checks`: API reads, each a path and the field values some item of its answer must have). `scripts/skill-evals.ts run` builds nothing itself: for each case it starts a fresh in-memory SendMock from the given binary on the default ports (where the plugin's `sendmock mcp` looks) with the case's seed, sends the traffic, runs `claude plugin eval plugin/evals/<case>/prompt.md --runs 1 --ablation none --mocks off --allow-tools "mcp__plugin_sendmock_sendmock__*" --trust-plugin --json`, then checks the end state through the API, and reports each case (score, graders, end-state checks) in the job summary, keeping each case's JSON result and HTML report (with the run's tool calls) as an artifact. The "Skill evals" workflow runs it on demand and from `stable-publish` before a stable when `ANTHROPIC_API_KEY` is set. `scripts/skill-evals.ts check`, run in CI on every pull request against the binary built there, checks every case is well formed: the prompt and graders parse with known grader types, every `tool_used` and `tool_order` grader names a tool the MCP server lists with its default toolsets, the case checks its outcome (an end-state read or a `regex` or `llm` grader), the seed applies to a fresh instance, the traffic is accepted, and every end-state read is a `GET` operation in `docs/api/openapi.yaml` whose response schema has the fields named (AI-05.7).
  - W9c changed 2026-11-08 (owner decision: no real agent and no model calls in any test, so no `ANTHROPIC_API_KEY`): the evals run with a **scripted agent** instead of `claude plugin eval`. Each case gains `scripted-run.json`, the tool calls an agent following the skill makes, in order: `Skill` (`{"skill": "sendmock"}`), then `mcp__plugin_sendmock_sendmock__<tool>` calls whose inputs may name an earlier call's answer as `{{results.<call number>.<field>}}` (an endpoint's `id` for its rule). `scripts/skill-evals.ts run` starts the case's SendMock as before, replays the calls: `Skill` answers the plugin's `SKILL.md`, and each MCP call goes through `tools/call` to a real `sendmock mcp` (the server the plugin starts) and fails the case when the tool answers an error. The reply is made only of the tools' answers, so a `regex` grader such as the OTP still has to find the value in what SendMock answered. The graders are evaluated by the script itself, deterministically: `tool_used` (tool name, `input_match` against the input's JSON), `regex` on the last message and `tool_order`, weighted as in their files; the score must reach the threshold (1 by default), and the end-state reads must pass. `check` also refuses a case without a scripted run, a call to a tool the MCP server does not list or the skill does not name, and grader types that need a model (`llm`, `baseline`). CI runs `check` and `run` on every pull request against the binary built there; the "Skill evals" workflow, its call from `stable-publish` and the `ANTHROPIC_API_KEY` secret are removed. - **W19 design (realtime under load, 2026-11-12, owner report, [#224](https://github.com/shibbirweb/sendmock/issues/224)):** when an app sends thousands of emails, the web UI stops showing new mail.
  - **Cause:** `RealtimeProvider` (`web/src/features/realtime/realtime-provider.tsx`) calls `invalidateQueries` for every event. The `["emails"]` key covers every list, every loaded page of the infinite list and the open message's detail, raw and timeline queries, and TanStack Query cancels a refetch in flight before it starts the next one (`cancelRefetch` is true by default). Under a burst each event cancels the last list request, so none finishes. Each event also writes the bell store and shows its own toast. On the server, a WebSocket client more than 1,024 events behind skips them with only a log warning (`RecvError::Lagged` in `resumable_event_stream.rs`), and after a reconnect the UI neither resumes nor refetches.
  - **How Mailpit does it** (read from `axllent/mailpit` on `develop`, 2026-11-12): the `new` event carries the message summary, and the mailbox view puts it into the list it already holds (`unshift`, then `pop` past the page size, skipping an ID already there) with no request. On a later page it only moves the page offset, and updates the URL at most twice a second. Totals come from a separate `stats` event the server sends at most four times a second (one pending broadcast at a time, 250 ms). Toasts and browser notifications pause for 2 seconds after one is shown. Deletes refetch once, 500 ms after the last. The hub serializes each event once, gives each client a 256-message buffer and drops a client whose buffer is full; the client reconnects after 1 second and reloads the mailbox when it was away more than 5 seconds.
  - **Client fix** (`web/src/features/realtime/`):
    1. An event batcher queues events and flushes them every 250 ms, so a burst of thousands becomes four flushes a second.
    2. Each flush writes the events whose `data` has the list-view fields into the cached first page of the matching lists with `setQueryData`: newest first, IDs already there skipped, trimmed to the page size, as Mailpit does. Each area (email, SMS, HTTP, webhooks, payments, push) registers its own cache patch, so the batcher does not change when an area is added.
    3. What cannot be patched (the `/stats` counters, filtered or later pages) is invalidated once per flush with `cancelRefetch: false`, so a request in flight always finishes. Invalidation uses the list keys only (`["emails", "list"]`, `["emails", "infinite-list"]`), never the open message's detail, and an infinite list refetches its first page only.
    4. Bell notifications are added in one store write per flush, and at most one toast shows every 2 seconds, saying how many more arrived ("and 241 more").
    5. After a reconnect the open lists are refetched once.
  - **Server fix:** a realtime client that falls behind is closed (close reason `lagged`) instead of skipping events silently; the client reconnects and refetches (step 5). No new event type and no change to the API contract.
  - **Proof:** Vitest unit tests for the batcher, the cache patches and the toast limit with a fake clock; a Rust test that a lagging WebSocket client is closed; a live Playwright test (`web/tests/live/`) that sends 5,000 emails over SMTP against a release binary while the mail list is open, counts the browser's list requests and checks the list, the counters and a message opened during the burst.

# 29. Phase 4: Integrations, fidelity and AI

Phase 4 makes SendMock a drop-in for the providers apps already use and gives agents a first-class way in: the email providers' HTTP send APIs and their webhook formats, configurable and custom email and SMS providers, email quality checks, release and forwarding, inbound email and Mailgun-style routes, the rest of the webhook templating (fake data, aliases, environment variables, multipart bodies, the remaining built-in templates), more SMS providers and WhatsApp, the HTTP catcher backend, chaos and scenarios, more payment gateways with subscriptions and disputes, the published OpenAPI spec, the AI integration (MCP resources and prompts, streamable HTTP, the agent skill, `sendmock ai install`, `llms.txt`) and example apps in eight languages ([11](11-roadmap.md#phase-4-integrations-fidelity-and-ai-about-2-3-weeks)).

## Goal and done-when

**Done when** (from [11](11-roadmap.md#phase-4-integrations-fidelity-and-ai-about-2-3-weeks)): all eight example apps pass their smoke tests in CI, and an agent in Claude Code and Codex completes the example session in [14](14-ai-integration.md#example-what-an-agent-session-looks-like). In full:

- every Phase 4 item in [PROGRESS.md](PROGRESS.md) is ticked and the Phase 4 criteria of the features below have passing tests that name them;
- the `examples/` apps for PHP, Node, Python, Go, Java, Rust, Ruby and .NET run in CI against a release binary;
- the HTTP Catcher, Scenarios and Mail > Providers screens run in the live UI suite with real data and no failing calls;
- the agent session runs through the MCP server and the skill, recorded as a scripted MCP client test in CI (a real agent run in Claude Code and Codex is checked by hand before the release).

## Design notes

- **Same patterns as before:** every provider emulation is an Adapter registered in the provider runtime beside Twilio, Vonage, Stripe, PayPal and SSLCommerz, answering at the provider's real paths on the provider port and under `/providers/<key>/...`, with the provider's real answer and error shapes and a fixture test built from its docs; every new operation comes with REST, CLI, MCP and skill docs from the `sendmock-ops` registry; every new screen or tab joins the live UI suite.
- **Outbound traffic stays off by default:** release, auto-forward and HTTP catcher forwarding only reach the network when an allowlist is configured ([AGENTS.md](../../AGENTS.md#project-rules)); everything else keeps working with outbound traffic blocked, as the Payment apps workflow proves for payments.
- **Official SDKs where they exist:** each provider emulation is checked with the provider's official SDK in CI, pointed at the provider port by its base URL setting, or by swapping the provider's host in the SDK's HTTP client when it has no base URL setting (as for PayPal in Phase 3P W12b).
- **The email providers' HTTP send APIs (W1):** email providers are data, like SMS providers: the mock already ships the six built-in definitions (`email-provider-fixtures.ts`: SendGrid, Mailgun, Postmark, Resend, SES v2, Brevo) with their operations, field mappings (`personalizations[*].to[*].email`, `content[type=text/html].value`, `h:*`), validation rules, success and error responses and message id templates, and the binary's provider runtime already reads those source paths for SMS. So W1 does not hand-write six adapters: it runs the same definitions for the `email` area. W1 is split into four commits:
  - W1a, the runtime and single sends: `export-builtin-definitions.ts` also writes `crates/sendmock-ops/builtin/email-providers.json`; the provider catalogue loads the `email` area beside `sms`, and the provider runtime routes a matched email operation of kind `send` to a new `email_send_operation_kind.rs`. It reads the parts (`from`, `to`, `cc`, `bcc`, `reply_to`, `subject`, `text`, `html`, `tags`, `headers` as `name: value`, `attachments` as each item's JSON, `template_id`, `template_data`), applies the definition's validation rules and answers its error responses, checks the credentials when the definition asks to, builds the message with the native send's MIME builder (attachments read from the provider's own shape: `content` or `Content` in base64, `filename`, `Name` or `name`, `type`, `ContentType` or `content_type`, `content_id` or `ContentID`), ingests it as sent by the app with the provider's key, runs the delivery outcome simulation as `/send` does, and answers the success response with `message.provider_id` from the message id template. Multipart requests (Mailgun) read their text fields and their file parts as attachments, extending W12a's form reader. Tests: one API test file per provider built from its docs' request and response examples (a send, a missing field, an invalid address, a wrong key when credentials are checked), at the real paths on the provider port and under `/providers/<key>/` (EM-08.1 to EM-08.3).
  - W1b, batch and template sends: the `send_batch` kind (Postmark `/email/batch`, Resend `/emails/batch`) sends each message on its own and answers one item per message (the success template's body, or the failure's for a message refused), as a bare list for Postmark and under `data` for Resend; `send_with_template` (Postmark `/email/withTemplate`) is a send. Migration `0027` adds `email_provider_sends` (the email, the provider, the provider's own message id, a template send's id and data), so the email detail's `template` answers the Template data tab, and a template send needs no body. (Decided while building, 2026-11-05: the batch wrapper is a small table by provider key until the definition gets a field for it, as [22](22-configurable-providers.md#14-open-points) leaves batch answers open.)
  - W1c, local templates: the seed file's `[[email.templates]]` (`id`, `subject`, `text`, `html`, rendered with the template data by the webhook template engine) render a template send whose id matches, so the stored email has the body the provider would have sent (EM-08.4). (Decided while building: SES v2's `Content.Raw.Data` needs a `raw` message part in the provider contract, so it moves to W4 with the definitions' other contract changes.)
  - W1d, the official SDKs: `examples/email-providers/node/` sends through `@sendgrid/mail`, `mailgun.js`, `postmark`, `resend`, `@aws-sdk/client-sesv2` and `@getbrevo/brevo`, each pointed at the provider port by its base URL setting , and reads every message back through `GET /api/v1/emails`, in a new "Email provider SDKs" workflow against a release binary run offline as in Payment apps, also run by Release build (EM-08.5).

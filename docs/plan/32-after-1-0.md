## A1. Mailpit API compatibility (EM-19)

**Why:** SendMock listens on Mailpit's ports (SMTP 1025, HTTP 8025, [10](10-open-questions.md)), so an app switches by changing nothing. Its test suite does not: tests that read mail through Mailpit's API (`/api/v1/messages`, `/api/v1/message/latest`, `/api/v1/search`) fail against SendMock. [10](10-open-questions.md) §9 recommended compatibility aliases after 1.0; this builds them.

**Source of truth:** Mailpit's own API definition, `server/ui/api/v1/swagger.json` in `axllent/mailpit` at `v1.33.0` (the latest release on 2026-11-07). A trimmed copy (the paths and definitions below) is kept as a test fixture in `crates/sendmock-api/tests/fixtures/mailpit/`, with its source and licence (MIT) noted, and every answer is checked against it.

**What is served,** on the main HTTP port at Mailpit's paths:

| Mailpit endpoint | Answer | From |
|------------------|--------|------|
| `GET /api/v1/messages?start&limit` | `MessagesSummary`: `total`, `unread`, `messages_count`, `messages_unread`, `start`, `tags`, `messages` (each a `MessageSummary`), newest first | the email list |
| `GET /api/v1/search?query&start&limit` | the same, for messages matching a [Mailpit search](https://mailpit.axllent.org/docs/usage/search-filters/) | the email list with its `query` |
| `DELETE /api/v1/search?query` | `ok` | delete each match |
| `PUT /api/v1/messages` (`IDs`, `Read`, `Search`) | `ok`; no IDs and no search sets every message | mark read or unread |
| `DELETE /api/v1/messages` (`IDs`) | `ok`; no IDs deletes every message | delete |
| `GET /api/v1/message/{ID}` | `Message`: addresses as `{Name, Address}`, `Text`, `HTML`, `Attachments` and `Inline` with `PartID`, `Tags`, `Size`, `Date`; marks it read | the email detail |
| `GET /api/v1/message/{ID}/headers` | `{header: [values]}`, keys in alphabetical order | the raw source's headers |
| `GET /api/v1/message/{ID}/raw` | the source as `text/plain` | the raw source |
| `GET /api/v1/message/{ID}/part/{PartID}` | the part's bytes with its content type | the MIME part |
| `GET /api/v1/tags`, `PUT /api/v1/tags` (`IDs`, `Tags`) | the tag names; `ok` after replacing the messages' tags | the email tags |
| `GET /view/{ID}.html`, `GET /view/{ID}.txt` | the HTML or text part; 404 when the message has none | the email detail |

`{ID}` is SendMock's email ID; `latest` means the newest message, as in Mailpit. Mailpit's search words map to SendMock's own search, which reads the same `from:`, `to:`, `subject:`, `tag:`, `is:read`, `is:unread` and `has:attachment` filters; other filters are read as words. Errors answer as Mailpit does: 404 with a plain text body for a missing message, 400 with plain text for a bad request.

**Not served:** `GET /api/v1/info` and `POST /api/v1/send` are SendMock's own endpoints at the same paths, with their own shapes, and stay so (an app that sends through Mailpit's HTTP API is rare; one that reads through it is common). Mailpit's chaos, web UI configuration, HTML, link and spam checks, release, thumbnails and tag rename and delete are not emulated: SendMock has its own versions of most of them in its API. The docs page lists both.

**Where it lives** (the Adapter pattern, as for provider emulation): `crates/sendmock-ops/src/email/mailpit/` translates SendMock's email records to Mailpit's shapes (`MailpitMessageSummary`, `MailpitMessage`, `MailpitMessagesSummary`) and Mailpit's requests to SendMock's email operations, with no HTTP in it; `crates/sendmock-api/src/mailpit_routes.rs` is the thin router that reads the request and writes the answer. These are compatibility aliases, like the provider APIs, not new operations: they add no CLI command or MCP tool, since the native ones already do the same.

**Docs:** a guide page "Coming from Mailpit" under Mail: what keeps working unchanged (ports, the endpoints above, `X-Tags`), the two endpoints that differ, and what SendMock adds.

**Tests naming EM-19:** unit tests of the adapter's translations; API tests for every endpoint above, each answer checked against the fixture's definitions; an end-to-end test that sends mail over SMTP and reads it back through the Mailpit paths, as a Mailpit-based test suite does.

**As built (2026-11-07):** `crates/sendmock-ops/src/email/mailpit/` (`mailpit_shapes.rs`, `mailpit_mailbox.rs`) and `crates/sendmock-api/src/mailpit_routes.rs`, merged into the app router, so UI auth covers it like the native API. New store queries in `crates/sendmock-store/src/email/email_mailbox_queries.rs` (a page by offset, counts, every tag, read status for a search), and `compute_file_checksums` in `sendmock-core` for the attachments' `Checksums`. Deletes and per-message changes go through the native operations, so `email.deleted` and the UI follow. Two things found while building: the mail parser renders an HTML version of a text-only message for SendMock's preview, which Mailpit does not have, so the adapter reads the MIME tree and answers `HTML: ""` and a 404 view for those; and Mailpit's dates are Go's RFC 3339 without trailing zero fractions, which SendMock's format already matches. Tests: `mailpit_api.rs` (every endpoint, each answer checked against `fixtures/mailpit/mailpit-definitions.json`), `crates/sendmock/tests/mailpit_compatibility.rs` (SMTP to `search` and `message/latest` on a real binary), unit tests in `mailpit_shapes.rs`, and `scripts/mailpit-docs.test.ts` (the guide lists every path the router serves).

## A2. `email.clicked` link-click tracking (EM-20)

**Why:** apps test click tracking the way they test opens: "the user clicked the verify link, so stop the reminder", engagement scores, A/B links. Every email provider SendMock emulates reports clicks, and `email.opened` already exists ([05](05-webhooks.md#opened-events), EM-11); clicks were left for after 1.0 ([11](11-roadmap.md)).

**What the providers send** (checked against their docs on 2026-11-07): SendGrid `"event": "click"` with `url` (and `url_offset`); Mailgun `"event": "clicked"` with `url`; Postmark `"RecordType": "Click"` with `OriginalLink` and `ClickLocation` (`HTML` or `Text`); Resend `"type": "email.clicked"` with `data.click` `{ ipAddress, link, timestamp, userAgent }`; Amazon SES `"eventType": "Click"` with `click` `{ ipAddress, link, linkTags, timestamp, userAgent }`; Brevo `"event": "click"` with `link`; SparkPost `"type": "click"` with `target_link_url`. Each built-in template gains its click shape, and each provider's status names gain `clicked`, so a provider endpoint receives clicks exactly as the provider sends them.

**When it fires,** as opens do, but a click is always deliberate, so there is no setting to turn the UI's clicks off:

| Source | `source` | Behaviour |
|--------|----------|-----------|
| A link clicked in the email's HTML or text preview | `ui` | the link opens in a new tab as before, and the click is recorded |
| Simulate click in the email's actions (pick one of its links) | `manual` | always fires |
| `POST /api/v1/emails/{emailId}/clicks` with `url` (and optional `user_agent`) | `api` | always fires, for CI tests |

The URL must be one of the email's links (the `links` SendMock already extracts, EM-13), as a provider only tracks links it rewrote; another URL answers 422 `unknown_link` with the email's links in the message.

**Payload** (`email.clicked`): the email fields `email.opened` carries, plus `url`, `clicked_at`, `first_click` (the first click on that URL), `click_count` (all clicks on the email), `source` and `user_agent`. Each click is kept (`GET /api/v1/emails/{emailId}/clicks`, newest first), the email's detail gains `click_count`, and its timeline shows each click.

**Where it lives:** migration `email_clicks` (email, URL, time, source, user agent); `EmailClickRepository` beside the opens; `RecordEmailClickOperation` and `ListEmailClicksOperation` in `crates/sendmock-ops/src/email/` (so REST, CLI `sendmock email click <emailId> --url` and the MCP tool `sendmock_email_click` come from the registry); the event in the event catalogue and webhook rule filters on `url`, `first_click`, `click_count` and `source`. The UI first, against the mock (API change in [06](06-api.md), then types, the regenerated spec and the MSW handlers), then the binary.

**Split:** A2a the contract, mock and UI (the preview's click capture, Simulate click, the timeline entries, the Deeper entries); A2b the binary (store, operations, event, rule filters); A2c the provider templates and their fixture tests; A2d the docs (Opened and clicked events, the Mail guide, the skill).


**As built, A2a and A2b (2026-11-07):** one commit, since the generated spec and the binary's registry must agree in CI. UI and mock: `web/src/features/mail/detail/preview/use-preview-link-clicks.ts` listens for clicks in the preview (the listener belongs to the app page; the click's target comes from the preview's own realm, so it is checked with `closest`, not `instanceof Element`), `simulate-click-menu.tsx` adds Simulate > Click a link, and `web/src/mocks/clicks/` and `email-click-handlers.ts` answer the API. Binary: migration `0034_email_clicks.sql`, `email_click.rs` in the store, `email_click_operations.rs` in the operations (422 `unknown_link` lists the email's links), `email.clicked` in the event catalogue, the rule fields `url`, `first_click` and `click_count` in `sendmock-webhooks` and in the UI's rule builder, and `with_engagement_event_fields` reading a click's own fields as an open's. The wait-for-email answer now carries the same detail as `GET /emails/{emailId}`, click count included. Tests: `crates/sendmock-api/tests/email_clicks_api.rs`, `web/tests/e2e/email-clicks.spec.ts`, `web/src/mocks/clicks/record-mock-click.test.ts` and the rule message unit test. A2c (provider click shapes) and A2d (docs, CLI test, skill) follow.

**As built, A2c (2026-11-07):** the click shapes live in the template definitions (`web/src/mocks/fixtures/template-definitions.ts`, exported to `crates/sendmock-ops/builtin/` with the providers' `clicked` status names and `email.clicked` in each email template's events), plus `clicked` in both event name tables (`template_event_name_filters.rs` and the demo's `render-template-text.ts`). SES now sends a click as event publishing does (`eventType` with a `click` object) and SparkPost sends opens and clicks as `track_event`s. `crates/sendmock-api/tests/email_click_provider_formats.rs` delivers one click to all seven templates and reads each body at the paths `fixtures/provider_webhooks/click_events.json` records from the providers' docs. Building it found a bug in the demo's template renderer: an `if` nested in another `if`'s branch took the inner tag into its condition and left an `endif` behind; the condition now stops at the first `%}` (regression test in `render-template-conditions.test.ts`).

**As built, A2d (2026-11-07):** "Clicked events" in the Mail guide's reading page with the CLI, API and MCP rows, `email.clicked` in the webhooks event list and its fields in Rules and filters, `sendmock_email_click` named in the skill's webhook workflow (and the plugin's copy), and binary tests of `sendmock email click` and the MCP tool (`email_commands.rs`, `mcp_stdio.rs`). A list from an MCP tool comes back as the tool's text, since structured content must be an object.

## A3. More SMS providers (SM-17)

**Why:** apps that send SMS through Infobip, Telnyx, Sinch, Africa's Talking or Amazon SNS cannot point their SDK at SendMock yet. SendMock already has the webhook formats for the first four (`infobip.dlr`, `telnyx.message`, `sinch.sms`, `africastalking.sms`, checked against their docs on 2026-11-05) but not their send APIs; SNS has neither. Five SMS providers ship today (Twilio, Twilio Verify, Vonage, Plivo, MessageBird).

**How:** each provider is a new definition beside the built-in ones (SM-16, [22](22-configurable-providers.md)), so nothing in the existing providers changes: its send operation (method, path, request format), the field mapping to SendMock's message parts, the success answer and the error answers in the provider's own shape, the message ID it makes, its status names, and the callback template its delivery reports use. The definitions live in `web/src/mocks/fixtures/more-sms-provider-fixtures.ts` (the existing file is long) and are exported to `crates/sendmock-ops/builtin/` like the others. Every request and answer is read from the provider's API reference first, as a fixture with its link and the date checked; each provider also passes its official Node SDK against the provider port in the SMS clients workflow, as the Twilio SDKs do.

| Part | Provider | Send API | Delivery reports | Node SDK |
|------|----------|----------|------------------|----------|
| A3a | Infobip | `POST /sms/2/text/advanced` | `infobip.dlr` to `notifyUrl` | `@infobip-api/sdk` |
| A3b | Telnyx | `POST /v2/messages` | `telnyx.message` to `webhook_url` | `telnyx` |
| A3c | Sinch | `POST /xms/v1/{service_plan_id}/batches` | `sinch.sms` to `callback_url` | `@sinch/sdk-core` |
| A3d | Africa's Talking | `POST /version1/messaging` | `africastalking.sms` to the callback set on the account (the provider's settings) | `africastalking` |
| A3e | Amazon SNS | `Publish` with `PhoneNumber` (the query API: form body, XML answer) | none: SNS logs delivery status to CloudWatch, which SendMock does not emulate | `@aws-sdk/client-sns` |

The exact paths, fields and shapes above are checked against the API references when each part starts and corrected here if they differ. A part that finds the provider's API cannot be described by a definition (for example SNS's request signing or XML answers) says so in its As built note and adds the smallest engine change it needs, with its own test.


**As built, A3a Infobip (2026-11-07):** the definition is in `web/src/mocks/fixtures/more-sms-provider-fixtures.ts`. Infobip's Node SDK (`@infobip-api/sdk` 0.3.2, read from its source) posts to `/sms/2/text/advanced` with `Authorization: App <key>`, and accepts an `http://` base URL, so it points at the provider port unchanged. The answer is Infobip's `bulkId` and `messages[]` with the `PENDING_ACCEPTED` status; a refusal is its `requestError.serviceException`. Delivery reports use `infobip.dlr`, which turns SendMock's status names into Infobip's itself, so the provider's status names keep SendMock's (`delivered`, `failed`, `undelivered`) and only gate which statuses are reported (final ones). Tests: `crates/sendmock-api/tests/more_sms_providers_api.rs` and `examples/sms/node-infobip` in the SMS clients workflow.

**As built, A3b Telnyx (2026-11-07):** Telnyx's Node SDK (`telnyx` 7.30.0, read from its source) posts to `/messages` under `https://api.telnyx.com/v2` and takes a `baseURL`, so it reaches `/v2/messages` on the provider port. The answer is Telnyx's `data` message object with the recipient `queued`; a refusal is its `errors` list (`10004`, missing required parameter, 422). The `telnyx.message` template sent `message.received` for every event, which is wrong for an outbound status; it now sends `message.received` for inbound messages and `message.sent` then `message.finalized` for status updates, with Telnyx's status names (`sent`, `delivered`, `sending_failed`, `delivery_failed`) on the recipient. Webhook signing (Ed25519 with the account's key) is not emulated. Tests: `more_sms_providers_api.rs` and `examples/sms/node-telnyx`.

**As built, A3c Sinch (2026-11-07):** Sinch's Node SDK (`@sinch/sdk-core` 1.8.0) calls the SMS API with a Bearer token and no OAuth when it is given a service plan ID and an API token, at `/xms/v1/{service_plan_id}/batches`; `sms.setHostname` points it at the provider port. The answer is Sinch's `mt_text` batch, a refusal its `code` and `text`. `sinch.sms` already wrote inbound messages and recipient delivery reports, so the provider keeps SendMock's status names. Sinch sends reports only when the batch asks for them (`delivery_report`); SendMock sends them whenever a `callback_url` is given. Tests: `more_sms_providers_api.rs` and `examples/sms/node-sinch`.

**As built, A3d Africa's Talking (2026-11-07):** Africa's Talking's Node SDK (`africastalking` 0.8.4) posts a form to `/version1/messaging` with the `apikey` header and only accepts a 201; it has no base URL option, so the example adds a request interceptor to the SDK's own axios that sends its calls to the provider port. The answer is `SMSMessageData` with the recipient's `statusCode` 101, a refusal is plain text. Its delivery reports go to a callback set on the account, so the provider sends none itself; a webhook rule with `africastalking.sms` does. While writing the refusals, `error.reason` turned out to be empty for a failed required-field rule (it carries only a provider's own message), so each new provider's refusal now names its own field (Infobip `Message text is missing`, Telnyx `The 'text' parameter is required.`, Sinch `Field 'body' is required`, Africa's Talking `missing required form field 'message'`) and the tests check the text. Tests: `more_sms_providers_api.rs` and `examples/sms/node-africastalking`. The Advanced guide's walkthrough for adding an SMS provider used Africa's Talking as its example of a vendor SendMock does not ship; it now adds Clickatell (`POST /messages` on `platform.clickatell.com`, told apart from MessageBird's same path by its host). Termii was tried first and refused, since its real path starts with `/api/`, which is SendMock's own.

**As built, A3e Amazon SNS (2026-11-07):** the AWS SDK's SNS client (`@aws-sdk/client-sns` 3.1164.0) uses the Query protocol: a form posted to `/` with `Action=Publish`, answered in XML. A definition describes that (form request, `PublishResponse` and `ErrorResponse` bodies with `Content-Type: text/xml`); two engine changes were needed. SNS has no sender field, and the engine required one: a provider whose field mapping has no `from` and no messaging service now stores its messages from the provider's name (`send_operation_kind.rs`), while providers that map a sender still require it. And `/providers/<key>/` with nothing after it fell through to the web UI, since a catch-all route takes no empty path; `provider_routes.rs` now routes a provider's root. SNS logs delivery status to CloudWatch, so the provider has no callback. Tests: `more_sms_providers_api.rs` and `examples/sms/node-sns`; SM-17.6 is proven by `message-providers.spec.ts` (the five listed as built-in) and `sms-clients-workflow.test.ts` (the providers page names each send API).

**Also found while building A3:** the CI run of A3a failed SM-16.3 because the demo's live traffic toasts stack over the last provider row's buttons, now that the list is longer; that test hides the toaster. And `otp_answers_the_newest_code_per_recipient_and_channel` failed about 3 times in 10: two SMS stored in the same millisecond got random ULIDs, so "the newest" (and any list in id order) could swap them. `SystemIdGenerator` now uses the `ulid` crate's monotonic generator, with a test that 10,000 ids in a row strictly increase.

## A4. Vonage Verify v2 (VF-05)

**Why:** Twilio Verify is the only one-time-code API SendMock answers (VF-01 to VF-04). Vonage Verify v2 is the other common one; an app using it cannot run its login flow against SendMock today. Other providers' verify APIs (Sinch Verification, Infobip 2FA, Plivo Verify) follow as later parts once this one shows the pattern.

**What Vonage sends and answers,** read from the Vonage Node SDK's source and its test data (`@vonage/verify2` 1.22.1, 2026-11-07), which builds every URL from a configurable `apiHost`:

| Request | Answer |
|---------|--------|
| `POST /v2/verify` with `brand`, `workflow` (`[{channel: "sms", to}]`, also `email`, `whatsapp`, `voice`), optional `code_length`, `code`, `locale`, `channel_timeout`, `callback_url` | 202 `{ request_id }` |
| `POST /v2/verify/{request_id}` with `code` | 200 `{ request_id, status: "completed" }` (the SDK's `checkCode` returns this status); a wrong code 400 problem `Invalid Code` |
| `DELETE /v2/verify/{request_id}` | 204, the request cancelled |
| a finished, cancelled or unknown request | 404 problem `Not Found`, "Request <id> was not found or it has been verified already." |

Errors are problem details (`title`, `type`, `detail`, `instance`), as the SDK's data sets show.

**How:** like Twilio Verify, a stateful API stays in code as an adapter (`vonage_verify_api.rs` beside `twilio_verify_api.rs`, [22](22-configurable-providers.md)) over the same verify domain, so a Vonage verification is an ordinary SendMock verification: listed in Verify, its code delivered as an SMS (or email, or WhatsApp) into SendMock, readable by `GET /api/v1/otp`, and firing the same `verify.*` events. Vonage has no verify service the way Twilio does, only a `brand` per request, so SendMock keeps one verify service per brand, made on first use and named after it, with `code_length` (default 4) and the workflow's channel taken from the request. A wrong code counts toward the service's attempt limit; past it, the request ends and later checks answer 404, as Vonage's do. The provider is built in as `vonage_verify`, a sibling of the existing `vonage` SMS provider, and the Vonage Node SDK's `Verify2` client runs a login against it in the SMS clients workflow.

**Not in this part:** `next_workflow`, silent authentication and templates; the status `callback_url` events; Vonage's legacy Verify v1 (`/verify/json`).

**As built, A4 (2026-11-07):** `vonage_verify_api.rs` answers the three requests over the verify domain, tried after Twilio Verify in the provider runtime, and the `vonage_verify` definition lists it with Basic credentials (`api_key`, `api_secret`), which Verify v2 accepts beside the SDK's JWT; the JWT itself is not checked. Reading the SDK showed the check answers `completed`, not `complete` as first written here, so the table and VF-05.2 say `completed` (the SDK's `checkCode` returns that status, and an app compares against it). Vonage's phone numbers have no `+`; SendMock adds it, so the code SMS and the Verify list show E.164. The `request_id` is the verification's SID (`VE...`) rather than a UUID, so one id works in both APIs. The captured code SMS still carries `twilio_verify` as its API, since the verify domain sends it for either API. Tests: `vonage_verify_api.rs` (VF-05.1 to VF-05.3) and `examples/sms/node-vonage-verify` with `@vonage/verify2` 1.22.1 (VF-05.4), which generates an RSA key for the SDK's JWT, completes one login and cancels another.

## A5. Projects: multi-project inboxes (PL-10)

**Why:** a team often shares one SendMock (a dev server, a CI runner, a Docker host). Today every app's mail, SMS and codes land in one list, so each developer filters by recipient or subject and a test reading "the latest code" can read another app's. Separate instances work but need more ports and more configuration.

**How others do it** (read 2026-11-07): smtp4dev keeps several mailboxes in one server, chosen by rules on the recipient, with a default mailbox for the rest and a mailbox picker in its UI ([its configuration doc](https://github.com/rnwood/smtp4dev/blob/master/docs/Configuration.md)). Mailtrap's sandbox groups inboxes into projects, and each inbox has its own SMTP credentials, so the username picks the inbox ([its sandbox API](https://docs.mailtrap.io/developers/email-sandbox/sandboxes-inboxes)). Mailpit and MailHog have one mailbox. SendMock follows Mailtrap's credentials model, since apps already set an SMTP username, plus a header and a URL prefix for HTTP APIs, which have no username of their own.

**What a project is:** a name for captured traffic inside one instance. A project has a key (lowercase letters, digits and dashes, up to 40 characters) and a display name. `default` always exists and holds everything not sent to another project; it cannot be deleted.

| Belongs to a project | Shared by every project |
|---|---|
| emails (with their attachments, timeline, opens, clicks and responses), SMS messages and threads, verifications | providers, templates, webhook endpoints, rules and variables, numbers, outcome rules, payments, HTTP bins, settings |

Projects separate traffic; they do not secure it. Anyone who can open SendMock can pick any project or "All projects", as in smtp4dev. Access control stays what it is today ([PL-06](acceptance/04-catcher-platform.md#pl-06-security-defaults)).

**How traffic picks its project:**

| Way in | Picked by | Unknown key |
|---|---|---|
| SMTP | the AUTH username, when it is a project's key (any password under `accept-any`) | stored in `default`, as without AUTH; apps send all kinds of usernames, and refusing would break mail that works today |
| REST send APIs (`/api/v1/send`, `/api/v1/sms`, inbound) | the `X-SendMock-Project` header | 404 `project_not_found` |
| provider APIs (Twilio, Vonage, SendGrid and the rest, on the provider port or under `/providers/<key>`) | the `X-SendMock-Project` header, or the URL prefix `/projects/<project>/` before the provider's path, for SDKs that take a base URL but no extra header | 404 in the provider's own error shape when it has one for a missing resource, else SendMock's |

**How reading works:** every list and lookup of captured traffic (emails, SMS, threads, verifications, `GET /otp`, `/links`, the `/wait/*` helpers, `GET /events/recent` and the realtime stream) takes an optional `project` (query parameter, `--project` in the CLI, a `project` argument in MCP). Without it they read every project, as today, so a single-project instance sees no change. Events carry `project` in their data, so a webhook rule can filter on it.

**Managing projects:** Settings > Projects lists them with their key, their message counts and a "Connect" block (the SMTP username and the header or URL prefix to use), and creates, renames and deletes them. Deleting a project deletes its traffic. REST `GET/POST /api/v1/projects`, `PATCH/DELETE /api/v1/projects/{projectKey}`, CLI `sendmock projects list|create|update|delete`, MCP `sendmock_project_*`, all from operations in `sendmock-ops`. The seed file has a `[[projects]]` table, and reset keeps projects like other configuration.

**In the UI:** a project switcher in the top bar ("All projects", then each project) kept in the URL (`?project=`), which filters Mail, SMS and Verify and the live toasts. It shows only when a project other than `default` exists, so a single-project instance looks as it does today.

**Parts:** A5a the store, operations, REST, CLI and MCP, with SMTP and the header; A5b the provider URL prefix; A5c the UI (mock first, then live) and docs.

**As built, A5a and A5b (2026-11-07):** projects live in their own table (migration 0035), and emails, SMS and verifications gained a `project_key` column (`default` for everything stored before). The request's client and project travel together as `RequestScope` in the operation context; the REST router and the provider routes set it from `X-SendMock-Project` (allowed in CORS) or, on provider routes, from a leading `/projects/<key>/`, which is stripped before the provider sees the path, so `http://127.0.0.1:8026/projects/shop` (provider port) or `http://127.0.0.1:8025/providers/twilio/projects/shop` (main port) is a project's base URL. SMTP looks the AUTH username up with a cheap existence check and only then clones the context. An unknown project on a provider route answers SendMock's own `404 project_not_found`, not the provider's not-found shape the table above planned: the project is resolved before any provider is matched, and a provider's not-found means a missing resource of its own, which would mislead. `/projects/` joins `/api/` and `/providers/` as paths a provider definition may not use. Reads take `project` on emails (and the email delete filter), the latest email, SMS, conversations (which then count only the project's messages), verifications, OTP, links, the email and SMS waits and recent events; the live stream is not filtered on the server, and the UI filters its toasts by the event's `project`. Rule messages carry `project` (from the stored email or SMS, or from a verification event's data). Tests: `projects_api.rs`, `project_traffic_api.rs`, `project_reads_api.rs`, `project_provider_api.rs`, and the Telnyx Node SDK example sending under `/projects/shop/` (PL-10.4).

**As built, A5c (2026-11-07):** Settings > Projects lists the projects with their traffic counts, adds (key and name), renames and deletes them, and shows the three ways to send to one with copy buttons. The top bar picker appears once a second project exists; its choice is a root search parameter kept from screen to screen with TanStack Router's `retainSearchParams`, read by the email, SMS, conversation and verification list hooks, so every screen using them is scoped. The realtime provider sits outside the router and reads the choice from the URL when an event arrives; events about another project stay in the bell without a toast. Seed files carry `[[projects]]` (`key`, `name`; never `default`), applied by a seed adapter that adds or renames and, on a reset with a seed, removes the projects the seed does not list. Tests: `projects.spec.ts` (mock mode), `realtime-event-effects.test.ts`, `project_seed_api.rs`.

**Not in this part:** per-project settings, retention or webhook endpoints; per-project credentials that SendMock checks; routing by recipient rules (smtp4dev's model), which tag rules and inbound routes already cover for filtering.

## A6. POP3 read access (EM-21)

**Why:** some apps and test suites read a mailbox over POP3: an inbound-mail feature that polls a support address, a QA script built on Python's `poplib` or PHP's IMAP extension, a desktop mail client pointed at a test server. Today they cannot read what SendMock caught without changing to its API.

**How others do it** (Mailpit's `internal/pop3` source, read 2026-11-07): Mailpit's POP3 server is off until credentials are configured, since it hands out every message. It serves the newest 100 messages, with USER and PASS, STAT, LIST, UIDL (the message id), RETR, TOP, NOOP, DELE, RSET, QUIT and CAPA (RFC 1939 and 2449); DELE only marks, and the marked messages are deleted when the client sends QUIT, so a dropped connection deletes nothing. A line over RFC 1939's limit is refused, an idle session closes after 10 minutes, and five failed logins close the connection. TLS is implicit, with a certificate given on the command line.

**How:** a new `sendmock-pop3` crate with the protocol (a session state machine over a `Pop3Mailbox` trait, testable without a socket) and the listener, wired by the binary like the SMTP one; the mailbox is implemented in `sendmock-ops` over the email repository, so deletes go through the same path as the API and fire `email.deleted`.

- **Off by default:** `--pop3-addr` (`SENDMOCK_POP3_ADDR`) turns it on, bound to `127.0.0.1` unless told otherwise (Docker publishes it only when asked).
- **Login:** `--pop3-auth` takes `accept-any` (the default, as for SMTP on a local machine) or `file:<path>` with the same `user:password` lines as `--smtp-auth`.
- **Mailbox:** the username picks it, as SMTP's does: a project's key reads that project's emails ([A5](#a5-projects-multi-project-inboxes-pl-10)), any other username reads `default`. The newest 100 emails of that project, numbered oldest first as POP3 clients expect; the list is fixed at login, as RFC 1939 asks.
- **Messages:** RETR answers the stored raw message with dot-stuffing; TOP the headers and the first n body lines; UIDL the email id, which never changes, so clients that remember downloaded ids work across sessions.
- **Seen in the product:** `/api/v1/info` lists the POP3 address, Settings > Connection shows the host, port and how to log in, and the CLI's `serve --help` and the configuration docs describe the options.

**As built (2026-11-07):** A6a is the `sendmock-pop3` crate (`Pop3Session` over a `Pop3Mailbox` trait, tested with a fake, and the listener with a 512-byte line limit and a 10-minute idle timeout) and `sendmock-ops/src/pop3_mailbox.rs`; transport crates may not depend on each other, so the `user:password` file reader moved from `sendmock-smtp` to `sendmock-core` for both. A6b wires it into the binary: `--pop3-addr` and `--pop3-auth` (flags, environment and `sendmock.toml`), the listener started with the SMTP ones and stopped on shutdown, `pop3_addr` in the ready line, `pop3_address` in `/api/v1/info` (null when off; the types, the mock and the spec changed together), and a POP3 card in Settings > Connection, shown only while POP3 is on, so mock mode is unchanged. Tests: `pop3_session_tests.rs`, `pop3_listener.rs` (over a socket with SendMock's operations), `pop3_config.rs`, the live `pop3-connection.spec.ts` (the live suite now starts the binary with `--pop3-addr 127.0.0.1:0`), and `examples/smtp/python-poplib/verify.py` in the SMTP clients workflow, which turns POP3 on for the job.

**Not in this part:** STLS and implicit TLS (SendMock runs on the developer's machine or a private network; TLS follows if asked), APOP and SASL logins, IMAP.

## A7. Push notifications (PN-01)

**Why:** apps send push notifications through Firebase Cloud Messaging, Expo and OneSignal as often as they send email or SMS: sign-in codes, order updates, chat messages. Today the HTTP catcher captures those calls as raw requests (HC-03): nothing shows the notification as the phone would, and a test cannot wait for "the push to this device" or make a token fail the way an expired one does.

**How it works:** push becomes its own area beside Mail and SMS, with the same model: the app calls the provider's real API on the provider port (or under `/providers/<key>/`), SendMock stores the notification and answers exactly as the provider does, fires `push.sent`, and shows it in **Push**.

- **Providers, in code like Twilio Verify** (their answers depend on stored state and their requests are nested JSON): FCM HTTP v1 (`POST /v1/projects/{project_id}/messages:send`, answering `{ "name": "projects/<id>/messages/<id>" }`), Expo (`POST /--/api/v2/push/send`, one message or a list, answering tickets; `POST /--/api/v2/push/getReceipts`), OneSignal (`POST /notifications`). Each adapter is read from the provider's official SDK and its tests before it is written: `firebase-admin`, `expo-server-sdk`, `@onesignal/node-onesignal`. APNs needs HTTP/2 with TLS, which the provider port does not serve, and follows later.
- **What is stored:** the provider, the device token (or Expo push token, or OneSignal player or alias), the title, body, image, sound, badge and data, the platform the message targets when it says, the request as sent, the answer, and the project ([A5](#a5-projects-multi-project-inboxes-pl-10)) from the header or URL prefix.
- **Failures on purpose:** magic device tokens like SMS's magic numbers: a token containing `unregistered` answers each provider's "not registered" error (FCM `UNREGISTERED` 404, Expo `DeviceNotRegistered`, OneSignal `invalid_player_ids`), `invalid` its invalid-token error, and `throttled` its rate limit (FCM `QUOTA_EXCEEDED` 429).
- **Reading and waiting:** `GET /api/v1/push` (with `project`, `token`, `provider`), `GET /api/v1/push/{pushId}`, `DELETE`, and `GET /api/v1/wait/push`, with CLI and MCP commands from the same operations. `push.sent` and `push.failed` events reach webhook rules, which filter on `token`, `title` and `project`.
- **The Push screen:** a list of notifications and a detail with a phone-style preview (lock screen card for iOS and Android), the data payload, the request and the answer; filters by provider, token and status. Built on the mock first, as every screen is.

**Parts:** A7a the store, operations and FCM; A7b Expo and OneSignal; A7c the Push screen (mock, then live); A7d magic tokens, events and the SDK examples in CI.

**As built, A7a (2026-11-07):** a `push_notifications` table (migration 0036, pruned with the SMS count and cleared by reset and by deleting a project), `PushNotificationRepository`, and the `push` operations: list (`project`, `device_token`, `provider`, `status`), one, delete one, delete all and `GET /api/v1/wait/push`, with `sendmock push list|show|delete|clear|wait` and `sendmock_push_*` tools. The filter is `device_token`, not `token`, since `--token` is the CLI's global API token flag. FCM HTTP v1 is answered in code before the provider definitions (`push/fcm_send_api.rs`): the message name `projects/<id>/messages/0:<micros>%<hex>`, `validate_only` answered with `fake_message_id` and not stored, a message without a token, topic or condition refused with `INVALID_ARGUMENT` and an `FcmError` detail; topics and conditions are stored as `topic:<name>` and `condition:<expression>`. The title, body and image come from the cross-platform notification, then the Android, APNs and Web Push blocks, and the platform from which block the message carries. To free a line in `OperationContext::new` for the repository, the SMTP session and API request repositories became `logs: LogStores`. `firebase-admin` 14.5 hard-codes `https://fcm.googleapis.com` (HTTP/2 unless its legacy transport is on), so its CI example will redirect its requests to the provider port, as the PayPal example does (A7d). Tests: `push_fcm_api.rs` and the contract samples.

**Design, A7b (read from `expo-server-sdk` 8.0 and `@onesignal/node-onesignal` 5.20, 2026-11-07):**

- **Expo:** the SDK posts an array of messages to `${EXPO_BASE_URL}/--/api/v2/push/send` (`https://exp.host` by default, so `EXPO_BASE_URL=http://127.0.0.1:8026` points it at SendMock) and gzips any body over 1 KB with `Content-Encoding: gzip`, so the provider routes now inflate gzip request bodies (the one new dependency, `flate2` on its pure-Rust backend, also lets any other provider SDK compress). Each message's `to` is one token or a list; every recipient is a ticket, in order, and a stored notification. The answer is `{ "data": [tickets] }`, a ticket being `{ "status": "ok", "id": "<uuid>" }`; a single message object with one recipient is answered with one ticket object, as Expo does. A message without `to` refuses the whole request with `400 { "errors": [{ "code": "VALIDATION_ERROR", "message": ..., "isTransient": false }] }`, the shape the SDK turns into its error. `getReceipts` takes `{ "ids": [...] }` and answers `{ "data": { "<id>": { "status": "ok" } } }` for the ids SendMock issued (failed ones carry the ticket's error, A7d); unknown ids are left out, as Expo leaves out receipts it does not have. Title, body, `richContent.image` and `data` are read; `subtitle`, `sound`, `badge` and the rest stay in the stored request.
- **OneSignal:** the SDK posts the notification to `${baseServer}/notifications` (`https://api.onesignal.com`; `createConfiguration({ baseServer: new ServerConfiguration("http://127.0.0.1:8026", {}) })` points it at SendMock). The recipients are `include_subscription_ids`, `include_player_ids` (the older name) and `include_aliases` (each alias label with its ids, stored as `<label>:<id>`), each a stored notification sharing one notification id; a segment send (`included_segments`) is stored once as `segment:<names>`. The answer is `200 { "id": "<uuid>", "external_id": null }` (the request's `external_id` when it sent one). Title and body come from `headings` and `contents` (English first, else the first language), the image from `big_picture`, then `ios_attachments`, then `chrome_web_image`, the platform from `target_channel` or the `is_*` flags when only one is set. No recipients, or `contents` without a language when no `template_id` is given, answer `400 { "errors": ["..."] }` with OneSignal's messages.
- **Routes:** on the provider port at the real paths, or under `/providers/expo/` and `/providers/onesignal/` on the main port, with the project header or URL prefix as for every provider.

**As built, A7b (2026-11-07):** `push/expo_push_api.rs` and `push/onesignal_notifications_api.rs` beside the FCM adapter, chosen by `push_api.rs` (on the provider port each push provider is tried in turn; under `/providers/<key>/` only that one). Expo stores each recipient's message (not the whole batch) as its request and the ticket as its answer, so `getReceipts` reads the ticket back by its id. The provider routes inflate `Content-Encoding: gzip` bodies with `flate2` (pure Rust, refused past the 32 MB body limit), so the request log and every provider see the plain JSON. Tests: `push_expo_api.rs` (a gzipped batch included), `push_onesignal_api.rs` and the decoding unit tests in `sendmock-api`.

**Design, A7c (2026-11-07):** **Push** is a top-level sidebar item after SMS (`/push`, the guide at `push.md`), shown as Not available yet until the server serves `GET /api/v1/push` (UI-12). The screen follows Verify's: filter chips for the provider (All, FCM, Expo, OneSignal) and the status (Sent, Failed), a search on the device token (exact, as the API filters), a table (time, provider, device token, title, status) and a drawer kept in the URL (`?push=<id>`) with a phone preview (an iOS and an Android lock screen card with the app's title, body, image and time, chosen by the message's platform and switchable), the facts (provider, message id, token, project), the data payload as key and value rows, and the request and answer as JSON with copy buttons. Delete one from the drawer; Clear all under the filters asks first. The demo data gets a handful of FCM, Expo and OneSignal notifications (one failed) so the demo and the Deeper crawl show every part. The embedded UI is close to its 2 MB budget, so the screen reuses the Verify table, the sheet, the filter chips and `HttpBodyView` rather than adding components. The realtime refresh on `push.sent` comes with the events in A7d.

**As built, A7c (2026-11-07):** `web/src/features/push/` (page, list panel, table, drawer, phone preview, status badge, labels) over `use-push-queries.ts`; the sidebar item has the shortcut `g` then `u`, and the empty state's Connect hint gained a `push` area with the FCM, Expo and OneSignal base URLs. The demo data has four notifications (`push-fixtures.ts`). The guide page is `docs/wiki/push.md`, the Deeper page `website/lib/deeper/screens/push.ts`, and every screenshot was retaken since the sidebar changed. Tests: `push.spec.ts` (mock mode), `tests/live/push-screen.spec.ts` (an Expo push sent to the binary), the connect values unit test, and every-screen checks that now include `/push`.

**Design, A7d (read from `firebase-admin` 14.5's `messaging-errors-internal.js`, `expo-server-sdk` 8.0's types and `@onesignal/node-onesignal` 5.20's models, 2026-11-07):**

- **Magic device tokens:** a token (Expo push token, OneSignal subscription, player id or alias id) containing `unregistered`, `invalid` or `throttled`, in any case, fails the way that provider fails. The notification is still stored, as `failed` with the provider's error code as its reason and the error as its answer, so a test can assert on what the app was told.

  | Token has | FCM (whole request) | Expo (that recipient's ticket, request 200) | OneSignal |
  |---|---|---|---|
  | `unregistered` | `404 NOT_FOUND`, `FcmError` `UNREGISTERED` (the SDK's `messaging/registration-token-not-registered`) | `DeviceNotRegistered`, "`<token>` is not a registered push notification recipient" | listed under `errors.invalid_player_ids` (subscriptions, player ids) or `errors.invalid_aliases.<label>` (aliases), request 200 |
  | `invalid` | `400 INVALID_ARGUMENT`, `FcmError` `INVALID_ARGUMENT` (`messaging/invalid-argument`) | `DeviceNotRegistered`, "`<token>` is not a valid Expo push token" | as `unregistered` |
  | `throttled` | `429 RESOURCE_EXHAUSTED`, `FcmError` `QUOTA_EXCEEDED` (`messaging/message-rate-exceeded`) | `MessageRateExceeded` | the whole request `429 { "errors": ["API rate limit exceeded"] }` |

  A OneSignal send whose every recipient is refused answers `200 { "id": "", "errors": ["All included players are not subscribed"] }`, as OneSignal does. A failed Expo ticket has no id, so it has no receipt.
- **Events:** storing a notification publishes `push.sent`, or `push.failed` for a refused one, with the notification's `id`, `provider`, `device_token`, `title`, `status`, `error_reason` and `project`. Webhook rules listen to both (Push in the rule editor's events) and filter on the new fields `token`, `title` and `provider`, plus `body`, `status` and `project`, read from the stored notification. The Push screen refreshes on either event; neither raises a toast.
- **SDK examples in CI:** `examples/push/` has a Node app per provider run by the "Push SDKs" workflow against a release binary: `firebase-admin` (`messaging().send()` over HTTP/1.1, its `fcm.googleapis.com` requests sent to the provider port by wrapping Node's `https.request`, as the PayPal example wraps its client, and a credential that answers a fixed access token), `expo-server-sdk` (`EXPO_BASE_URL`, a batch large enough to be gzipped, then `getPushNotificationReceiptsAsync`) and `@onesignal/node-onesignal` (`baseServer`). Each sends a notification, waits for it with `GET /api/v1/wait/push`, sends to an `unregistered` token and checks the SDK reports the provider's error.

**As built, A7d (2026-11-08):** `push/magic_push_tokens.rs` reads the failure a token asks for; each adapter answers it in its own shape (FCM in `refuse_magic_token`, Expo per ticket in `issue_ticket`, OneSignal in `answer_recipients`) and stores the notification as failed with the provider's code (`UNREGISTERED`, `DeviceNotRegistered`, `invalid_player_ids`, ...) as its reason. `store_push_notification` publishes `push.sent` or `push.failed`; the rule subscriber reads a push event's stored notification (`build_push_rule_message`), and `token`, `title` and `provider` joined the filter fields (Rust `KNOWN_FIELDS`, the web rule builder's Push subject). The Push screen refreshes on both events. `examples/push/node/done-when.js` runs the three SDKs in the new "Push SDKs" workflow and from Release build; it passed locally against a debug build with Node 22 first. Tests: `push_failures_and_events.rs`, `magic_push_tokens.rs`'s unit test, `scripts/push-sdks-workflow.test.ts`, the rule fields and realtime unit tests.

**Not in this part:** APNs, Web Push (VAPID), topics and condition sends (FCM topics are stored as the target, with no fan-out), delivery receipts beyond Expo's `getReceipts`.

## A8. WhatsApp Business Cloud API (SM-18)

**Why:** most apps that send WhatsApp today call Meta's Cloud API directly (`graph.facebook.com`), not Twilio. SendMock answers WhatsApp only through Twilio's Messages API with `whatsapp:` addresses (SM-11), so those apps cannot point at SendMock: their sends, templates, media and the webhooks Meta sends back have nowhere to go.

**What Meta sends and answers,** read from Meta's Node SDK (`whatsapp` 0.0.5-Alpha, archived by Meta, its types and webhook handler) and the Cloud API reference, 2026-11-08:

| Request | Answer |
|---------|--------|
| `POST /{version}/{phone_number_id}/messages` with `messaging_product: "whatsapp"`, `to`, `type` and the type's object (`text`, `template`, `image`, `audio`, `video`, `document`, `sticker`, `location`, `contacts`, `interactive`, `reaction`) | 200 `{ messaging_product, contacts: [{ input, wa_id }], messages: [{ id: "wamid...." }] }`; a template send adds `message_status: "accepted"` |
| the same path with `{ messaging_product, status: "read", message_id }` | 200 `{ success: true }` |
| a request Meta refuses | Graph's error: `{ error: { message: "(#100) ...", type: "OAuthException", code, error_data: { messaging_product, details }, fbtrace_id } }` |
| `POST /{version}/{phone_number_id}/media` (multipart `file`, `type`, `messaging_product`) | `{ id }` |
| `GET /{version}/{media_id}` | `{ messaging_product, url, mime_type, sha256, file_size, id }`; `GET` on the `url` answers the bytes; `DELETE` answers `{ success: true }` |

Meta's webhooks go to the one callback URL of the app, as `{ object: "whatsapp_business_account", entry: [{ id, changes: [{ field: "messages", value: { messaging_product, metadata: { display_phone_number, phone_number_id }, contacts, messages | statuses } }] }] }`, signed with `X-Hub-Signature-256: sha256=<hex HMAC-SHA256 of the body with the app secret>`. Statuses are `sent`, `delivered`, `read` and `failed`, a failed one with `errors: [{ code, title, message, error_data: { details } }]`. Before Meta sends anything, it checks the URL with `GET ?hub.mode=subscribe&hub.verify_token=...&hub.challenge=...`, which the app answers with the challenge.

**How:** a stateful, nested-JSON API stays in code as an adapter, like Twilio and Vonage Verify ([22](22-configurable-providers.md)): `whatsapp_cloud_api.rs` beside them, listed by a built-in `whatsapp_cloud` provider definition (host `graph.facebook.com`) that holds its credentials: `access_token` (not checked, like the other providers' keys), `app_secret` (signs the webhooks), `phone_number` (the business number the messages are stored from, default `+15550783881`), `verify_token`, and `webhook_url` (Meta's callback URL). A Cloud API message is an ordinary SendMock message on the `whatsapp` channel with the API `whatsapp_cloud`, so it shows in SMS with WhatsApp styling, fires `sms.sent`, counts for OTP and links, and follows the delivery profile and the magic numbers (an `undelivered` or `failed` outcome becomes Meta's `failed` status with `131026`, "Message undeliverable"). The `phone_number_id` of the path is kept on the message.

- **Bodies:** each message type is stored with a readable body so the conversation needs no new UI: `text.body`; a template as `Template <name> (<language>)` and its body parameters on the next line; media as its caption (or `Photo`, `Video`, `Audio`, `Document <filename>`, `Sticker`) with the file attached; a location as its name, address and `<latitude>, <longitude>`; contacts as each name and phone; interactive as the body text and each button or list row title on its own line; a reaction as `Reacted <emoji>`. The request as sent is stored too.
- **Refusals:** `messaging_product` other than `whatsapp` (`(#100) Param messaging_product must be 'whatsapp'`), no `to`, an unknown `type`, or a type without its object or its required field (`(#100) The parameter text['body'] is required.`) answer 400 with Graph's error and store nothing; a template, media or reply id SendMock does not have is accepted, as Meta checks those later.
- **Webhooks:** with `webhook_url` set, each status of a Cloud API message (through the status callback queue, so it is retried and listed on the message) and each reply in a Cloud API conversation (through the reply webhook, in the new `whatsapp_cloud` format) is posted there in Meta's envelope, signed with `app_secret`. `POST /api/v1/sms/providers/whatsapp_cloud/verify-webhook` sends Meta's subscribe check to the URL and answers whether it echoed the challenge, and Settings for the provider shows it as **Verify callback URL**.
- **Read receipts:** marking an inbound message read (`status: "read"`) sets it read, as opening it in the UI does.

**Parts:** A8a the send API, read receipts, Graph errors and the definition, with an example in CI; A8b media upload, lookup, download and delete, and sends by media id; A8c the webhooks (statuses, replies, signature, the verification check) and the docs.

**Not in this part:** template management (`/message_templates`), the 24-hour customer service window (`131047`), business profile and phone number management, flows, catalogues and payments, and the on-premises API. Meta's Node SDK is archived and only speaks HTTPS to a fixed host, so the CI example calls the API with `fetch`, as most apps do.

**As built, A8a (2026-11-08):** `whatsapp_cloud_api.rs` (routing, credentials, sends), `whatsapp_cloud_content.rs` (each message type read into a body and its media), `whatsapp_graph_errors.rs` and `whatsapp_read_receipts.rs` in `sendmock-ops/src/providers/`, tried after Vonage Verify in the provider runtime; the definition is `web/src/mocks/fixtures/whatsapp-cloud-provider-fixture.ts`, exported with the others. Messages are stored from `whatsapp:<phone_number>` to `whatsapp:+<to>` with the path's `phone_number_id` in the message's metadata and the `wamid.` as its provider id. A number the outcome rules refuse answers `400` with code `131026` at once, as Meta does for a recipient it cannot reach, rather than a later `failed` status; a media link that cannot be downloaded answers `131053`. A read receipt finds the message by its `wamid` and marks its whole conversation read, as Meta marks earlier messages read too. Tests: `whatsapp_cloud_api.rs` (SM-18.1, SM-18.2), the content unit tests, `message-providers.spec.ts` (SM-18.5) and `examples/sms/node-whatsapp-cloud` in the SMS clients workflow, which passed locally against a debug build first.

**As built, A8b (2026-11-08):** uploads live in a `whatsapp_media` table (migration 0037, pruned with the SMS limit, cleared by reset and by deleting a project), reached as `sms_repository.whatsapp_media()` so the operation context gains no field. `whatsapp_cloud_paths.rs` tells the messages, upload and media object paths apart; `whatsapp_cloud_media.rs` answers them and `whatsapp_cloud_send.rs` now holds the send, attaching media named by id (unknown ids are skipped, as planned). Provider answers are text, so the download link (`/whatsapp_business/attachments/?mid=<id>`, on the address the app called) is answered by `find_whatsapp_media_download` in the provider route before the provider runtime and is not written to the request log. Media ids are 16-digit numbers like Meta's. Tests: `whatsapp_cloud_media_api.rs` (SM-18.3) and the example's upload, send by id and download.

**As built, A8c (2026-11-08):** the `whatsapp.cloud` template (`web/src/mocks/fixtures/whatsapp-template-definitions.ts`, exported with the others) renders a reply or a status in Meta's envelope with `X-Hub-Signature-256` from `whatsapp_signature(secret)`, a new body signer. Provider callbacks and reply webhooks now render their headers with `SignedBodyFunctions`, as endpoint deliveries did, so any body signature works there; that type also lists its signers itself, since a provider callback's own functions did not name them. Cloud API sends take the provider's `webhook_url` as their status callback, and a reply to the provider's business number goes there as the number's own reply webhook (the `number` target, so the reply webhook's contract is unchanged), when no virtual number claims it. The callback URL check is `POST /api/v1/sms/whatsapp-cloud/verify-webhook` (`sendmock sms whatsapp-cloud verify-webhook`, `sendmock_sms_whatsapp_verify_webhook`) with a **Verify callback URL** button on the provider's Callbacks tab; without an HTTP client it reports the missing client rather than failing. The provider gained the `phone_number_id`, `business_account_id`, `webhook_url` and `verify_token` credentials. Inbound replies keep SendMock's `SM` ids rather than `wamid.` ones. Tests: `whatsapp_cloud_webhooks_api.rs` (SM-18.4) and the example's webhook handler, which verifies both signatures with `crypto.createHmac`.

## A9. System tray app (DS-08)

**Why:** most developers run SendMock on their own machine for the whole working day. Today that means a terminal window kept open, or a service set up by hand, and nothing says mail arrived until the browser tab is looked at.

**How others do it** (read 2026-11-08): Ollama's menu bar and tray app starts its server in the background, shows that it runs and offers "View logs" and "Quit"; Docker Desktop's whale menu shows the engine's state, opens the dashboard and quits. Mailpit, MailHog and smtp4dev have no tray app (smtp4dev's old Windows tray was dropped). In Rust, the Tauri team's `tray-icon` (0.26, MIT or Apache-2.0, with `muda` menus and `tao`'s event loop) is the common choice: the macOS menu bar, the Windows notification area, and on Linux an AppIndicator over GTK 3.

**How:** a new crate and binary, `sendmock-tray`, so `sendmock` itself gains no GUI dependency and keeps its size and Docker image. The crate has two halves:

- **A library with no GUI** (tested on every OS like the rest): `TrayController` decides what the menu shows and does, over a `SendmockConnection` trait (health and `GET /api/v1/stats` with a few lines of HTTP/1.1 to the local address, no HTTP client crate) and a `ServerProcess` trait (start `sendmock serve` as a child, stop it). Tests use fakes for both.
- **The tray shell** behind a `gui` feature (the binary has `required-features = ["gui"]`), so workspace builds, clippy and `cargo publish --dry-run` need no GTK. A "Tray app" workflow builds and tests it with the feature on Linux (with `libgtk-3-dev`, `libxdo-dev` and `libayatana-appindicator3-dev`), macOS and Windows.

**Behaviour:**

- On start it looks for SendMock at `--url` (`SENDMOCK_URL`, default `http://127.0.0.1:8025`). If one answers, it uses it; if not, it starts `sendmock serve` (the `sendmock` beside the tray binary, else on `PATH`, else `--sendmock <path>`).
- The menu: the status ("Running at http://127.0.0.1:8025", "Starting...", "Not running"), the unread counts ("3 unread emails, 1 unread SMS", from the stats the Overview uses), **Open SendMock** (the web UI in the default browser), **Start SendMock** or **Stop SendMock** (stop only for a server the tray started; one it found keeps running), and **Quit**, which stops the server it started. The tooltip repeats the status, and on macOS the menu bar shows the unread total next to the icon.
- It polls every 2 seconds. The icon is drawn in code (an envelope in SendMock's mint), so no image decoder is needed.

**Install:** `cargo install sendmock-tray --features gui` (the crate is published with the others), with the GTK and AppIndicator libraries on Linux; the docs give each OS's steps.

**Not in this part:** a native notification per message, starting at login, signed installers and a macOS `.app` bundle (they need the owner's signing identities, so they follow the release runbook), and Linux packages.

**As built, A9 (2026-11-08):** `crates/sendmock-tray`: the library (`TrayController`, `LocalHttpConnection` reading `GET /api/v1/stats` over plain HTTP/1.1, `ChildServerProcess` running `sendmock serve --http-addr <the URL's address>`, `TrayOptions`, the icon drawn in `tray_icon_image.rs`, and `open_in_browser` with `open`, `cmd /C start` or `xdg-open`) and the shell (`main.rs`, `tray_menu.rs`) on `tray-icon` 0.26 and `tao` 0.37, with the macOS app set to an accessory so it has no Dock icon. The crate sits in the application layer of `scripts/rust-crate-layers.ts` and, like `sendmock`, is not a workspace dependency. A server the tray starts keeps running if the tray is killed rather than quit, as Ollama's does. Before CI, the GUI binary was built on macOS and started against a free port: it found no server, started `sendmock serve` beside itself, and the API answered. Tests: the library's unit tests (DS-08.1 to DS-08.3, with fake connections and processes, a one-request local server and a missing binary), the "Tray app" workflow (DS-08.4) and `scripts/tray-app-workflow.test.ts` (DS-08.4, DS-08.5).

## A12. Monitoring: Prometheus metrics, OpenTelemetry and log files (PL-11, PL-12, PL-13)

**Why (owner request, 2026-11-08):** SendMock that a team runs in Docker, Kubernetes or CI is a service like any other, and the people running it want it on the dashboards and log searches they already have. Today it has a health check (`sendmock health`, `GET /api/v1/health`, the Docker HEALTHCHECK and the Helm probes), JSON logs on stdout (`SENDMOCK_LOG_FORMAT=json`) and the Overview's counts (`GET /api/v1/stats`), but nothing a monitoring system collects by itself.

**How others do it** (read 2026-11-08):

- **Mailpit** ([Prometheus metrics](https://mailpit.axllent.org/docs/configuration/prometheus/)): `--enable-prometheus` (`MP_ENABLE_PROMETHEUS`), off by default; `true` serves `/metrics` on the web UI port behind the UI's TLS and login, an address runs a separate server without either. Eleven metrics: stored and unread messages (gauges), messages deleted and SMTP messages accepted, rejected, ignored and their bytes (counters), database size, uptime and memory (gauges), and messages per tag.
- **Prometheus** ([writing exporters](https://prometheus.io/docs/instrumenting/writing_exporters/), [OpenMetrics](https://github.com/prometheus/OpenMetrics/blob/main/specification/OpenMetrics.md)): one prefix per application, the unit in the name (`_bytes`, `_seconds`), counters end in `_total` and only rise, the `process_` prefix is for process facts with their standard meaning, and labels never hold unbounded values.
- **OpenTelemetry** ([environment variables](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/)): the vendor-neutral standard for logs, metrics and traces. Every collector and most vendors (Grafana Alloy, the OpenTelemetry Collector, Datadog, New Relic, Honeycomb, Elastic, SigNoz, Dynatrace) accept OTLP, and a program is pointed at one with the standard variables `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_SERVICE_NAME`, so nothing SendMock-specific is needed.
- **Logs** ([twelve-factor](https://12factor.net/logs)): a service writes one event per line to stdout and lets the platform collect it (Docker's logging drivers, the Kubernetes node agent, the systemd journal, Fluent Bit, Vector, Loki's agents). That already holds for SendMock; native installs without such a platform want a log file that rotates.

**The three parts:**

**A12a Prometheus metrics (PL-11).**

- **On and off:** `--metrics` (`SENDMOCK_METRICS`, `metrics = true` in `sendmock.toml`), off by default as in Mailpit, so a public port does not answer a path scanners look for. When on, `GET /metrics` on the HTTP port answers the Prometheus text format (`text/plain; version=0.0.4`), behind the same `--ui-auth` or `--api-token` as the API (Prometheus scrapes with `basic_auth` or `authorization`). A separate metrics listener is not in this part.
- **One operation, every surface:** `getMetrics` (`GET /api/v1/metrics`, `sendmock metrics`, the MCP `sendmock_stats` tool with `view: metrics`) answers the metric families as JSON and is always available, as the Overview's stats are; `/metrics` renders that same answer as text in the transport layer (a `PrometheusTextRenderer`), so the numbers cannot differ. The text format is written by hand: it is a few lines per family, and no client library is needed.
- **Gauges, what is stored now** (read with the Overview's count queries on read connections, never the writer queue): `sendmock_emails`, `sendmock_emails_unread`, `sendmock_sms`, `sendmock_sms_unread`, `sendmock_verifications_pending`, `sendmock_http_requests`, `sendmock_push_notifications`, `sendmock_payments`, `sendmock_webhook_deliveries_queued` (waiting for a retry) and `sendmock_database_size_bytes`. They fall after a delete, a reset or retention pruning.
- **Counters, since the process started:** `sendmock_events_total{type="email.received"}`, one series per event type, counted inside `EventBus::publish` (exact; a subscriber can fall behind and miss events), and `sendmock_smtp_rejected_total`, counted where the SMTP session log already records a refused message.
- **Process:** `sendmock_build_info{version}` (always 1), `process_start_time_seconds`, and on Linux `process_resident_memory_bytes` from `/proc/self/statm` (left out on macOS and Windows rather than adding a dependency).
- **Safety:** labels hold only event type names and the version: never an address, a number, a project name a user typed, message content or a secret.
- **UI:** Settings > Connection shows a Metrics card while metrics is on, with the scrape URL and a copyable `prometheus.yml` job (with its `basic_auth` or `authorization` lines when auth is set); `/api/v1/info` gets `metrics_path` (null when off), as POP3 did.
- **Deployments:** the Helm chart's `metrics.enabled` sets `SENDMOCK_METRICS` and adds the `prometheus.io/scrape`, `port` and `path` pod annotations, and `metrics.serviceMonitor.enabled` renders a ServiceMonitor for the Prometheus Operator. `examples/monitoring/` holds a Docker Compose file with SendMock and Prometheus, and a CI job sends an email and finds `sendmock_events_total{type="email.received"}` at 1 through Prometheus's query API.

**A12b OpenTelemetry export (PL-12).**

- **On and off:** off until `OTEL_EXPORTER_OTLP_ENDPOINT` (or a per-signal endpoint) is set, as every OpenTelemetry SDK does; `OTEL_SDK_DISABLED=true` turns it off again. The standard variables are read as the specification says (`OTEL_SERVICE_NAME`, default `sendmock`; `OTEL_RESOURCE_ATTRIBUTES`; `OTEL_EXPORTER_OTLP_HEADERS` for a vendor's API key, masked wherever SendMock shows its settings). OTLP over HTTP with protobuf (`http/protobuf`), the specification's default, through the `reqwest` client SendMock already has; gRPC is not offered, since it would add `tonic` and its stack for no extra reach (every collector takes HTTP).
- **Logs:** every log line goes to the collector as an OpenTelemetry log record with its level, target and fields, through the `tracing` bridge, as well as to stdout.
- **Metrics:** the same families as `/metrics` (A12a), sent every 60 seconds (`OTEL_METRIC_EXPORT_INTERVAL`), so a team on OpenTelemetry needs no Prometheus.
- **Traces:** one span per SMTP session, REST and provider API request, webhook delivery attempt, status callback and outgoing release, with the operation id and outcome as attributes (never message content, addresses or secrets); an incoming `traceparent` header continues the caller's trace, so a test can follow its request into SendMock. Sampling follows `OTEL_TRACES_SAMPLER` (default: always on, since SendMock's traffic is test traffic).
- **Cost:** the crates (`opentelemetry`, `opentelemetry_sdk`, `opentelemetry-otlp` without default features, `opentelemetry-appender-tracing`, `tracing-opentelemetry`) are measured before merging against the 20 MB binary and idle memory budgets of [09](09-distribution.md#performance-budget-checked-in-ci-on-linux-x64); if they do not fit, OpenTelemetry becomes a cargo feature built into the Docker image and an `-otel` binary only, and the plan records the numbers either way. Nothing runs, and no memory is taken, while it is off.
- **Proof:** a CI job runs the OpenTelemetry Collector with its file exporter next to SendMock, sends an email and an SMS and a webhook, and finds the log records, the metric points and the spans (with a caller's `traceparent` kept) in the collector's output.

**A12c Log files and readiness (PL-13).**

- **Log files:** `--log-file <path>` (`SENDMOCK_LOG_FILE`, `log_file` in `sendmock.toml`) also writes the logs to a file in the chosen format, rotated daily or at `--log-file-max-size` (default 10 MB), keeping `--log-file-keep` files (default 7), for native installs without a log collector; the tray app starts its server with a log file in its data folder, since it has no terminal to show stdout. Stdout stays as it is.
- **JSON log fields:** `SENDMOCK_LOG_FORMAT=json` lines keep their shape and add `trace_id` and `span_id` when a span is active (A12b), so a log search can jump to the trace. The fields are listed in the docs, so a Loki, Elastic or Datadog pipeline can be written against them.
- **Readiness:** `GET /api/v1/health/ready` (and `sendmock health --ready`) answers 200 once the listeners are bound and the database answers a read, and 503 while starting and once shutdown has begun, so a load balancer or Kubernetes stops sending traffic before SendMock stops. `GET /api/v1/health` stays the liveness check. The Helm chart's readiness probe moves to the new path; the Docker HEALTHCHECK stays on liveness.
- **Docs:** a new Monitoring page in the guide covers the health and readiness checks, logs (stdout, JSON fields, the log file, and collecting them with Docker's logging drivers, the systemd journal, Fluent Bit, Vector and Grafana Alloy), every Prometheus metric with its type and meaning, the Prometheus and OpenTelemetry setups for Docker Compose and Helm, and a starter Grafana dashboard (`examples/monitoring/grafana-dashboard.json`). The configuration reference and the skill list every option.

**Order:** A12a, then A12c (small and independent), then A12b (the largest, and it reuses A12a's families and A12c's log fields).

**Not in this part:** a separate metrics listener, StatsD and Graphite (the OpenTelemetry Collector translates OTLP to both), OTLP over gRPC, histograms of SMTP and API latency (traces carry durations; added if asked), per-project metric labels, and alerting rules (left to each team; the docs give two examples).

## A13. Accounts, login and roles: Admin, Developer, Viewer (PL-14, PL-15)

**Why (owner request, 2026-11-08, for later):** a team that shares one SendMock (in Docker, on Kubernetes, or a CI box everyone can open) today has one shared login: `--ui-auth` (one or more `user:password` lines, all equal) and one `--api-token`. Everyone can change everything, from the relay allowlist to retention, and nobody can tell who did what. Teams want each person to sign in as themselves, and to give QA or a product owner a read-only seat.

**How others do it** (read 2026-11-08):

- **Grafana** ([roles and permissions](https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/access-control/), [service accounts](https://grafana.com/docs/grafana/latest/administration/service-accounts/)): every user has one basic role (Admin, Editor or Viewer); machines use service accounts that carry a role, and their tokens inherit it, so a token keeps working when the person who made it leaves.
- **Mailtrap** ([user management](https://help.mailtrap.io/article/65-user-management)): account Owner, Admin and Viewer, where a Viewer sees every project and inbox but cannot add, edit or remove anything; inbox-level Admin and Viewer roles on top.
- **Mailpit, MailHog, smtp4dev:** one shared HTTP basic auth login, no users or roles. SendMock is the same today.
- **OWASP** ([password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)): Argon2id with at least 19 MiB of memory, 2 iterations and 1 lane; session ids in `HttpOnly`, `Secure` (over HTTPS) and `SameSite` cookies, renewed at sign-in, with an idle and an absolute timeout.
- **Jenkins** (first start): the first admin is created with a one-time setup code printed in the server's log, so whoever reaches an open port first cannot take the instance.

**A13a Accounts and login (PL-14).**

- **Off by default:** a developer's own SendMock stays open with no login, as today. `--auth accounts` (`SENDMOCK_AUTH`, `auth = "accounts"` in `sendmock.toml`) turns accounts on; `--ui-auth` keeps working unchanged as the simple shared login, and the two cannot be set together.
- **The first admin:** given by `SENDMOCK_ADMIN_USERNAME` and `SENDMOCK_ADMIN_PASSWORD` (or `_FILE` variants for Docker and Kubernetes secrets) on an instance with no users; otherwise the first visit shows a setup page that asks for the one-time setup code SendMock prints in its log at start, as Jenkins does. `sendmock users reset-password <username>` run on the host against the data file (with the server stopped) recovers a lost admin password.
- **Users:** username, display name, role and password, kept in SQLite. Passwords are hashed with Argon2id at OWASP's parameters, at least 12 characters, and never leave the server, not even as hashes in seed exports (the seed file lists users and roles; their passwords are set again on import).
- **Sign in and sessions:** a sign-in page in the web UI; a random session id in a `HttpOnly`, `SameSite=Lax` cookie (`Secure` behind HTTPS), renewed at sign-in, ending after 12 hours idle or 7 days at most (`--session-idle-timeout`, `--session-max-age`), and on sign-out or a password or role change. Failed sign-ins are slowed per username and address (five a minute, then a growing wait), and the answer never says whether the username exists. Requests that change something from the browser must carry the UI's own header and a same-origin `Origin`, against cross-site requests.
- **Tokens:** each user can make personal access tokens that act as them; an Admin can make service tokens that carry a role and belong to no one, for CI and agents (as Grafana's service accounts). A token is shown once, stored as a SHA-256 hash, has an optional expiry and a last-used time, and is revoked on its own. `--api-token` keeps working as a service token with the Admin role.
- **Every surface:** the REST API, the WebSocket stream and MCP over HTTP take the session cookie or `Authorization: Bearer <token>`; the CLI uses `SENDMOCK_TOKEN`, and `sendmock login` stores a token for a server in the user's config folder. Provider APIs keep checking the provider's own credentials and SMTP its own AUTH, since apps under test cannot sign in to SendMock.
- **Audit log:** sign-ins, failed sign-ins, user, role and token changes, and every destructive operation are recorded with the user or token, time and address, shown in a new Audit tab on the Logs screen (Admins only) and kept under the retention limits.
- **Managing users:** Settings > Users and tokens for Admins; Settings > Account for everyone (display name, password, personal tokens, sign out everywhere). The same through REST, `sendmock users ...` and `sendmock tokens ...`, and MCP.

**A13b Roles: Admin, Developer, Viewer (PL-15).**

| Role | Can |
|---|---|
| **Viewer** | Read everything: emails, SMS, verifications, push, payments, HTTP requests, webhook deliveries, logs, stats and settings (secrets stay masked, as for everyone). Change nothing; opening an email or SMS does not mark it read for a Viewer, since read state is shared. |
| **Developer** | Everything a test run needs: send and simulate messages and payments, delete and clear traffic, reset traffic, release email within the configured allowlist, and create, edit and delete webhook endpoints, rules, templates, variables, HTTP bins, scenarios, providers, virtual numbers and projects. |
| **Admin** | Everything a Developer can, plus the instance: users, roles and tokens, the audit log, retention, the relay and release servers and their allowlist, SMTP chaos and auth settings, the update check, seed import and a full reset that also clears configuration. |

- **One rule in one place:** every operation in the `sendmock-ops` registry declares the role it needs. The default comes from the existing flags (a read-only operation needs Viewer, anything else Developer), and Admin operations say so explicitly. The check runs in the operations layer before the handler, so REST, the CLI, MCP and the WebSocket enforce exactly the same thing; the transport edge maps it to 403, a CLI exit code or an MCP error naming the role needed. A registry snapshot test lists every operation with its role, so a new operation is a deliberate choice that shows up in review.
- **UI:** controls the role cannot use are shown disabled with "Needs the Developer role" (or Admin), rather than hidden, so people know the feature exists and whom to ask; the top bar shows who is signed in and their role.
- **MCP:** an agent's tool list only holds the tools its token's role may call, so it does not try the rest.
- **Changing a role** takes effect on the user's next request; the last Admin cannot be removed or demoted.

**Order:** A13a, then A13b; A13a alone treats every user as an Admin, so it is usable before roles land.

**Not in this part:** single sign-on (OpenID Connect, then SAML) and LDAP, two-factor sign-in, roles per project (a Developer on one project and a Viewer on another, as Mailtrap's inbox roles), custom roles, and email invitations (an Admin sets the first password and shares it).

## A14. Real forwarding: provider connections and routing rules for email and SMS (PL-16, PL-17)

**Why (owner request, 2026-11-08, for later):** SendMock catches everything, which is what tests need, but some messages should still reach a real person: the staging app's password reset to the developer's own inbox, every OTP SMS to the tester's phone, a client's newsletter preview to their real Outlook. Email has part of this today: **Release** (one email, by hand) and **auto-forward rules** (Settings > Email), both through one SMTP relay and only to allowed recipients. SMS has nothing, and neither can pick the provider a message goes out through.

**How others do it** (read 2026-11-08):

- **Mailpit** ([SMTP relaying](https://mailpit.axllent.org/docs/configuration/smtp-relay/)): one relay. Manual release is limited by `allowed-recipients`; `--smtp-relay-all` relays every message to its original recipients, `--smtp-relay-matching` only recipients matching a regular expression; `blocked-recipients` applies everywhere, including automatic relaying, and silently drops those recipients.
- **Mailtrap** ([automatic forwarding](https://docs.mailtrap.io/email-sandbox/management/automatic-email-forwarding)): per sandbox, forward to addresses whose owners confirmed they want the mail, or to a whole domain verified by a DNS TXT record; it matches To and Cc, ignores Bcc, and sends from its own `forward.mailtrap.info` address.
- **The providers themselves** (Twilio, Vonage, SendGrid, Mailgun, Amazon SES, Postmark, Resend): each has its own send API, credentials, error codes and rate limits; Twilio and others offer test credentials and magic numbers that never send.

**A14a Real provider connections (PL-16).**

- **Connections:** named, reusable connections to real services, managed in Settings > Connections: for email SMTP (the existing relay becomes the first connection, named `relay`, and its settings keep working), SendGrid, Mailgun, Amazon SES, Postmark and Resend; for SMS Twilio, Vonage, Plivo, Telnyx, Infobip and Amazon SNS. Each provider is a sending adapter (`TwilioSendClient`, `SendGridSendClient`, ...) registered in a real-provider registry beside the emulation adapters, so a new provider is a new type and existing ones are not touched; each translates SendMock's stored message to that provider's request and its answer and errors back.
- **Who may receive:** every connection has its own allowed recipients (addresses and `*@domain` patterns for email, numbers and `+44*` prefixes for SMS) and blocked recipients, which win everywhere, as in Mailpit. A real send to anyone outside the allowed list is refused before any request leaves. A connection with an empty allowed list sends nothing.
- **Secrets:** API keys, tokens and passwords are stored on the server, masked in the UI, API answers, logs and MCP results, and written to seed exports only as an environment reference such as `${TWILIO_AUTH_TOKEN}`, never in plain text.
- **Check before use:** **Test connection** checks the credentials with the provider without sending where its API allows that, and **Send a test** sends one message to an allowed recipient. A connection shows its last success and last error.
- **One switch for everything real:** `--real-delivery off` (`SENDMOCK_REAL_DELIVERY`) stops every real send from connections, release and rules, whatever is configured, for CI and shared demos; the UI shows a banner while it is off.
- **By hand:** **Send for real** on any email or SMS (Release, extended to SMS and to every connection) picks a connection and recipients from its allowed list; the message's timeline records it.

**A14b Forwarding rules for email and SMS (PL-17).**

- **Rules:** the existing email auto-forward rules gain the connection they send through and become one rule list with SMS (Settings > Forwarding, with Email and SMS tabs). A rule has a name, an order, on or off, and a filter built with the webhook rules' filter operators (equals, contains, matches, in): project, direction (outgoing or inbound), from, to, subject or body, the provider API the message came in through, tags and headers for email, and the extracted OTP's presence.
- **Where it goes:** **to the original recipients** (only those on the connection's allowed list; the rest are dropped and noted, as Mailpit does), or **redirect to** fixed recipients, such as "every SMS to +8801XXXXXXXXX" or "every email for `*@client.com` to qa@ourcompany.com". Options: a subject or text prefix (`[SendMock]`), a From address or sender ID the provider accepts, and whether to keep the original Message-ID.
- **First match or all:** rules run in order; **stop at this rule** ends the list for a matching message, otherwise every matching rule sends.
- **Limits, against floods and bills:** each rule has a per-minute and per-day cap (defaults 30 and 500), and each connection a per-day cap; past a cap the forward is skipped and recorded, not queued. **Dry run** on a rule shows which of the last 100 messages it would have forwarded, and to whom, without sending.
- **Reliability:** each forward is an attempt with its status, the provider's message id and its error, retried on network errors and the provider's rate-limit or server errors with the webhook retry policy, never on a refused recipient or bad credentials. Attempts show in the message's timeline and in a Forwards tab on the Logs screen, and fire `email.forwarded`, `sms.forwarded` and `forward.failed` events for webhooks and the event stream.
- **No loops:** a forwarded email carries `X-SendMock-Forwarded` and is never forwarded again if it comes back, and a rule cannot send to SendMock's own SMTP address or provider APIs.
- **Every surface:** connections and rules through REST, `sendmock connections ...` and `sendmock forward-rules ...` (the existing `sendmock email forward-rules` commands stay as aliases), MCP and the seed file. With roles ([A13](#a13-accounts-login-and-roles-admin-developer-viewer-pl-14-pl-15)), connections and rules are the Admin's, and Send for real is the Developer's within the allowed lists.
- **Proof without real sends:** CI runs a second SendMock as the "real" provider and forwards to it through each adapter (SendMock emulates every one of these provider APIs), so every adapter is tested against the provider's wire format; an optional workflow, run only when the owner sets the secrets, sends through Twilio's test credentials and a sandbox email account.

**Order:** A14a (connections, starting with SMTP, SendGrid and Twilio, plus Send for real), then A14b (rules), then the remaining providers one by one.

**Not in this part:** receiving real inbound messages from providers (a real Twilio number posting to SendMock is the inbound routes' job), WhatsApp and push to real devices, recipient confirmation by email as Mailtrap does (allowed lists are set by whoever manages the instance), and per-project connections.

**Not in this part:** analytics in the SendMock app itself (the web UI on users' machines never phones home), heatmaps and session recordings, and A/B tests.

## A17. List actions on every traffic screen: select, mark read or unread, delete, delete all (UI-14)

**Release:** ships in **1.1.0**, the next stable minor, with the fix for bug #278 (owner decision, 2026-11-16; see [16](16-website-and-releases.md#roadmap-placement)).

**Why (owner request, 2026-11-16):** Mail's list has a toolbar: a checkbox on each row and a select-all checkbox, Mark read and Delete for the checked emails, and Delete all (or Delete matching while a filter is on). No other screen has it. SMS's conversation list has only its search and channel chips, so a conversation cannot be marked unread, several cannot be deleted at once, and the only way to empty SMS is Settings > General. The HTTP Catcher can only clear one bin, Push only clear everything, and Verify, webhook deliveries, Payments and the Logs cannot be emptied at all, short of Reset to seed, which also throws away the configuration. The owner asked for the same actions on every service.

**How others do it:** mail clients and catchers (Gmail, Mailpit, Mailtrap) put the same toolbar above every list: a select-all checkbox, then actions that apply to the checked rows (mark read, mark unread, delete), and Delete all; webhook.site has Delete all requests on each URL. The toolbar looks and works the same on every list.

**One toolbar for every list:** a shared compound component in `components/common` (`ListActionToolbar`, with a row checkbox for the list items) that Mail moves onto and every other list uses, so the actions look, sit and behave the same everywhere:

- **Select:** a checkbox on each row (shown on hover and while anything is checked, always on touch screens) and a select-all checkbox for the loaded rows, which reads "3 selected" and turns indeterminate when only some are checked. `x` ticks the open item on the Mail and SMS lists (beside their `j`, `k`, `Enter` and `d` keys) and the focused row on the table screens, and the shortcut help lists it.
- **Act on the selection:** **Mark read** and **Mark unread** (on lists with read state) and **Delete**, shown while something is checked; deleting asks first with the count. The selection clears after an action and when the filter changes.
- **Delete all:** always in the toolbar, disabled while the list is empty; while a filter is on it reads **Delete matching** and deletes only what the filter shows, as Mail does today. One confirmation names what goes, how many and what stays; confirming deletes at once.

**Per screen:**

| Screen | Read state | Delete one | Delete all |
|---|---|---|---|
| Mail | exists; adds bulk **Mark unread** | exists | exists |
| SMS (conversations) | `unread_count` exists (opening marks read); new mark read or unread per conversation | new: a conversation with its messages | exists (`DELETE /sms`), moved from Settings onto the list |
| SMS > Verify > Verifications | none | new | new |
| Push | new, as Mail's | exists | exists (Clear all becomes the toolbar's Delete all) |
| HTTP Catcher (a bin, or All requests) | new, as Mail's | new | exists per bin (`DELETE /http/requests`); also on All requests |
| Webhooks > Deliveries | none | new (finished deliveries only) | new |
| Payments, Subscriptions | none | new | new |
| Logs > SMTP, Logs > HTTP | none | new | new |
| Settings > General | | | also **Delete all traffic**: every list above at once, configuration kept |

Read state follows Mail's: new items arrive unread, opening one marks it read, and the sidebar shows an unread count for SMS, Push and the HTTP Catcher as it does for Mail. Lists without read state (records of what happened, not an inbox) get Select, Delete and Delete all only.

**API (contract first in [06](06-api.md), then the registry and types, the regenerated spec and the mock):** `PATCH /sms/threads/{threadId}` (`is_read`) and `DELETE /sms/threads/{threadId}`; `is_read` on push notifications and captured HTTP requests with `PATCH /push/{pushId}` and `PATCH /http/requests/{requestId}`; `DELETE` for one verification, HTTP request, webhook delivery, payment, subscription, SMTP session and API request log entry; `DELETE /verify`, `/webhooks/deliveries`, `/payments`, `/payments/subscriptions`, `/logs/smtp` and `/logs/http` for all, taking the list's filters as `DELETE /emails` does; `project` on `DELETE /emails` and `DELETE /sms` (`DELETE /push` has it); and `DELETE /traffic` for Delete all traffic. The UI runs the per-item operation for each checked row, as Mail does.

**How it behaves:**

- **Scoped like the list:** with a project picked, Mail, SMS, Verify and Push act only on that project's traffic; "All projects" acts on every project.
- **Children go with their parent:** an email's attachments, timeline, opens and clicks; an SMS's media, status history and callback attempts; a verification's attempts; a payment's events, refunds and checkout session; a captured request's files.
- **Configuration stays:** providers, bins and their rules, webhook endpoints, rules, templates, variables and saved deliveries, Verify services, numbers, gateways, methods and flows, projects and settings. Only Reset to seed touches them.
- **Work in flight is kept:** webhook deliveries that are queued or waiting for a retry cannot be deleted (cancel them first); Delete all keeps them and its confirmation says how many stay.
- **Every tab updates:** a delete all publishes one `traffic.cleared` event (`{ "kinds": ["sms"], "project": "shop", "deleted_count": 128 }`, `project` null for all) instead of one event per row, and read changes refresh the unread counts, so every open tab drops the deleted rows and updates its badges without a reload. Like `traffic.pruned` (PL-08.5), webhook rules cannot pick `traffic.cleared`.
- **Every surface:** each action is one `sendmock-ops` operation served by REST, the CLI (deletes of everything need `--yes`, as `sendmock email delete-all --yes`) and MCP (deletes annotated destructive), named after each area's existing commands and tools (for example `sendmock verify delete-all --yes` and `sendmock_verify_delete_all`), recorded in the surface catalogue, and described on each screen's guide page.

**Order:** the contract and the mock handlers, then the shared toolbar with Mail moved onto it, then the other screens one by one (SMS first), then the operations, REST, CLI and MCP, then the guide pages.

**Not in this part:** undo after a delete (export the seed first), deleting on a schedule (retention, PL-08, does that), selecting across pages beyond the loaded rows (Delete matching covers that), and these actions on configuration lists.

## A18. Share and move a setup: versioned export and import (PL-18)

**Why (owner request, 2026-11-16):** someone who has built a setup (endpoints, rules, templates, numbers, providers, payments, settings) wants to export it and give it to a teammate, or import it on their other machine and carry on, without rebuilding anything by hand. A file written by one SendMock version has to work in another, or say clearly why not.

**What exists:** the seed file (`sendmock.seed.toml`, [02](02-architecture.md#configuration-and-seed-file)) with `sendmock seed export|apply|validate|status`, Settings > Seed and the `share-your-setup` recipe. Its gaps for this job: the file carries no version, so a file from a newer SendMock fails on an unknown key with no hint and a file from an older one cannot be upgraded when a section changes; it is TOML only; it is read from a path, never a URL; secrets come out only as `${ENV_VAR}` references, so moving to your own machine means setting every variable again; and apply always merges, with no preview of what it adds, changes or removes.

**How others do it** (read 2026-11-16):

- **Mockoon** ([CLI](https://www.npmjs.com/package/@mockoon/cli), [import and export](https://mockoon.com/docs/latest/import-export-data/)): the data file is migrated automatically when it comes from an older version, on a copy, never the user's file; a file from a newer version asks for a newer CLI; `--data` takes a path or a URL; migration is one-way.
- **Grafana** ([dashboard JSON model](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/view-dashboard-json-model/)): an integer `schemaVersion`, raised whenever the shape changes, and migrations from each version to the next; a file older than the oldest supported migration gets a "minimum version" error instead of a half-imported dashboard.
- **WireMock** ([import and export](https://docs.wiremock.io/import-export/wiremock)): export is a GET of every stub as JSON, import a POST of the same document, so the round trip is lossless.

**The design:**

- **One format, stamped with its version.** The setup file is the seed file with a header table; nothing else changes, so every existing seed file still works:

  ```toml
  [sendmock]
  format = "sendmock.setup"
  format_version = 2              # an integer, raised only when the shape changes
  exported_by = "1.4.0"           # the SendMock that wrote it
  exported_at = "2026-11-16T10:00:00Z"
  ```

  A file without the header is read as `format_version = 1`, today's seed. `format_version` is not the SendMock version: it changes only when a section or key changes shape, and only in a minor or major release, never a patch. The docs' Versions page keeps a table of each format version and the SendMock release that introduced it.
- **The version rules on import** (one place, `SetupVersionPolicy`, used by the UI, REST, CLI, MCP and `--setup`):
  - The same format version: applied as it is.
  - Older: upgraded in memory, one step at a time, by a registry of migrations (`SetupMigration` from 1 to 2, from 2 to 3, ...), each with fixture files of the older shape kept in the tests. The user's file is never rewritten; the import summary says "upgraded from format 1 to 3", and `sendmock setup migrate <file>` writes the upgraded copy for committing.
  - Older than the oldest migration this build keeps: refused, naming the last SendMock release that reads it. Every release reads every format version written since 1.0.
  - Newer than this build understands: refused before anything is applied, with "This setup was exported by SendMock 1.6.0 (format 4); this is 1.4.0 (format 2). Update SendMock to import it.", the update command for the way it was installed (from `GET /info`), and nothing half-applied.
  - A newer `exported_by` with the same format version is fine and only noted. An unknown section or key in a known format version is an error with its line number, as `seed validate` does today.
- **What a setup holds:** all configuration, the seed's sections plus every Settings section, projects, providers, HTTP Catcher bins and their mock responses, tag, forward and inbound routing rules, and saved scenarios (AI-07, below). Never traffic (emails, SMS, deliveries, payments, logs) or the server's own runtime options (`sendmock.toml`: ports, database path, auth), which belong to each machine. `--only` and `--except` take section names (see "Surfaces in practice" for why there is no `--project`).
- **Formats:** TOML (the default, as today), JSON and YAML, chosen by the file extension or `--format`, with one structure, so a file converts losslessly between them. A JSON Schema per format version is generated from the types and published on the website (`/schema/setup/v2.json`) and submitted to SchemaStore, so editors and AI agents validate a file as it is written. YAML reuses `serde_yaml_ng`, already a workspace dependency.
- **Secrets:** exported as `${ENV_VAR}` references by default, as today, so a shared file holds none. For moving to your own machine, `--include-secrets` asks for a passphrase and writes each secret encrypted (AES-256-GCM, key from PBKDF2-HMAC-SHA256 with a random salt, both from `ring`, already a dependency), as text starting `encrypted:v1:` (see "Secrets in practice" below); import asks for the passphrase (the UI field, a CLI prompt or `SENDMOCK_SETUP_PASSPHRASE`). A secret is never written in plain text, in line with the safe defaults.
- **Import from a file or a URL:** a path, an upload, pasted text or an `https://` URL (a raw file in a repository, a gist, an internal server). The fetch is capped at 1 MB and 10 seconds, follows at most 3 redirects and only to `https`, takes an optional `--sha256` that must match, and sends optional headers for a private URL (`--header "Authorization: Bearer ..."`, masked wherever it is shown or logged). Plain `http` is allowed only for loopback and private addresses, for a file served inside the CI network.
- **Preview, then merge or replace:** validation lists, per section, what would be added, changed and removed. **Merge** (the default, today's `seed apply`) upserts by name and keeps everything else; **Replace** also removes the configuration the file does not have, after a confirmation that names how many items go. Nothing is applied unless the whole file validates.
- **Every surface:** Settings > Seed becomes Settings > Setup (Export, Import, Validate, the status card), with Export offering the format, project, sections and the secrets choice, and Import a file, a paste or a URL with the preview. REST: `POST /setup/export`, `POST /setup/import`, `POST /setup/validate` and `POST /setup/migrate`, with `/seed/*` kept as aliases. CLI: `sendmock setup export|import|validate|migrate`, with `sendmock seed ...` kept as aliases. MCP: `sendmock_setup_export`, `sendmock_setup_import` (destructive), `sendmock_setup_validate`, `sendmock_setup_migrate`. The API change starts in [06](06-api.md), then the registry and types, then the regenerated spec.
- **Docs:** the `share-your-setup` recipe gains "Move to another machine" and "Import from a URL", the configuration reference documents the header and every section, and the Versions page lists the format versions.

**Proof:** a round trip on every surface (export, import into a fresh instance, export again: the two files are equal); a fixture file for every older format version, upgraded and applied; a file from a newer format refused with nothing applied; encrypted secrets that import with the passphrase and fail cleanly without it; URL import against a local test server (size cap, timeout, redirect rules, `--sha256`, headers masked); and a CI job that exports with the previous stable release and imports with the current build.

**Not in this part:** syncing setups between running instances, hosting shared setups on a SendMock service, a diff view between two files beyond the import preview, and exporting traffic.

**Formats in practice (step 3, 2026-11-20):** every format is read into the one structure the section adapters read (a TOML table) and written from it, so the checks, migrations and adapters are shared. JSON and YAML keep their key order; a `null` value is left out, as a missing key means the same; a TOML date is written as text in JSON and YAML, which SendMock reads as text anyway. Pasted text with no file name is detected: JSON starts with `{`, TOML is tried next, and YAML is chosen only when the text is not TOML and reads as a YAML mapping. Problems in a TOML file name their line, as today; JSON and YAML parsers keep no positions for values, so their syntax errors name the line and every other problem names its key path (`webhook.endpoints[0].secret`). The surfaces show the line when there is one and the key path otherwise (the answer gains `location` in step 6). `serde_yaml_ng` was only a test dependency; it becomes a dependency of `sendmock-ops` for YAML (the binary size budget in CI covers it). The JSON Schema is generated from each section adapter's item type (`schemars`; webhook templates and scenarios, read without one, describe their shape by hand), committed as `website/public/schema/setup/v2.json` and checked against the build by a test (`SENDMOCK_UPDATE_SCHEMA=1` rewrites it); a schema file is frozen once its format version is superseded. Format 1 has no schema: it predates the header that names a version, and every export is format 2 or later.

**Secrets in practice (step 4, 2026-11-20):** an encrypted secret is one string, `encrypted:v1:<salt>:<nonce, ciphertext and tag>` (both parts URL-safe base64), written exactly where the `${ENV_VAR}` reference would be. The plan first said `{ encrypted = "..." }`; a string was chosen instead because provider and payment gateway credentials sit inside the definition JSON that a setup holds as text, where a table cannot go, and because every secret field stays a string in the JSON Schema. `v1` fixes the scheme: AES-256-GCM, a key from PBKDF2-HMAC-SHA256 with 600,000 iterations (OWASP's figure) and a 16-byte random salt, and a random 12-byte nonce per secret; a later scheme gets a new prefix and `v1` keeps opening. Each secret carries its salt, so an item copied into another file still opens; one export uses one salt, so the key is derived once per file. An export refuses a passphrase shorter than 8 characters. On import, `${ENV_VAR}` references are resolved first and the secrets opened after, so a `${` inside a secret stays as written; a secret inside definition JSON goes in JSON-escaped. A missing passphrase answers `setup_passphrase_required` and a wrong one `setup_passphrase_wrong` (the GCM tag fails), both before anything is applied. The seed state keeps the file with each encrypted secret emptied, never the plain text, so reset can apply it again without the passphrase: an empty secret keeps the stored one, as an unset `${ENV_VAR}` does today. `seed validate` accepts an encrypted secret wherever a reference is required and names a damaged one; it does not need the passphrase. The export's secret handling is a Strategy (`SetupSecretWriter`: `SecretReferenceWriter`, the default, and `EncryptedSecretWriter`) passed to the four section adapters that hold secrets (webhook endpoints, webhook variables, SMS and email providers, payment gateways); the surfaces (`--include-secrets`, the passphrase field and `POST /setup/export`) come with step 6.

**URL import in practice (step 5, 2026-11-20):** `download_setup` in `sendmock-ops` takes a `SetupUrlSource` (the URL, an optional `sha256`, `SetupRequestHeader`s) and fetches through the `SetupFetcher` trait with `SetupFetchLimits` (1 MB, 10 seconds, 3 redirects); the binary provides `HttpSetupFetcher` over reqwest, as it does for media links. The rules: `https://` always; plain `http://` only when every address the host resolves to is loopback (`127.0.0.0/8`, `::1`) or private (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`), and the client is pinned to those checked addresses so a second lookup cannot point it elsewhere; link-local addresses (`169.254/16`, `fe80::/10`) are refused, as cloud metadata services answer there. A redirect is followed only to `https://` and at most 3 times. The cap holds whatever the server says: a larger `Content-Length` is refused before reading, and the body stops being read once it passes 1 MB. `sha256` takes 64 hex digits in either case, with or without `sha256:`, and a mismatch names both digests and applies nothing. A header's value never appears in a log, an error or debug output (`Authorization: ••••`), and the URL is logged without its user, password and query, which may carry a token. The format comes from the URL's file name after redirects, then the `Content-Type`, and otherwise is detected from the text. Errors: `setup_url_not_allowed` (scheme, address or redirect rules), `setup_download_refused` (too large, not UTF-8), `setup_download_failed` (unknown host, timeout, an unsuccessful status, unreachable), `setup_checksum_mismatch`, and `setup_download_unavailable` where no downloader is set. An `https://` URL may point at any address: the server binds `127.0.0.1` by default, and the import is the user's own request. The surfaces (`url`, `sha256` and `headers` on `POST /setup/import`, the CLI flags, the UI's URL field, and a URL for `--seed` at startup) come with step 6.

**Surfaces in practice (step 6, 2026-11-20):** four operations in `sendmock-ops` (`crates/sendmock-ops/src/setup/setup_export_operations.rs` and `setup_import_operations.rs`), served on REST, CLI and MCP from the registry; the seed operations stay as they are, as the aliases. Decisions made while building:

- **Export is one POST.** `POST /setup/export` takes `format`, `only`, `except`, `include_secrets` and `passphrase`. A GET with a query and a second POST for the passphrase would have been two operations and so two CLI commands; one POST keeps `sendmock setup export` and keeps the passphrase out of URLs. `GET /seed/export` stays for a plain TOML download.
- **No `--project`.** Projects separate captured traffic only ([A5](#a5-projects-multi-project-inboxes-pl-10)); no configuration item belongs to one, and a setup never holds traffic, so the option would only pick one row of `[[projects]]`. `only` and `except` take a section (`webhook.endpoints`) or a group (`webhook`); an unknown name is refused with the list of sections.
- **The passphrase on the CLI** comes from `--passphrase` or, when the flag is not given, `SENDMOCK_SETUP_PASSPHRASE` (a new `cli_environment_inputs` on the operation definition; clap's `env`, its value hidden in `--help`). There is no interactive prompt: reading a passphrase without echo needs a new dependency, which A24's launcher may bring later. An export encrypts only with `--include-secrets`, so a passphrase set in the environment for imports never encrypts an export by surprise.
- **`<file>` is optional** for `setup import` and `setup validate`, so `--url` can stand in for it (`is_optional` on `CliArgument`).
- **Import is destructive** (`--yes` on the CLI, `destructiveHint` in MCP), as the definition's flag cannot depend on the mode; `sendmock seed apply` stays the non-destructive merge.
- **The preview** compares each file item with an export of the stored one: items are matched by their section's key fields (a new `key_fields` on each `SeedSection`, such as `name`, `key`, `number`, `sid`, or `endpoint` and `name` for variables), the file item is read into the section's type and written back so defaults it leaves out are filled in (`normalize_item`; the settings and the sections read without a type compare as written), and `${ENV_VAR}` references and encrypted secrets compare as equal, since their values are not in the file. Settings are changed when applying the file's over the stored ones (merge) or over the defaults (replace) gives something else.
- **Replace** puts the settings the file leaves out back to their defaults and removes every item the file does not hold, the way reset restores the seed (reset now runs the same Replace path). It needs `confirm_removed_count` only when it removes something; a count that does not match answers `setup_replace_unconfirmed` and applies nothing. The import answers the validation it ran before applying, so the caller sees what changed.
- **Validate** takes the same request as import: text or URL, and the passphrase, which it tries on the secrets when given, so the UI's preview can say a passphrase is wrong before the import.
- **Read-only actions:** the reference builder treats `POST /setup/export` and `/setup/migrate` as read-only, as the server does (`readOnlyActionPattern`).
- **Saved scenarios on the contract:** the AI-07 operations from step 2 get their registry entries, types, catalogue rows, mock handlers and contract samples here, so the spec and the server agree before the screen comes in step 7.

**Screens, docs and CI in practice (step 7, 2026-11-20):**

### Saved scenarios (AI-07)

**The design:**

(`sendmock scenario run <file>` stays for files: the generated CLI reads a `<file>` argument as a file, so a saved scenario has its own command.) **MCP:** `sendmock_scenario_list`, `sendmock_scenario_get`, `sendmock_scenario_save`, `sendmock_scenario_update`, `sendmock_scenario_delete`, and `sendmock_scenario_run` takes `scenario_id` as well as `scenario_toml`.
- **UI:** the Scenarios screen gets a saved list beside the editor: **Save** (and **Save as**), open one into the editor, rename, delete with a confirmation, and an "Unsaved changes" mark while the editor differs from the saved file; **Run** runs what is in the editor, as today.
- **In a setup:** `[[scenarios]]` with `name`, `description` and the scenario file's own keys (`[[scenarios.steps]]` with `run`, `with` and `save`), so a scenario reads the same in a setup as in its own file and converts between TOML, JSON and YAML; import matches by name.

## A19. SendMock in CI/CD pipelines for webhook tests (WH-15)

**Why (owner request, 2026-11-16):** teams want to test their webhooks in CI/CD: that their app accepts and verifies the webhooks a provider sends, and that the webhooks their app sends arrive with the right body and signature. The pipeline should get SendMock's whole setup from one JSON or YAML file at a URL, and any AI agent should be able to add SendMock to a pipeline without a person working out the steps.

**What exists:** the Docker image as a CI service container ([09](09-distribution.md#docker)), `--ready-json` with free ports, the Testcontainers modules, the seed file, the wait helpers, the HTTP Catcher, and scenarios ([14](14-ai-integration.md#scenarios), AI-04: `sendmock scenario run` stops at the first failed `assert` with exit code `5`). Missing: a setup read from a URL (a service container starts before the repository is checked out, so it cannot be given a file), one command that runs a whole webhook test and reports it in the form CI systems show, webhook-specific checks, and ready-made pipeline snippets.

**How others do it** (read 2026-11-16): Mockoon's CLI starts a mock from a data file at a URL (`mockoon-cli start --data https://...`) and is run in GitHub Actions; WireMock runs as a service container and is loaded through its import API; Postman's Newman runs a collection from a URL and writes JUnit reports, which every CI system displays.

**The design:**

- **The setup from a URL:** `sendmock serve --setup <path|url>` and `SENDMOCK_SETUP` (with `SENDMOCK_SETUP_SHA256` and `SENDMOCK_SETUP_HEADERS`) load an A18 setup file, in TOML, JSON or YAML, at startup, with A18's version rules and fetch limits; the server only reports ready (`--ready-json`, `/health/ready`, PL-13) once the setup is applied, and a setup that fails to load or validate stops startup with the reason. So a service container needs one environment variable:

  ```yaml
  services:
    sendmock:
      image: ghcr.io/shibbirweb/sendmock:1
      ports: ["8025:8025", "1025:1025"]
      env:
        SENDMOCK_DB: memory
        SENDMOCK_SETUP: https://raw.githubusercontent.com/acme/shop/main/sendmock.setup.yml
  ```
- **A CI run file and one command:** `sendmock ci run <path|url>` reads a CI file (JSON or YAML, `format = "sendmock.ci"`, versioned like A18) that names the setup, the app's base URL and the scenarios (inline or as files or URLs). It starts SendMock in-process on free ports (or uses `--server <url>` for a running one), applies the setup, runs each scenario, and writes a JUnit XML report (`--junit <file>`), a JSON report (`--json`) and, when `GITHUB_STEP_SUMMARY` is set, a Markdown summary. Exit codes: `0` passed, `5` a scenario failed, `2` the files are invalid. Scenarios gain JSON and YAML alongside TOML, with the same steps.

  ```yaml
  sendmock:
    format: sendmock.ci
    format_version: 1
  setup: https://raw.githubusercontent.com/acme/shop/main/sendmock.setup.yml
  app_url: http://localhost:8000
  scenarios:
    - name: a paid order is accepted once
      steps:
        - run: payment.simulate
          with: { gateway: stripe, event: payment_intent.succeeded, amount: 4200 }
        - run: webhook.delivery.wait
          with: { endpoint: shop-stripe, status: succeeded, timeout: 10s }
        - run: http
          with: { method: GET, url: "{{ app_url }}/orders/latest" }
          save: order
        - run: assert
          with: { that: "{{ order.body.status }} == 'paid'" }
  report:
    junit: sendmock-report.xml
  ```
- **Both directions of a webhook test:**
  - *The app receives webhooks:* SendMock sends the provider's real webhook (Stripe, PayPal, Twilio status and inbound SMS, inbound email in Postmark, SendGrid or Mailgun shape, Standard Webhooks), signed with the endpoint's secret, so the app's signature check runs for real; steps check the response code, a retry after a failure (chaos and retry policies) and that a replayed webhook is handled once (idempotency).
  - *The app sends webhooks:* the app is pointed at an HTTP Catcher bin; new steps wait for a captured request (`http.request.wait` with method, path and body filters), check its signature (`webhook.signature.verify` for Standard Webhooks, Stripe-style and HMAC headers, with the secret from the setup) and assert on its body with JSONPath; the bin's mock responses return errors, timeouts or delays to test the app's own retries.
- **Pipeline snippets:** the docs give a tested, copy-paste job for GitHub Actions, GitLab CI, CircleCI, Bitbucket Pipelines, Azure Pipelines, Jenkins and Buildkite, each as numbered steps with each command in its own block: start SendMock (service container, Docker or the install script), start the app, `sendmock ci run`, publish the JUnit report. A GitHub Action (`shibbirweb/setup-sendmock`, in its own repository, since a Marketplace action's repository cannot hold workflows) installs a given version with its checksum, starts it with a setup path or URL, waits until ready, and outputs the SMTP and HTTP addresses; it can also run a CI file. Creating that repository is an owner step.
- **Any AI can set it up:** `sendmock ci init` looks at the repository (`.github/workflows`, `.gitlab-ci.yml`, `.circleci`, `bitbucket-pipelines.yml`, `azure-pipelines.yml`, `Jenkinsfile`), exports the running setup as YAML, and writes the setup file, a starter CI file with one scenario per webhook endpoint, and the pipeline job for the CI it found (`--provider` to choose), so an agent and a person get the same files. The skill gains a `ci-setup` section with these steps, MCP gains `sendmock_ci_init`, `sendmock_ci_validate` and a `setup-ci` prompt that walks an agent through it, `llms.txt` links the CI page, and the setup and CI JSON Schemas (A18) let the agent check its files before committing.
- **Every surface:** REST `POST /ci/run` (runs a CI file against this instance and answers the report), `POST /ci/validate` and `POST /ci/init`; the Scenarios screen imports a CI file from a file or a URL, runs it and shows the report per scenario and step, and offers the JUnit download; Settings > Setup gets a "Use in CI" card with the snippet for each CI system, filled in with the setup URL.

**Proof:** `examples/ci/` holds a small app that receives Stripe and Twilio webhooks and sends Standard Webhooks; a workflow runs it in GitHub Actions three ways: a service container with `SENDMOCK_SETUP` pointing at a URL (a local static server in the job, then the raw file on `develop`), `sendmock ci run` with the binary, and the GitHub Action. It checks the JUnit report and that a broken app fails the run with exit code `5`. The other CI systems' snippets are checked against their published schemas where one exists, and each is run by hand once before the docs page ships. `sendmock ci init` has snapshot tests for each CI system.

**Order:** A18 first (the versioned format, YAML and JSON, and the URL import are what A19 loads), then A19: `--setup` and `SENDMOCK_SETUP`, then `sendmock ci run` and the reports, then the webhook steps, then `ci init`, the MCP prompt and the docs, then the GitHub Action.

**Not in this part:** a hosted SendMock for CI, load testing, recording and replaying production webhooks, and CI systems' own plugins beyond the GitHub Action.

**As built (2026-11-22):** `--setup` in `crates/sendmock/src/startup_setup.rs`; the `ci` ops module (`ci_file.rs`, `ci_runner.rs`, `ci_reports.rs` with JUnit and the Markdown summary, `ci_init.rs`, `ci_pipeline_jobs.rs`, `ci_json_schema.rs` published as `website/public/schema/ci/v1.json`); `sendmock ci run` and `ci init` in `crates/sendmock/src/ci_command/` (paths inlined relative to the CI file, the in-process SendMock on the default ports when they are free, else free ones, so an app set up for SendMock's defaults reaches it); signature checks in `sendmock-webhooks` (`signature_verification.rs`) behind `webhook.signature.verify`; `http.request.wait` as an alias of `http.wait`; `assert` with `json`, `path` and `equals` or `exists`; a step whose answer has a false success flag (`is_valid`, `is_passed`) fails. Scenarios read TOML, JSON or YAML. The Scenarios screen's CI file card, Settings > Setup > Use in CI and a captured request's Verify signature; the demo runs JSON CI files with inline scenarios and cannot check signatures. `examples/ci/` runs `sendmock ci run` with its own SendMock and against one started with `SENDMOCK_SETUP` from a URL, and a broken app exits `5` (`.github/workflows/ci-examples.yml`). **Owner step still open:** the `shibbirweb/setup-sendmock` repository for the GitHub Action, so WH-15.8's Action and WH-15.9's third way wait for it; the docs do not name the Action until it exists.

## A20. Search engines and link previews (WS-13)

**Why (owner request, 2026-11-16):** the website at https://shibbir.me/sendmock/ had a title and description on its pages and nothing else search engines and link previews use: no canonical link, no Open Graph or Twitter tags, no structured data and no sitemap. The older docs versions and `/next/` repeat the current pages, so search engines saw duplicates.

**Where it is served:** the user site shibbirweb.github.io owns the custom domain shibbir.me, so the project site is served at https://shibbir.me/sendmock/ and shibbirweb.github.io/sendmock/ redirects there. That is the canonical origin. Search engines read `robots.txt` only at the domain root, which the portfolio serves, so the website has no `app/robots.ts`; a page is kept out of search with its robots meta tag, and the portfolio's `robots.txt` names the sitemap.

**How:**

- **One URL helper** (`website/lib/seo/site-url.ts`): `https://shibbir.me` plus the site root's base path, taken from the stable entry of the docs version list so every version links to the current site. Next does not add the base path to metadata URLs, so every URL is built absolute here and ends in `/` as Pages serves it; `metadataBase` is set as a fallback.
- **Every page's metadata from one helper** (`lib/seo/page-metadata.ts`): title, description (the docs frontmatter for docs pages), canonical, Open Graph and Twitter. Next replaces a layout's `alternates` and `openGraph` with a page's instead of merging, so the helper returns all of them.
- **Versions:** every docs version is built with today's website code, so this needs no change to old tags. `scripts/build-docs-versions.ts` builds the site root first and writes its page list; each other version reads it (`DOCS_ROOT_PAGE_PATHS_FILE`), names the root's page canonical when it exists, and is `noindex, follow` otherwise (owner decision: noindex rather than a canonical to the docs root, which search engines ignore for a different page). The decision is made in the page metadata, not by editing the HTML afterwards, so the HTML and Next's page data agree. Only the site root keeps `sitemap.xml`.
- **Link previews:** static 1200x630 images in `website/public/social/` (landing and docs), rendered by `bun run social-images` (`scripts/write-social-images.ts`) and committed.
- **Sitemap** (`app/sitemap.ts`, static): home, every docs page, the API, CLI and MCP references with their area pages, and the changelog. The playground (a tool with little text) and the demo (an app, `noindex`) are left out. **`lastmod` (owner request, 2026-11-17, #306, WS-13.9):** each entry carries the date of the last commit that changed the files its content comes from (`git log -1 --format=%cI -- <files>`, `lib/seo/source-last-modified.ts`): a docs page its Markdown in `docs/wiki/`, What's new, the upgrade guide and the changelog `CHANGELOG.md`, the API, CLI and MCP pages `docs/api/openapi.yaml`, `cli-reference.json` and `mcp-tools.json`, the landing page `website/app/(home)` and `website/components/landing`. The site root is built in a worktree of the stable tag, so content dates come from the tag's history; its website code is today's, so the landing page's date comes from the current checkout (`WEBSITE_GIT_ROOT`, set by `scripts/build-docs-versions.ts`). Template changes do not move the dates (search engines want content changes). When git cannot give a date (no git, no history for the file), the entry has no `lastmod`: wrong dates are worse than none. The Pages build checks out with full history (`fetch-depth: 0`).
- **JSON-LD** (`lib/seo/structured-data.ts`): the landing page's `WebSite` and SendMock as `SoftwareApplication` and `SoftwareSourceCode` (for `codeRepository`), free, MIT or Apache-2.0, with its GitHub, npm and Docker Hub pages; its author is `https://shibbir.me#person`, the Person the portfolio publishes, with only the name repeated. Google shows a software rich result only with ratings or reviews, which SendMock does not invent; the data still links the project to its author. Docs pages are `TechArticle` with a `BreadcrumbList`, the API, CLI and MCP area pages `WebPage` with one.
- **Basics:** the demo gets `noindex` when it is copied into the site (`scripts/build-pages-site.ts`); Next already marks the 404 page `noindex`.
- **Tests:** unit tests for the helpers, `website/tests/versioned-site/seo-export.spec.ts` over every page of the versioned export, and Lighthouse's SEO category at 100 on six pages.

**After it ships:** once `https://shibbir.me/sendmock/sitemap.xml` answers, the portfolio adds `Sitemap: https://shibbir.me/sendmock/sitemap.xml` to its `robots.txt`.

## A23. Fuller Twilio and Mailgun emulation (SM-19, SM-20, SM-21, EM-23, PL-20, PL-21)

**Why (a user's request, 2026-11-19, planned by owner request for 1.4.0):** a team on SendMock 1.2.0 (Laravel 13, PHP 8.5, the Twilio PHP SDK with one subaccount per customer, Mailgun's HTTP API and Laravel's Mailgun mailer) tests SMS and email locally and found gaps around webhook signature checks and less common API calls. Each item was reproduced on 1.2.0 (Homebrew, in-memory database) before planning:

| # | What the user reported | Checked on 1.2.0 |
|---|------------------------|------------------|
| 1 | `GET /2010-04-01/Accounts/{AccountSid}.json` answers 404 | Confirmed; `Accounts.json` too. The app reads a subaccount's auth token from it to check `X-Twilio-Signature`. |
| 2 | Callbacks are signed with one token whatever the account | Confirmed: a send under `AC1111...` with its own token was signed with the provider's `auth_token`. SendMock has no per-account tokens. |
| 3 | The `twilio_auth_token` webhook variable and the provider token look linked | Not linked. `GET /api/v1/webhooks/variables` masks a secret as `••••` and its last four characters, so the user checked signatures against the mask. Sending that mask as the provider's `auth_token` answered `is_modified: false` because it equals the mask of the stored token (`••••oken`), which keeps the stored value. The two tokens are separate: provider status callbacks and simulated replies sign with the provider credential, the `twilio.inbound_sms` and `twilio.status_callback` endpoint templates with the variable. Neither the split nor the default token (`twilio-test-token`) is documented. |
| 4 | Messaging Services and numbers are not mocked | Partly: `/v1/Services` already lists, creates, fetches, updates and deletes (SM-03). `/v1/Services/{sid}/PhoneNumbers` and `IncomingPhoneNumbers.json` answer 404. |
| 5 | No Debugger webhook template | Confirmed: only `twilio.status_callback` and `twilio.inbound_sms`. |
| 6 | Mailgun answers only `POST /v3/{domain}/messages` | Confirmed: it is the provider's only operation. |
| 7 | The provider port is plain HTTP | Confirmed. Symfony's Mailgun API and HTTP transports, which Laravel's `mailgun` mailer uses, build `'https://'.$endpoint` with no way to choose `http`. |
| 8 | No way to fill such gaps on a built-in provider | Confirmed: every operation kind ([22](22-configurable-providers.md#3-operation-kinds)) stores or reads a message, an unknown path answers 404 with no fallback, and a bin answers only on the catcher port or under `/catch/`, never on the provider's base URL. |
| 9 | `909582 is your App login code` gives no OTP | Confirmed, a bug: the code-first pattern only allows `is your code` with nothing between, so `909582 is your code` is found and the user's wording is not. |

**What Twilio and Mailgun do** (read 2026-11-19 from their API references):

- Twilio's Account resource has `sid`, `friendly_name`, `status` (`active`, `suspended`, `closed`), `type` (`Trial`, `Full`), `auth_token`, `owner_account_sid` (a parent's own SID for the main account), `date_created` and `date_updated` in RFC 2822, `subresource_uris` and `uri`. `POST /Accounts.json` creates a subaccount. The main account's credentials reach every subaccount's v2010 resources, and a subaccount's own credentials reach only its own.
- Twilio signs a webhook with HMAC-SHA1 and the auth token of the account the resource belongs to. Twilio now also offers shared signing keys with HMAC-SHA256 for webhooks; that is not in this part.
- A Messaging Service's PhoneNumber has `sid` (`PN`), `account_sid`, `service_sid`, `phone_number`, `country_code`, `capabilities` (`Voice`, `SMS`, `MMS`), dates and `url`; it is added with `PhoneNumberSid`.
- The Debugger webhook is a form POST signed with `X-Twilio-Signature`: `Sid`, `AccountSid`, `ParentAccountSid` (only for a subaccount), `Timestamp`, `Level`, `PayloadType` (`application/json`) and `Payload`, a JSON object with `resource_sid`, `service_sid`, `error_code`, `more_info` and, when a webhook failed, `webhook` with its request and response.
- Mailgun's `GET /v3/{domain}/events` answers `items` and `paging` (`first`, `last`, `next`, `previous` URLs) and filters by `event`, `recipient`, `message-id`, `from`, `to`, `subject`, `tags`, `severity`, `begin`, `end`, `ascending` and `limit` (up to 300). Complaints are listed, fetched, added and deleted per address under `/v3/{domain}/complaints`; a send to an address with a complaint is not delivered and is logged as a `failed` event with reason `suppress-complaint`.
- Other local mocks serve HTTPS with their own certificate and leave trust to the user: WireMock generates a self-signed certificate (or a CA) and asks clients to trust it; mkcert's local CA is the common way to trust one on a developer machine.

**The design:**

- **Twilio accounts and subaccounts (SM-19):**
  - The Twilio provider keeps its main account as today (`account_sid`, `auth_token`) and gains a list of **subaccounts**: SID, friendly name, auth token and status. They are managed on the Twilio provider's sheet (a new Accounts tab), through REST, CLI and MCP (agents set tokens but never read them back, as for other secrets), and in the seed file with tokens as `${ENV}` references.
  - The provider port answers `GET`/`POST /2010-04-01/Accounts.json` (list, filtered by `FriendlyName` and `Status`, and create) and `GET`/`POST /2010-04-01/Accounts/{AccountSid}.json` (fetch, and update `FriendlyName` and `Status`) in Twilio's shapes. These endpoints answer an auth token, so they always check credentials, even when **Check credentials** is off: the main account's credentials see every account, a subaccount's own see only itself, and anything else gets Twilio's `401`. The API request log masks the token in the answer.
  - Every Twilio webhook for a message is signed with the token of the message's account: status callbacks, simulated inbound replies and Debugger events. A SID that is not a subaccount uses the main token, so today's setups keep working. A send under a suspended or closed subaccount is refused with Twilio's error.
  - **One signing token by default (item 3):** the `twilio.inbound_sms` and `twilio.status_callback` endpoint templates read `vars.twilio_auth_token`, which now defaults to the provider's token for the event's account. A `twilio_auth_token` webhook variable still overrides it, and the template editor and the variables list say which token signs ("Twilio provider, account AC..." or "variable twilio_auth_token").
  - **Docs:** the SMS guide gets a "Twilio signatures" section: which token signs each Twilio webhook, the default token `twilio-test-token`, that a masked value such as `••••oken` is not the token, and how to read the real one (`sendmock sms providers credential twilio auth_token --reveal`, or the reveal on the provider sheet).
- **Twilio phone numbers (SM-20):**
  - `IncomingPhoneNumbers.json` lists, fetches, creates (from `PhoneNumber` or `AreaCode`), updates (`FriendlyName`, `SmsUrl`, `SmsMethod`, `SmsFallbackUrl`, `StatusCallback`) and deletes SendMock's virtual numbers (SM-12), each with a stable `PN` SID and the account it was created under (numbers made in the UI belong to the main account). Changes show on the Numbers screen, and edits there show in the API.
  - `messaging.twilio.com/v1/Services/{ServiceSid}/PhoneNumbers` lists, fetches, adds (`PhoneNumberSid`) and removes a service's numbers over the existing sender pool (SM-03.4). Adding a number that is in another service answers Twilio's error, as Twilio does; the Numbers screen's move stays.
  - Both answer on the one provider port by path, as `/v1/Services` does now, so an SDK pointed at the port reaches `api.twilio.com` and `messaging.twilio.com` paths alike.
- **Twilio Debugger webhook (SM-21):** a built-in `twilio.debugger` template with the fields above, `Level` `ERROR`, a `NO` SID, `ParentAccountSid` for a subaccount, and the Payload's `error_code`, `resource_sid` (the message SID) and `more_info`, signed with the account's token. The Twilio provider and each subaccount get a **Debugger webhook URL**, like the Console's; when set, a message that ends `failed` or `undelivered` with an error code (magic numbers, outcome rules, Simulate) and a status callback or inbound URL that fails (error `11200`, with the `webhook` object) each send one event. The template is also offered to webhook endpoints. Events are logged on the message's timeline and retried like status callbacks.
- **Mailgun events and complaints (EM-23):**
  - `GET /v3/{domain}/events` is built from the emails sent through the Mailgun provider for that domain and their simulated outcomes (`accepted`, `delivered`, `failed` with `severity` and `delivery-status`, `opened`, `clicked`, `complained`), with the same event data the `mailgun.events` webhook template sends, Mailgun's filters, and paging URLs that answer the next page.
  - `/v3/{domain}/complaints` lists, fetches, adds and deletes complaints (one address, or all), in Mailgun's shapes and errors. A complaint simulated in SendMock (Simulate, the `complaint@` alias, outcome rules) adds the address for that domain, and a later send to it is recorded as a `failed` event with reason `suppress-complaint`, as Mailgun does.
  - The Mailgun provider's sheet lists each domain's complaints and clears them; REST, CLI and MCP do the same.
- **HTTPS on the provider port (PL-20):**
  - `--provider-tls-addr <HOST:PORT>` (`SENDMOCK_PROVIDER_TLS_ADDR`, off by default) serves the same provider routes over HTTPS next to the plain `--provider-addr`, so SDKs that need HTTP keep it.
  - The certificate comes from `--provider-tls-cert` and `--provider-tls-key` (for example made with mkcert). Without them SendMock creates a **local CA** once, in its data folder with the key readable only by the user, and a server certificate from it for `localhost`, `127.0.0.1`, `::1` and the names in `--provider-tls-names`, renewed before it expires. The CA carries name constraints for those names only, so trusting it cannot vouch for any other site. `rcgen` and `rustls` are already in the binary (SMTP TLS), so no dependency is added.
  - `sendmock tls ca` prints the CA's path and PEM (`--json` too), `GET /api/v1/tls/ca` downloads it, and Settings > Connection shows the HTTPS address with a download button. The docs give numbered steps to trust it on macOS, Windows and Linux, in Docker, and per runtime (PHP `openssl.cafile`, Node `NODE_EXTRA_CA_CERTS`, Python `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE`, Java and .NET), each command in its own block.
  - `/api/v1/info`, `--ready-json` and the Docker docs include the HTTPS address.
- **Fill provider gaps with HTTP Catcher bins on the provider's own URL (PL-21; widened 2026-11-20 by owner request):** every emulated vendor misses some endpoints, and today the HTTP Catcher can only answer them on its own port or under `/catch/`, a different base URL from the one the app's SDK uses. One mechanism closes that, reusing the bins and their response rules (HC-02) instead of adding a second rule system:
  - **Unmatched requests, per provider, in every area** (email and SMS providers, Verify, push and payment gateways; storage providers when A25 lands): answer 404 in the provider's error shape (the default, as today) or **send them to an attached bin**. A request on the provider's base URL (the provider port, the provider's own `--provider-port`, and `/providers/<key>/` on the main port) that no built-in operation answers is captured in that bin, marked with the provider's name, and answered by the bin's response rules. Built-in operations always answer first. The catch-all port and `/catch/<bin>/` keep working unchanged, so a bin can serve both.
  - **A vendor SendMock does not ship:** a custom provider with no operations and an attached bin serves it on the provider port at the vendor's paths, with the vendor's credentials and accent like any provider.
  - **Follow-up webhooks:** a response rule can send a webhook after it answers: to a URL from a template (`{{ request.form.StatusCallback }}`) or a webhook endpoint, with any webhook template, the vendor-signed ones included (`twilio.status_callback`, `stripe.event`, ...), after a delay. It is delivered, logged and retried as a webhook delivery, so a missing endpoint can behave like the vendor's, callback and all.
  - **Visible:** the provider sheet shows its attached bin with **Create a bin for this provider**, the bin shows which providers send to it, and the API request log and the captured request name the provider, the bin and the rule that answered. Set on the provider sheet, through REST, CLI and MCP, and in the seed file.
  - **For agents:** the agent skill gets a "Fill a missing vendor endpoint" section (find the provider, attach a bin, add a rule with the vendor's documented answer and, if the vendor calls back, a follow-up webhook, then call the endpoint to check), MCP gets a `fill-provider-gap` prompt that walks through it, the tool descriptions of bins and providers mention it, and `llms.txt` links the docs page.
- **OTP fix (item 9, EM-05.6):** the code-first pattern allows up to three words between `is your` and the word for the code (`909582 is your App login code`), in SMS bodies and email subjects and bodies. A number without such words after it is still not a code. This is a bug fix (#316), so EM-05.6 is added and ticked in the pull request that fixes it, with its regression test.

**Proof:** fixture tests built from Twilio's and Mailgun's documented requests, answers and errors for every new path; SDK tests in CI: the Twilio PHP and Node SDKs fetch a subaccount's token, send under it and validate every callback and the Debugger event with `RequestValidator`, then provision a number, create a Messaging Service, attach the number and send with `MessagingServiceSid`; the Mailgun PHP SDK reads events and complaints; a Laravel app sends through the `mailgun` mailer over HTTPS with the local CA trusted; a Twilio SDK call SendMock does not implement is answered on the same base URL by an attached bin, which then sends the signed follow-up webhook.

**Order:** EM-05.6 first (small, unblocks the user), then SM-19 (the signing fix the user needs most), SM-20, SM-21, EM-23, PL-20, then PL-21.

**Not in this part:** Twilio's shared signing keys and HMAC-SHA256 webhook signatures, `AvailablePhoneNumbers` search, Mailgun's bounces and unsubscribes suppression lists (they can follow the complaints design), HTTPS for the main port, and per-provider HTTPS ports (`--provider-port` stays plain HTTP).

## A24. Interactive launcher (PL-22)

**Why (owner request, 2026-11-20):** each listener has its own flag (`--smtp-addr`, `--smtps-addr`, `--provider-addr`, `--provider-tls-addr`, `--catcher-addr`, `--pop3-addr`), and people do not remember them. Running `sendmock` in a terminal should instead ask which services to start, on which ports, remember the answer, and make the next start one key press. Scripts, CI, agents and MCP need the same saved choice without any question.

**What exists:** `sendmock` with no command runs `serve` with today's defaults (the HTTP port for the UI, API and MCP, and SMTP); the other listeners are off unless their flag, `SENDMOCK_*` variable or `sendmock.toml` key is set. `sendmock ai install` already asks a question only when stdin is a terminal. No prompt library is in the binary.

**How others do it:** the Command Line Interface Guidelines (clig.dev) say to prompt only when stdin is an interactive terminal, to make every prompt skippable with a flag, and to offer `--no-input` to turn prompts off. Scaffolding tools such as `create-vite` ask only for what was not given as an argument; `gh` never prompts outside a terminal.

**The design:**

- **When it asks:** only for a bare `sendmock` (no command, no option) when stdin and stdout are terminals, `CI` is not set and neither `--no-input` nor `SENDMOCK_NO_INPUT=1` is given. Anything else runs exactly as today, so `sendmock serve`, every flag, the systemd unit, Homebrew and Scoop services, the npm launcher, the tray app (`sendmock serve ...`) and pipes are unchanged. The Docker image sets `SENDMOCK_NO_INPUT=1`, since its entrypoint is a bare `/sendmock` and `docker run -it` gives it a terminal.
- **The questions** (keyboard only: arrows, Space, Enter; readable without colour):
  1. **Services**, a checkbox list: Web UI, REST API and MCP over HTTP (always on, shown ticked and locked, since everything else is managed there), SMTP, SMTPS, Provider APIs (HTTP), Provider APIs (HTTPS, A23), HTTP Catcher, POP3. Each line shows its address. The ticks are the last run's, or today's defaults on a first run. A service that is off today and has no address in `sendmock.toml` or a `SENDMOCK_*` variable is offered on `127.0.0.1` with a fixed port: SMTPS `1465`, Provider APIs `8026` (as in the Docker docs), Provider APIs over HTTPS `8027`, HTTP Catcher `8030` and POP3 `1110` (as in the guide's examples).
  2. **Start**, a list with **Run** selected: Run, Change ports, Reset to defaults, Cancel. So a returning user presses Enter twice.
  3. **Change ports** asks for the address of each ticked service, prefilled, and checks it: a port already in use or used twice is named, with the next free port offered. Then back to step 2.
- **Remembered:** after Run, the ticked services and their addresses are written to `last-run.toml` in SendMock's OS config folder (next to `sendmock.toml`), one key per line, with the format version. It holds no secrets. **Reset to defaults** deletes it. The first run's starting values come from `sendmock.toml`, `SENDMOCK_*` variables and the defaults, in today's order.
- **Without questions:**
  - `sendmock --last` (and `sendmock serve --last`) starts with the saved choice and never asks; with nothing saved it starts with the defaults and says so on stderr. Flags given with `--last` win over the saved values, for that run only.
  - `sendmock mcp --embedded --last` starts the embedded SendMock with the saved services, so an agent gets the same ports as the person who last ran it.
  - `--no-input` and `SENDMOCK_NO_INPUT=1` never ask, for any command.
  - **Several services in one command, as today:** every listener flag keeps working (`sendmock serve --smtp-addr 127.0.0.1:1025 --catcher-addr 127.0.0.1:8030 --pop3-addr 127.0.0.1:1110`), and a shorter form needs no addresses: `sendmock --services smtp,catcher,pop3` (`SENDMOCK_SERVICES`) starts the HTTP port and those services on their saved or default addresses, without asking. The names are `smtp`, `smtps`, `provider`, `provider-tls`, `catcher` and `pop3`; an unknown name is refused with the list. Address flags given with it win.
  - `sendmock last-run` prints the saved choice (`--json` too) and `sendmock last-run clear` deletes it. These are local start-up settings, not server operations, so like `serve` they have no REST or MCP form; the startup line and `/api/v1/info` already show what is listening.
- **After Run:** the usual startup output, plus one line with the equivalent command (`sendmock serve --smtp-addr ... --catcher-addr ...`) for scripts and CI.
- **Dependency:** one small prompt crate. `dialoguer` (on `console`) is the first choice over `inquire` (on `crossterm`), as the smaller tree; the pull request measures the release binary before and after (`cargo bloat`) and states the cost, within the [budget](09-distribution.md#performance-budget-checked-in-ci-on-linux-x64).

**Proof:** unit tests for when it asks (each flag, variable, `CI`, a pipe), the saved file (write, read, unknown version, corrupt file falls back to the defaults with a warning) and port checks; CLI tests that drive the prompt through a pseudo-terminal (tick a service, change a port, Run, Enter-Enter on the second start); snapshot tests for `--last`, `--no-input` and `last-run --json`; the Docker image test starts it with `-it` and sees no question.

**Not in this part:** a full-screen terminal UI that stays open while SendMock runs, named profiles beyond the last run, and asking for non-listener settings (database, retention, auth), which stay as flags and `sendmock.toml`.

**As built (2026-11-22):** `crates/sendmock/src/launcher/` (services, the decision, `last-run.toml`, port checks, the question flow behind a `LauncherPrompter` trait, the `dialoguer` 0.12 terminal prompter without default features, and `sendmock last-run`). Two changes from the design above, both recorded here: **SMTP is shown ticked and locked like the HTTP port**, because SendMock has no way to start without its SMTP listener (`/api/v1/info`, the connection snippets and the ready line all assume one); turning SMTP off is a later change. **The question flow is proven by a scripted prompter** (`launcher_flow.rs` tests: Enter twice, Change ports with a repeated, busy and malformed address, Reset to defaults, Cancel) instead of driving a pseudo-terminal, which needs a PTY crate on every OS; the binary tests (`crates/sendmock/tests/launcher_commands.rs`) cover `--last`, `--services`, `last-run` and a bare start without a terminal. `SENDMOCK_LAST_RUN_FILE` moves the file, as the tests need on Windows, where the config folder ignores the environment.

## A25. Storage mock (ST-01 to ST-06)

**Why (owner request, 2026-11-20, for 2.0.0):** apps upload files as often as they send email: user avatars to S3, product images to Cloudinary, documents to Google Cloud Storage. Testing that locally today means a real bucket or a separate emulator per vendor. SendMock should answer the storage and image upload APIs the way it answers the email, SMS and payment ones: the vendor's real paths, requests, answers and errors, with every file visible in the UI, and as many vendors as the other areas, added the same way.

**How others do it** (read 2026-11-20): Adobe's S3Mock covers buckets, objects and multipart uploads, path-style only, with no authentication and presigned URLs accepted without checking the signature or expiry. LocalStack and MinIO answer the S3 API more fully. Google Cloud Storage has no official emulator (fake-gcs-server is the community one); Azure's official emulator is Azurite. Each is one vendor per tool, so an app that uses S3 for documents and Cloudinary for images runs two emulators and still has nowhere to see what was uploaded.

**What the vendors do:**

- **S3:** REST over HTTP with XML answers and errors (`NoSuchBucket`, `NoSuchKey`, `BucketAlreadyOwnedByYou`, ...), path-style (`/bucket/key`) and virtual-hosted-style (`bucket.host/key`) addressing, Signature Version 4 in the `Authorization` header or in a presigned URL's query, browser uploads with a POST policy, multipart uploads, and event notifications whose JSON has a `Records` array with `eventName` such as `ObjectCreated:Put` and the object's URL-encoded `key`, `size` and `eTag`. Cloudflare R2, DigitalOcean Spaces, MinIO, Backblaze B2 and Wasabi answer the same API at their own endpoints.
- **Cloudinary:** `POST /v1_1/{cloud_name}/image/upload` with a signature that is a SHA-1 of the sorted parameters with the API secret appended (or Basic auth with the key and secret), answering `public_id`, `version`, `format`, `width`, `height`, `bytes`, `secure_url`, and calling a `notification_url` when given.
- **ImageKit:** `POST https://upload.imagekit.io/api/v1/files/upload` with the private key, answering `fileId`, `name`, `url` and `thumbnailUrl`.
- **Uploadcare:** `POST https://upload.uploadcare.com/base/` (every path ends in `/`), answering the file's UUID, served from its CDN URL.
- **Cloudflare Images:** `POST /client/v4/accounts/{account_id}/images/v1` and one-time upload URLs from `/images/v2/direct_upload`, answering the image with its `variants` URLs.
- **Google Cloud Storage** (JSON API: media, multipart and resumable uploads, get, list, delete) and **Azure Blob Storage** (Put Blob, Get Blob, List Blobs, Delete Blob, Shared Key and SAS tokens).

**The design:**

- **A new area, Storage (ST),** built like email, SMS and payments: a domain with buckets and objects, a `StorageRepository`, a `StorageService`, and one **adapter per vendor** registered in a **storage provider registry** (Adapter and Registry, as in [22](22-configurable-providers.md)). Adding a vendor is adding an adapter and its built-in definition; no existing adapter changes.
- **S3-compatible API first (ST-01):** on the provider port (and `/providers/s3/` on the main port): buckets (create, list, head, delete), objects (put, get with `Range`, head, delete, delete many, copy, list v2 with `prefix`, `delimiter` and continuation tokens), multipart uploads (create, upload part, complete, abort, list parts), user metadata and content type, MD5 `ETag`s, browser POST uploads with a policy, and CORS preflight from the bucket's CORS rules. Path-style always; virtual-hosted-style when the `Host` names a bucket (`bucket.localhost:8026`). Signatures follow the provider rule: any credentials pass by default, and with **Check credentials** on, a wrong SigV4 signature answers S3's `SignatureDoesNotMatch`; a presigned URL's expiry is always checked. R2, Spaces, MinIO, B2 and Wasabi are built-in presets of the same adapter with their endpoint styles. The official AWS SDKs, the AWS CLI with `--endpoint-url`, and Laravel's `s3` disk (with `AWS_ENDPOINT` and `AWS_USE_PATH_STYLE_ENDPOINT`) work against it.
- **The Storage screen and every surface (ST-02):** a Storage screen lists buckets per provider and browses objects as folders, with an image, text, JSON and PDF preview, upload, download, delete, metadata, and a presigned URL generator; live updates as files arrive. REST, CLI, MCP and the seed file (buckets and their settings, never file contents) cover the same, from the `sendmock-ops` registry. Events `storage.object.created` and `storage.object.deleted` go to webhook rules, with an **S3 event notification** template (the `Records` JSON) and each image vendor's own notification shape.
- **Where files are kept (ST-03):** by default SendMock keeps uploaded files itself, in its data folder (in memory with `--db memory`), under the storage size limit (`--max-storage`, default 1 GB) and the traffic retention, oldest first. **Settings > Storage > Keep files in a folder** (`--storage-dir`, `SENDMOCK_STORAGE_DIR`, `storage_dir` in `sendmock.toml`) writes each file as a real file at `<folder>/<provider>/<bucket>/<key>`, so it opens in the file manager, and reads it back from there; the folder must exist and be writable, a key that would leave the folder (`..`, absolute paths) is refused, and names a file system cannot hold are encoded. Turning it on or off asks whether to copy the existing files over. Files in the folder are not pruned by retention unless **Prune the folder too** is on.
- **More storage vendors (ST-04):** Google Cloud Storage's JSON API and Azure Blob Storage, as adapters of their own over the same buckets and objects, each with its errors and its SDK test.
- **Image upload vendors (ST-05):** Cloudinary, ImageKit, Uploadcare and Cloudflare Images as built-in providers, each answering its upload API with its own fields and errors, checking its signature when Check credentials is on, serving the uploaded file at the URL it answered (the original file: transformations in the URL are accepted and ignored, and the answer says so in a header), and sending its upload notification. Uploads land in the Storage screen under the vendor, with the image's width and height read from the file.
- **Your own storage service (ST-06):** a custom storage provider, from blank or from a built-in, with the operations an app needs: upload (a multipart field or the raw body, with the key from a template), download, delete, list and metadata, each with a method and path pattern, the request fields it reads, an auth check (a header, a query token or none) and answer and error templates in any format (JSON, XML or text) using the template language of webhooks and bin responses. A live preview runs a sample request. Saved, exported and reset like the other configurable providers.

**Safe defaults:** files never leave the machine; the storage APIs listen only where the provider port does (`127.0.0.1` by default); credentials are masked as everywhere; the seed file and setup exports hold bucket settings, never file contents; a folder setting can only be changed from the UI, REST or CLI by someone who can change Settings.

**Lightweight:** SigV4 uses the `hmac` and `sha2` crates already in the binary, and `md5` gives the `ETag`s. S3's XML and the image dimensions may each need a small crate (an XML writer and reader, an image header reader that does not decode pixels); the first pull request measures them against the [budget](09-distribution.md#performance-budget-checked-in-ci-on-linux-x64) and justifies them.

**Proof:** fixture tests built from each vendor's documented requests, answers and errors; SDK tests in CI: the AWS SDKs for JavaScript, Python, PHP and Go (put, get, list, multipart, presigned GET and PUT), the AWS CLI, Laravel's `s3` disk, the Google Cloud Storage and Azure Blob SDKs, and the Cloudinary, ImageKit and Uploadcare SDKs; a test that a key with `..` cannot leave the folder; e2e tests for the Storage screen.

**Order:** ST-01 and ST-03 (the core and where files live), then ST-02 (the screen and surfaces), then ST-05 (image vendors), ST-04 (GCS and Azure), and ST-06 (custom storage services).

**Not in this part:** image transformations, video processing, object versioning, lifecycle rules, bucket policies and ACLs beyond public or private, S3 Select, and forwarding uploads to a real bucket (A14's real forwarding can follow).

## A26. Download activity in the footer wordmark (WS-15)

**Why (owner request, 2026-11-21):** the website's footer wordmark, the letters made of scrolling event lines (#335, 1.3.1), made the page lag on phones and laptops, because every line repainted through an SVG clip and mask on each frame. 1.3.1 stops the scrolling. For 1.4.0 the owner wants the design of the footer signature on shibbir.me (`SignatureSpotlight` in the portfolio repository), with SendMock's own data: where that one shows the owner's GitHub contributions, SendMock's shows how many times it was downloaded each day.

**How the portfolio's signature works:** the name is an outline SVG path in a dim solid colour. A canvas over it fills the letters with small rounded squares, coloured in five levels from the activity data. Two CSS radial-gradient masks, driven by `--pointer-x`, `--pointer-y` and `--spotlight-opacity`, make a soft circle: the graph shows at 30% everywhere and at full strength inside the circle, where the solid letters step aside. One window `pointermove` listener measures how close the pointer is to the signature, so the circle wakes before the pointer reaches the letters. It writes the variables straight to the element (React never renders on pointer moves) and runs animation frames only while something is still moving.

**The design:**

- **The wordmark:** "SendMock" (only S and M in capitals) as an outline path in Oswald at weight 400, the face of the portfolio signature, made once from the font file (SIL Open Font License) and committed, so it looks the same on every device (owner decisions 2026-11-21: Geist Black looked short and wide). There is no solid letter behind the squares: with coloured squares the grey letter showed through the gaps and its smooth edge stuck out past the stepped squares, so the squares alone draw the word, as a contribution graph does. The bottom edge fades into the page.
- **The pixel graph:** a canvas fills the letters with small rounded squares on a 1.8-unit grid (owner choice: 10% smaller than the portfolio's 2). The letter shape is drawn once into a tiny off-screen canvas, one pixel per square, and read back in one call. The five levels use the design tokens' brand colours and follow the light and dark themes; a day with no downloads is a grey square, so the word reads even with no data. The squares show at 55% at rest and at full strength under the spotlight. Until the canvas has drawn, an inline SVG in the HTML draws the same squares (the letters filled with a pattern on the same grid), so the first paint is never blank; it fades out once the canvas draws.
- **The data:** total downloads per day for 7 days, oldest on the left: the 7 days up to the newest day any source reports, never later than yesterday (UTC), so a registry that is a day behind does not leave the last letter empty. The busiest day is at the top level and every other day at `ceil(4 x day / busiest)`, a day with none at level 0. The days blend into each other at their edges, with a little variation per square, as in the portfolio.
- **The sources:** only registries that publish counts per day:
  - npm: `sendmock` and `sendmock-testcontainers`, in one bulk request (`api.npmjs.org/downloads/range`).
  - crates.io: the `sendmock` crate, its per-version counts summed per day (`crates.io/api/v1/crates/sendmock/downloads`).
  - PyPI: `sendmock-testcontainers` (`pypistats.org/api/packages/sendmock-testcontainers/overall`, without mirrors). pypistats blocks browser requests, so PyPI's days come from the build only.
  - Left out, because they come along with a counted package and would count one install twice: the npm platform packages and the library crates (`sendmock-api`, `sendmock-ops`).
  - Not counted: GitHub Releases (the binaries, install scripts, Homebrew, Scoop, WinGet and AUR), Docker Hub, NuGet and Chocolatey give running totals only, not days; GHCR, apt, dnf, COPR and Nix give no counts.
- **At build, then live (owner decision 2026-11-21):**
  - **The build** fetches every source's days and writes them into the site (`website/lib/download-activity/`, run by the website build), so the graph shows real numbers on first paint, with no request. A source that fails at build is left out, and a build with no data at all still succeeds, with every square at level 0. Every website deploy refreshes them: each push to `develop`, each release, and a hand-run of the Website workflow (`workflow_dispatch`) whenever the owner wants newer numbers.
  - **In the browser** the page then fetches npm and crates.io again, when the footer comes within 600 px of the screen (8 second timeout), and keeps the answer in `localStorage` for 4 hours. Each source's live days replace its build days; PyPI keeps its build days. The 7 days are always the last 7 complete UTC days at the time of the visit, so an older build's days that fall outside them drop out. A failed live request keeps the build's numbers, and nothing errors.
- **The spotlight:** a soft circle `72cqw` wide (it scales with the wordmark), which wakes as the pointer comes within 72 px above, 56 px beside or 28 px below the letters. Its position eases over 120 ms and its brightness over 380 ms. While dark it jumps to the pointer, so it never slides in, and when the pointer leaves, the circle stays where the pointer left it and fades out. The squares breathe gently while it is lit.
- **Cost:** no frame runs while idle, only changed squares are repainted, and touch screens (no hover, coarse pointer) attach no listener, so phones show the graph at rest. With reduced motion the squares do not breathe and the circle moves without easing.
- **Decorative:** hidden from assistive technology; the footer above already names SendMock.
- **Files:** `website/components/footer-wordmark/` (the server component that reads the build's numbers, the client spotlight, the placeholder, the path, the CSS module and the hooks), `website/lib/download-activity/` (the sources, the build read, the 7 days and their levels, the cache, the live refresh and the canvas graph, with unit tests), and `website/tests/footer-wordmark.spec.ts`, with npm and crates.io answered by fixtures and the test build reading `website/tests/fixtures/download-activity-sources.json` (`DOWNLOAD_ACTIVITY_SOURCES_FILE`) instead of the registries. The footer, and so the wordmark, is on the landing, changelog, API, CLI, MCP and playground pages; the docs pages have their own layout.

## A27. Startup banner (PL-23)

**Why (owner request, 2026-11-22):** starting SendMock in a terminal shows only log lines. The owner wants the SendMock wordmark and its version on top, in the look of the website's footer wordmark ([A26](#a26-download-activity-in-the-footer-wordmark-ws-15)), whose letters are made of small squares.

**What exists:** the footer's letters are "SendMock" in Oswald at weight 400, an outline path in `website/components/footer-wordmark/sendmock-wordmark-path.ts` (viewBox 366.3 by 82.6, SIL Open Font License). The startup logs go to stdout (stderr for `sendmock mcp`), with colour only when stdout is a terminal (`logging.rs`), and the ready line follows. `sendmock --version` prints one plain line that scripts read. The `console` crate is already in the binary (through `dialoguer`, A24) and reads the terminal's width.

**How others do it:** Spring Boot prints an ASCII banner with the version at startup, from a `banner.txt`, and turns it off with `spring.main.banner-mode=off`. Vite and Next.js print one styled line with their version when a dev server starts. The Command Line Interface Guidelines (clig.dev) say to decorate only when the output is a terminal, to keep machine-readable output unchanged, and to respect `NO_COLOR` and `TERM=dumb`. Colour libraries such as `supports-color` use 24-bit colour only when `COLORTERM` is `truecolor` or `24bit`, and 256 colours otherwise.

**The design (owner choices 2026-11-22: the footer's look, braille dots, fitted to the terminal's width, 1.5.0):**

- **The picture:** the footer's outline drawn in braille characters (`U+2800` to `U+28FF`, each a 2 by 4 grid of dots), so it reads as a grid of dots like the footer.
- **Fitted to the width:** the picture is the tallest that fits the terminal's width (read when SendMock starts), from 5 lines (about 44 columns) up to 12 lines (about 107 columns), so an 80-column terminal gets 8 lines and 71 columns and a very wide one is not filled with the logo. Under it, right-aligned, `v` and the version (`v1.5.0`, `v1.5.0-beta.1`; a development build shows its dev version as `sendmock --version` does).
- **Colour:** mint at the top, fading toward the foot like the footer, one colour per line from the design tokens' brand colours. 24-bit colour when `COLORTERM` is `truecolor` or `24bit`, the nearest of 256 colours otherwise, and no colour with `NO_COLOR` or `TERM=dumb`.
- **When it prints:** first, before the server runs: as soon as a server command (`sendmock`, `sendmock serve`, `--last`, `--services`) has read its settings and stdout is a terminal, before SendMock opens its database, binds a port or prints its first log line. For a bare `sendmock` it comes before the launcher's questions, so the questions and then the startup lines follow it.
- **When it does not:** stdout not a terminal (pipes, files, systemd, the tray app, Docker without `-t`, CI logs), `--ready-json`, `--log-format json`, `sendmock mcp` and `sendmock mcp --embedded` (stdout carries MCP messages), every client command, and `--version`. So scripts, parsers and agents see exactly today's output.
- **Turning it off:** `--no-banner`, `SENDMOCK_NO_BANNER=1`, or `banner = false` in `sendmock.toml`. Like `--no-input`, a start-up option of the local process, not a server operation, so it has no REST or MCP form.
- **Fallback:** one plain line, `SendMock v1.5.0`, when the terminal is too narrow for 5 lines, its width cannot be read, or it cannot show braille: on Unix, no UTF-8 locale in `LC_ALL`, `LC_CTYPE` or `LANG`; on Windows, a console whose output code page is not UTF-8 (65001), outside Windows Terminal (`WT_SESSION`).
- **Cost:** the outline is turned into straight edges once, not at runtime: a script (`scripts/banner/export-wordmark-outline.ts`) flattens the footer's path and writes the points into a Rust constant (`crates/sendmock/src/startup_banner/wordmark_outline.rs`), and a test fails when the committed points differ from what the script makes from the current path, as the schema tests do. At startup SendMock reads the width, fills the outline row by row at that size (a scanline fill: under 50 dot rows by about a thousand edges, well under a millisecond) and writes the lines once. No new dependency (the width comes from `console`, already in the binary), a few KB of binary and no measurable startup time, within the [budget](09-distribution.md#performance-budget-checked-in-ci-on-linux-x64).
- **Code:** `crates/sendmock/src/startup_banner/` (the decision when to print, the size for a width, the scanline fill, the colour level, the fallback and the rendering), called once at the start of a server command, before the launcher, the database and the listeners.

**Proof:** unit tests for the decision (terminal or not, each flag, variable and config key, `--ready-json`, `--log-format json`, MCP), the colour level (`COLORTERM`, `NO_COLOR`, `TERM=dumb`), the size for a width (44, 80 and 200 columns, and the cap), the fallback (too narrow, no width, locale, code page) and the version line; snapshot tests of the banner at 5, 8 and 12 lines without colour and at 8 lines in 24-bit colour; the outline export test; and binary tests that piped output and `--ready-json` start with today's first line.

**Not in this part:** animation, a banner file of the user's own, and a banner for client commands.

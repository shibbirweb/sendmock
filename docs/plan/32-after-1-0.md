## A1. Mailpit API compatibility (EM-19)

**Why:** SendMock listens on Mailpit's ports (SMTP 1025, HTTP 8025, [10](10-open-questions.md)), so an app switches by changing nothing. Its test suite does not: tests that read mail through Mailpit's API (`/api/v1/messages`, `/api/v1/message/latest`, `/api/v1/search`) fail against SendMock. [10](10-open-questions.md) §9 recommended compatibility aliases after 1.0; this builds them.

**Source of truth:** Mailpit's own API definition, `server/ui/api/v1/swagger.json` in `axllent/mailpit` at `v1.33.0` (the latest release on 2026-11-07). A trimmed copy (the paths and definitions below) is kept as a test fixture in `crates/sendmock-api/tests/fixtures/mailpit/`, with its source and licence (MIT) noted, and every answer is checked against it.

**What is served,** on the main HTTP port at Mailpit's paths:

| Mailpit endpoint | Answer | From |
|------------------|--------|------|
| `GET /api/v1/messages?start&limit` | `MessagesSummary`: `total`, `unread`, `messages_count`, `messages_unread`, `start`, `tags`, `messages` (each a `MessageSummary`), newest first | the email list |
| `GET /api/v1/search?query&start&limit` | the same, for messages matching a [Mailpit search](https://mailpit.axllent.org/docs/usage/search-filters/) | the email list with its `query` |
| `DELETE /api/v1/search?query` | `ok` | delete each match |
| `PUT /api/v1/messages` (`IDs`, `Read`, `Search`) | `ok`; no IDs and no search sets every message | mark read or unread |
| `DELETE /api/v1/messages` (`IDs`) | `ok`; no IDs deletes every message | delete |
| `GET /api/v1/message/{ID}` | `Message`: addresses as `{Name, Address}`, `Text`, `HTML`, `Attachments` and `Inline` with `PartID`, `Tags`, `Size`, `Date`; marks it read | the email detail |
| `GET /api/v1/message/{ID}/headers` | `{header: [values]}`, keys in alphabetical order | the raw source's headers |
| `GET /api/v1/message/{ID}/raw` | the source as `text/plain` | the raw source |
| `GET /api/v1/message/{ID}/part/{PartID}` | the part's bytes with its content type | the MIME part |
| `GET /api/v1/tags`, `PUT /api/v1/tags` (`IDs`, `Tags`) | the tag names; `ok` after replacing the messages' tags | the email tags |
| `GET /view/{ID}.html`, `GET /view/{ID}.txt` | the HTML or text part; 404 when the message has none | the email detail |

`{ID}` is SendMock's email ID; `latest` means the newest message, as in Mailpit. Mailpit's search words map to SendMock's own search, which reads the same `from:`, `to:`, `subject:`, `tag:`, `is:read`, `is:unread` and `has:attachment` filters; other filters are read as words. Errors answer as Mailpit does: 404 with a plain text body for a missing message, 400 with plain text for a bad request.

**Not served:** `GET /api/v1/info` and `POST /api/v1/send` are SendMock's own endpoints at the same paths, with their own shapes, and stay so (an app that sends through Mailpit's HTTP API is rare; one that reads through it is common). Mailpit's chaos, web UI configuration, HTML, link and spam checks, release, thumbnails and tag rename and delete are not emulated: SendMock has its own versions of most of them in its API. The docs page lists both.

**Where it lives** (the Adapter pattern, as for provider emulation): `crates/sendmock-ops/src/email/mailpit/` translates SendMock's email records to Mailpit's shapes (`MailpitMessageSummary`, `MailpitMessage`, `MailpitMessagesSummary`) and Mailpit's requests to SendMock's email operations, with no HTTP in it; `crates/sendmock-api/src/mailpit_routes.rs` is the thin router that reads the request and writes the answer. These are compatibility aliases, like the provider APIs, not new operations: they add no CLI command or MCP tool, since the native ones already do the same.

**Docs:** a guide page "Coming from Mailpit" under Mail: what keeps working unchanged (ports, the endpoints above, `X-Tags`), the two endpoints that differ, and what SendMock adds.

**Tests naming EM-19:** unit tests of the adapter's translations; API tests for every endpoint above, each answer checked against the fixture's definitions; an end-to-end test that sends mail over SMTP and reads it back through the Mailpit paths, as a Mailpit-based test suite does.

**As built (2026-11-07):** `crates/sendmock-ops/src/email/mailpit/` (`mailpit_shapes.rs`, `mailpit_mailbox.rs`) and `crates/sendmock-api/src/mailpit_routes.rs`, merged into the app router, so UI auth covers it like the native API. New store queries in `crates/sendmock-store/src/email/email_mailbox_queries.rs` (a page by offset, counts, every tag, read status for a search), and `compute_file_checksums` in `sendmock-core` for the attachments' `Checksums`. Deletes and per-message changes go through the native operations, so `email.deleted` and the UI follow. Two things found while building: the mail parser renders an HTML version of a text-only message for SendMock's preview, which Mailpit does not have, so the adapter reads the MIME tree and answers `HTML: ""` and a 404 view for those; and Mailpit's dates are Go's RFC 3339 without trailing zero fractions, which SendMock's format already matches. Tests: `mailpit_api.rs` (every endpoint, each answer checked against `fixtures/mailpit/mailpit-definitions.json`), `crates/sendmock/tests/mailpit_compatibility.rs` (SMTP to `search` and `message/latest` on a real binary), unit tests in `mailpit_shapes.rs`, and `scripts/mailpit-docs.test.ts` (the guide lists every path the router serves).

## A2. `email.clicked` link-click tracking (EM-20)

**Why:** apps test click tracking the way they test opens: "the user clicked the verify link, so stop the reminder", engagement scores, A/B links. Every email provider SendMock emulates reports clicks, and `email.opened` already exists ([05](05-webhooks.md#opened-events), EM-11); clicks were left for after 1.0 ([11](11-roadmap.md)).

**What the providers send** (checked against their docs on 2026-11-07): SendGrid `"event": "click"` with `url` (and `url_offset`); Mailgun `"event": "clicked"` with `url`; Postmark `"RecordType": "Click"` with `OriginalLink` and `ClickLocation` (`HTML` or `Text`); Resend `"type": "email.clicked"` with `data.click` `{ ipAddress, link, timestamp, userAgent }`; Amazon SES `"eventType": "Click"` with `click` `{ ipAddress, link, linkTags, timestamp, userAgent }`; Brevo `"event": "click"` with `link`; SparkPost `"type": "click"` with `target_link_url`. Each built-in template gains its click shape, and each provider's status names gain `clicked`, so a provider endpoint receives clicks exactly as the provider sends them.

**When it fires,** as opens do, but a click is always deliberate, so there is no setting to turn the UI's clicks off:

| Source | `source` | Behaviour |
|--------|----------|-----------|
| A link clicked in the email's HTML or text preview | `ui` | the link opens in a new tab as before, and the click is recorded |
| Simulate click in the email's actions (pick one of its links) | `manual` | always fires |
| `POST /api/v1/emails/{emailId}/clicks` with `url` (and optional `user_agent`) | `api` | always fires, for CI tests |

The URL must be one of the email's links (the `links` SendMock already extracts, EM-13), as a provider only tracks links it rewrote; another URL answers 422 `unknown_link` with the email's links in the message.

**Payload** (`email.clicked`): the email fields `email.opened` carries, plus `url`, `clicked_at`, `first_click` (the first click on that URL), `click_count` (all clicks on the email), `source` and `user_agent`. Each click is kept (`GET /api/v1/emails/{emailId}/clicks`, newest first), the email's detail gains `click_count`, and its timeline shows each click.

**Where it lives:** migration `email_clicks` (email, URL, time, source, user agent); `EmailClickRepository` beside the opens; `RecordEmailClickOperation` and `ListEmailClicksOperation` in `crates/sendmock-ops/src/email/` (so REST, CLI `sendmock email click <emailId> --url` and the MCP tool `sendmock_email_click` come from the registry); the event in the event catalogue and webhook rule filters on `url`, `first_click`, `click_count` and `source`. The UI first, against the mock (API change in [06](06-api.md), then types, the regenerated spec and the MSW handlers), then the binary.

**Split:** A2a the contract, mock and UI (the preview's click capture, Simulate click, the timeline entries, the Deeper entries); A2b the binary (store, operations, event, rule filters); A2c the provider templates and their fixture tests; A2d the docs (Opened and clicked events, the Mail guide, the skill).


**As built, A2a and A2b (2026-11-07):** one commit, since the generated spec and the binary's registry must agree in CI. UI and mock: `web/src/features/mail/detail/preview/use-preview-link-clicks.ts` listens for clicks in the preview (the listener belongs to the app page; the click's target comes from the preview's own realm, so it is checked with `closest`, not `instanceof Element`), `simulate-click-menu.tsx` adds Simulate > Click a link, and `web/src/mocks/clicks/` and `email-click-handlers.ts` answer the API. Binary: migration `0034_email_clicks.sql`, `email_click.rs` in the store, `email_click_operations.rs` in the operations (422 `unknown_link` lists the email's links), `email.clicked` in the event catalogue, the rule fields `url`, `first_click` and `click_count` in `sendmock-webhooks` and in the UI's rule builder, and `with_engagement_event_fields` reading a click's own fields as an open's. The wait-for-email answer now carries the same detail as `GET /emails/{emailId}`, click count included. Tests: `crates/sendmock-api/tests/email_clicks_api.rs`, `web/tests/e2e/email-clicks.spec.ts`, `web/src/mocks/clicks/record-mock-click.test.ts` and the rule message unit test. A2c (provider click shapes) and A2d (docs, CLI test, skill) follow.

**As built, A2c (2026-11-07):** the click shapes live in the template definitions (`web/src/mocks/fixtures/template-definitions.ts`, exported to `crates/sendmock-ops/builtin/` with the providers' `clicked` status names and `email.clicked` in each email template's events), plus `clicked` in both event name tables (`template_event_name_filters.rs` and the demo's `render-template-text.ts`). SES now sends a click as event publishing does (`eventType` with a `click` object) and SparkPost sends opens and clicks as `track_event`s. `crates/sendmock-api/tests/email_click_provider_formats.rs` delivers one click to all seven templates and reads each body at the paths `fixtures/provider_webhooks/click_events.json` records from the providers' docs. Building it found a bug in the demo's template renderer: an `if` nested in another `if`'s branch took the inner tag into its condition and left an `endif` behind; the condition now stops at the first `%}` (regression test in `render-template-conditions.test.ts`).

**As built, A2d (2026-11-07):** "Clicked events" in the Mail guide's reading page with the CLI, API and MCP rows, `email.clicked` in the webhooks event list and its fields in Rules and filters, `sendmock_email_click` named in the skill's webhook workflow (and the plugin's copy), and binary tests of `sendmock email click` and the MCP tool (`email_commands.rs`, `mcp_stdio.rs`). A list from an MCP tool comes back as the tool's text, since structured content must be an object.

## A3. More SMS providers (SM-17)

**Why:** apps that send SMS through Infobip, Telnyx, Sinch, Africa's Talking or Amazon SNS cannot point their SDK at SendMock yet. SendMock already has the webhook formats for the first four (`infobip.dlr`, `telnyx.message`, `sinch.sms`, `africastalking.sms`, checked against their docs on 2026-11-05) but not their send APIs; SNS has neither. Five SMS providers ship today (Twilio, Twilio Verify, Vonage, Plivo, MessageBird).

**How:** each provider is a new definition beside the built-in ones (SM-16, [22](22-configurable-providers.md)), so nothing in the existing providers changes: its send operation (method, path, request format), the field mapping to SendMock's message parts, the success answer and the error answers in the provider's own shape, the message ID it makes, its status names, and the callback template its delivery reports use. The definitions live in `web/src/mocks/fixtures/more-sms-provider-fixtures.ts` (the existing file is long) and are exported to `crates/sendmock-ops/builtin/` like the others. Every request and answer is read from the provider's API reference first, as a fixture with its link and the date checked; each provider also passes its official Node SDK against the provider port in the SMS clients workflow, as the Twilio SDKs do.

| Part | Provider | Send API | Delivery reports | Node SDK |
|------|----------|----------|------------------|----------|
| A3a | Infobip | `POST /sms/2/text/advanced` | `infobip.dlr` to `notifyUrl` | `@infobip-api/sdk` |
| A3b | Telnyx | `POST /v2/messages` | `telnyx.message` to `webhook_url` | `telnyx` |
| A3c | Sinch | `POST /xms/v1/{service_plan_id}/batches` | `sinch.sms` to `callback_url` | `@sinch/sdk-core` |
| A3d | Africa's Talking | `POST /version1/messaging` | `africastalking.sms` to the callback set on the account (the provider's settings) | `africastalking` |
| A3e | Amazon SNS | `Publish` with `PhoneNumber` (the query API: form body, XML answer) | none: SNS logs delivery status to CloudWatch, which SendMock does not emulate | `@aws-sdk/client-sns` |

The exact paths, fields and shapes above are checked against the API references when each part starts and corrected here if they differ. A part that finds the provider's API cannot be described by a definition (for example SNS's request signing or XML answers) says so in its As built note and adds the smallest engine change it needs, with its own test.


**As built, A3a Infobip (2026-11-07):** the definition is in `web/src/mocks/fixtures/more-sms-provider-fixtures.ts`. Infobip's Node SDK (`@infobip-api/sdk` 0.3.2, read from its source) posts to `/sms/2/text/advanced` with `Authorization: App <key>`, and accepts an `http://` base URL, so it points at the provider port unchanged. The answer is Infobip's `bulkId` and `messages[]` with the `PENDING_ACCEPTED` status; a refusal is its `requestError.serviceException`. Delivery reports use `infobip.dlr`, which turns SendMock's status names into Infobip's itself, so the provider's status names keep SendMock's (`delivered`, `failed`, `undelivered`) and only gate which statuses are reported (final ones). Tests: `crates/sendmock-api/tests/more_sms_providers_api.rs` and `examples/sms/node-infobip` in the SMS clients workflow.

**As built, A3b Telnyx (2026-11-07):** Telnyx's Node SDK (`telnyx` 7.30.0, read from its source) posts to `/messages` under `https://api.telnyx.com/v2` and takes a `baseURL`, so it reaches `/v2/messages` on the provider port. The answer is Telnyx's `data` message object with the recipient `queued`; a refusal is its `errors` list (`10004`, missing required parameter, 422). The `telnyx.message` template sent `message.received` for every event, which is wrong for an outbound status; it now sends `message.received` for inbound messages and `message.sent` then `message.finalized` for status updates, with Telnyx's status names (`sent`, `delivered`, `sending_failed`, `delivery_failed`) on the recipient. Webhook signing (Ed25519 with the account's key) is not emulated. Tests: `more_sms_providers_api.rs` and `examples/sms/node-telnyx`.

**As built, A3c Sinch (2026-11-07):** Sinch's Node SDK (`@sinch/sdk-core` 1.8.0) calls the SMS API with a Bearer token and no OAuth when it is given a service plan ID and an API token, at `/xms/v1/{service_plan_id}/batches`; `sms.setHostname` points it at the provider port. The answer is Sinch's `mt_text` batch, a refusal its `code` and `text`. `sinch.sms` already wrote inbound messages and recipient delivery reports, so the provider keeps SendMock's status names. Sinch sends reports only when the batch asks for them (`delivery_report`); SendMock sends them whenever a `callback_url` is given. Tests: `more_sms_providers_api.rs` and `examples/sms/node-sinch`.

**As built, A3d Africa's Talking (2026-11-07):** Africa's Talking's Node SDK (`africastalking` 0.8.4) posts a form to `/version1/messaging` with the `apikey` header and only accepts a 201; it has no base URL option, so the example adds a request interceptor to the SDK's own axios that sends its calls to the provider port. The answer is `SMSMessageData` with the recipient's `statusCode` 101, a refusal is plain text. Its delivery reports go to a callback set on the account, so the provider sends none itself; a webhook rule with `africastalking.sms` does. While writing the refusals, `error.reason` turned out to be empty for a failed required-field rule (it carries only a provider's own message), so each new provider's refusal now names its own field (Infobip `Message text is missing`, Telnyx `The 'text' parameter is required.`, Sinch `Field 'body' is required`, Africa's Talking `missing required form field 'message'`) and the tests check the text. Tests: `more_sms_providers_api.rs` and `examples/sms/node-africastalking`. The Advanced guide's walkthrough for adding an SMS provider used Africa's Talking as its example of a vendor SendMock does not ship; it now adds Clickatell (`POST /messages` on `platform.clickatell.com`, told apart from MessageBird's same path by its host). Termii was tried first and refused, since its real path starts with `/api/`, which is SendMock's own.

**As built, A3e Amazon SNS (2026-11-07):** the AWS SDK's SNS client (`@aws-sdk/client-sns` 3.1164.0) uses the Query protocol: a form posted to `/` with `Action=Publish`, answered in XML. A definition describes that (form request, `PublishResponse` and `ErrorResponse` bodies with `Content-Type: text/xml`); two engine changes were needed. SNS has no sender field, and the engine required one: a provider whose field mapping has no `from` and no messaging service now stores its messages from the provider's name (`send_operation_kind.rs`), while providers that map a sender still require it. And `/providers/<key>/` with nothing after it fell through to the web UI, since a catch-all route takes no empty path; `provider_routes.rs` now routes a provider's root. SNS logs delivery status to CloudWatch, so the provider has no callback. Tests: `more_sms_providers_api.rs` and `examples/sms/node-sns`; SM-17.6 is proven by `message-providers.spec.ts` (the five listed as built-in) and `sms-clients-workflow.test.ts` (the providers page names each send API).

**Also found while building A3:** the CI run of A3a failed SM-16.3 because the demo's live traffic toasts stack over the last provider row's buttons, now that the list is longer; that test hides the toaster. And `otp_answers_the_newest_code_per_recipient_and_channel` failed about 3 times in 10: two SMS stored in the same millisecond got random ULIDs, so "the newest" (and any list in id order) could swap them. `SystemIdGenerator` now uses the `ulid` crate's monotonic generator, with a test that 10,000 ids in a row strictly increase.

## A4. Vonage Verify v2 (VF-05)

**Why:** Twilio Verify is the only one-time-code API SendMock answers (VF-01 to VF-04). Vonage Verify v2 is the other common one; an app using it cannot run its login flow against SendMock today. Other providers' verify APIs (Sinch Verification, Infobip 2FA, Plivo Verify) follow as later parts once this one shows the pattern.

**What Vonage sends and answers,** read from the Vonage Node SDK's source and its test data (`@vonage/verify2` 1.22.1, 2026-11-07), which builds every URL from a configurable `apiHost`:

| Request | Answer |
|---------|--------|
| `POST /v2/verify` with `brand`, `workflow` (`[{channel: "sms", to}]`, also `email`, `whatsapp`, `voice`), optional `code_length`, `code`, `locale`, `channel_timeout`, `callback_url` | 202 `{ request_id }` |
| `POST /v2/verify/{request_id}` with `code` | 200 `{ request_id, status: "completed" }` (the SDK's `checkCode` returns this status); a wrong code 400 problem `Invalid Code` |
| `DELETE /v2/verify/{request_id}` | 204, the request cancelled |
| a finished, cancelled or unknown request | 404 problem `Not Found`, "Request <id> was not found or it has been verified already." |

Errors are problem details (`title`, `type`, `detail`, `instance`), as the SDK's data sets show.

**How:** like Twilio Verify, a stateful API stays in code as an adapter (`vonage_verify_api.rs` beside `twilio_verify_api.rs`, [22](22-configurable-providers.md)) over the same verify domain, so a Vonage verification is an ordinary SendMock verification: listed in Verify, its code delivered as an SMS (or email, or WhatsApp) into SendMock, readable by `GET /api/v1/otp`, and firing the same `verify.*` events. Vonage has no verify service the way Twilio does, only a `brand` per request, so SendMock keeps one verify service per brand, made on first use and named after it, with `code_length` (default 4) and the workflow's channel taken from the request. A wrong code counts toward the service's attempt limit; past it, the request ends and later checks answer 404, as Vonage's do. The provider is built in as `vonage_verify`, a sibling of the existing `vonage` SMS provider, and the Vonage Node SDK's `Verify2` client runs a login against it in the SMS clients workflow.

**Not in this part:** `next_workflow`, silent authentication and templates; the status `callback_url` events; Vonage's legacy Verify v1 (`/verify/json`).

**As built, A4 (2026-11-07):** `vonage_verify_api.rs` answers the three requests over the verify domain, tried after Twilio Verify in the provider runtime, and the `vonage_verify` definition lists it with Basic credentials (`api_key`, `api_secret`), which Verify v2 accepts beside the SDK's JWT; the JWT itself is not checked. Reading the SDK showed the check answers `completed`, not `complete` as first written here, so the table and VF-05.2 say `completed` (the SDK's `checkCode` returns that status, and an app compares against it). Vonage's phone numbers have no `+`; SendMock adds it, so the code SMS and the Verify list show E.164. The `request_id` is the verification's SID (`VE...`) rather than a UUID, so one id works in both APIs. The captured code SMS still carries `twilio_verify` as its API, since the verify domain sends it for either API. Tests: `vonage_verify_api.rs` (VF-05.1 to VF-05.3) and `examples/sms/node-vonage-verify` with `@vonage/verify2` 1.22.1 (VF-05.4), which generates an RSA key for the SDK's JWT, completes one login and cancels another.

## A5. Projects: multi-project inboxes (PL-10)

**Why:** a team often shares one SendMock (a dev server, a CI runner, a Docker host). Today every app's mail, SMS and codes land in one list, so each developer filters by recipient or subject and a test reading "the latest code" can read another app's. Separate instances work but need more ports and more configuration.

**How others do it** (read 2026-11-07): smtp4dev keeps several mailboxes in one server, chosen by rules on the recipient, with a default mailbox for the rest and a mailbox picker in its UI ([its configuration doc](https://github.com/rnwood/smtp4dev/blob/master/docs/Configuration.md)). Mailtrap's sandbox groups inboxes into projects, and each inbox has its own SMTP credentials, so the username picks the inbox ([its sandbox API](https://docs.mailtrap.io/developers/email-sandbox/sandboxes-inboxes)). Mailpit and MailHog have one mailbox. SendMock follows Mailtrap's credentials model, since apps already set an SMTP username, plus a header and a URL prefix for HTTP APIs, which have no username of their own.

**What a project is:** a name for captured traffic inside one instance. A project has a key (lowercase letters, digits and dashes, up to 40 characters) and a display name. `default` always exists and holds everything not sent to another project; it cannot be deleted.

| Belongs to a project | Shared by every project |
|---|---|
| emails (with their attachments, timeline, opens, clicks and responses), SMS messages and threads, verifications | providers, templates, webhook endpoints, rules and variables, numbers, outcome rules, payments, HTTP bins, settings |

Projects separate traffic; they do not secure it. Anyone who can open SendMock can pick any project or "All projects", as in smtp4dev. Access control stays what it is today ([PL-06](acceptance/04-catcher-platform.md#pl-06-security-defaults)).

**How traffic picks its project:**

| Way in | Picked by | Unknown key |
|---|---|---|
| SMTP | the AUTH username, when it is a project's key (any password under `accept-any`) | stored in `default`, as without AUTH; apps send all kinds of usernames, and refusing would break mail that works today |
| REST send APIs (`/api/v1/send`, `/api/v1/sms`, inbound) | the `X-SendMock-Project` header | 404 `project_not_found` |
| provider APIs (Twilio, Vonage, SendGrid and the rest, on the provider port or under `/providers/<key>`) | the `X-SendMock-Project` header, or the URL prefix `/projects/<project>/` before the provider's path, for SDKs that take a base URL but no extra header | 404 in the provider's own error shape when it has one for a missing resource, else SendMock's |

**How reading works:** every list and lookup of captured traffic (emails, SMS, threads, verifications, `GET /otp`, `/links`, the `/wait/*` helpers, `GET /events/recent` and the realtime stream) takes an optional `project` (query parameter, `--project` in the CLI, a `project` argument in MCP). Without it they read every project, as today, so a single-project instance sees no change. Events carry `project` in their data, so a webhook rule can filter on it.

**Managing projects:** Settings > Projects lists them with their key, their message counts and a "Connect" block (the SMTP username and the header or URL prefix to use), and creates, renames and deletes them. Deleting a project deletes its traffic. REST `GET/POST /api/v1/projects`, `PATCH/DELETE /api/v1/projects/{projectKey}`, CLI `sendmock projects list|create|update|delete`, MCP `sendmock_project_*`, all from operations in `sendmock-ops`. The seed file has a `[[projects]]` table, and reset keeps projects like other configuration.

**In the UI:** a project switcher in the top bar ("All projects", then each project) kept in the URL (`?project=`), which filters Mail, SMS and Verify and the live toasts. It shows only when a project other than `default` exists, so a single-project instance looks as it does today.

**Parts:** A5a the store, operations, REST, CLI and MCP, with SMTP and the header; A5b the provider URL prefix; A5c the UI (mock first, then live) and docs.

**As built, A5a and A5b (2026-11-07):** projects live in their own table (migration 0035), and emails, SMS and verifications gained a `project_key` column (`default` for everything stored before). The request's client and project travel together as `RequestScope` in the operation context; the REST router and the provider routes set it from `X-SendMock-Project` (allowed in CORS) or, on provider routes, from a leading `/projects/<key>/`, which is stripped before the provider sees the path, so `http://127.0.0.1:8026/projects/shop` (provider port) or `http://127.0.0.1:8025/providers/twilio/projects/shop` (main port) is a project's base URL. An unknown project on a provider route answers SendMock's own `404 project_not_found`, not the provider's not-found shape the table above planned: the project is resolved before any provider is matched, and a provider's not-found means a missing resource of its own, which would mislead. `/projects/` joins `/api/` and `/providers/` as paths a provider definition may not use. **Not in this part:** per-project settings, retention or webhook endpoints; per-project credentials that SendMock checks; routing by recipient rules (smtp4dev's model), which tag rules and inbound routes already cover for filtering.

## A6. POP3 read access (EM-21)

**Why:** some apps and test suites read a mailbox over POP3: an inbound-mail feature that polls a support address, a QA script built on Python's `poplib` or PHP's IMAP extension, a desktop mail client pointed at a test server. Today they cannot read what SendMock caught without changing to its API.

**How others do it** (Mailpit's `internal/pop3` source, read 2026-11-07): Mailpit's POP3 server is off until credentials are configured, since it hands out every message. It serves the newest 100 messages, with USER and PASS, STAT, LIST, UIDL (the message id), RETR, TOP, NOOP, DELE, RSET, QUIT and CAPA (RFC 1939 and 2449); DELE only marks, and the marked messages are deleted when the client sends QUIT, so a dropped connection deletes nothing. A line over RFC 1939's limit is refused, an idle session closes after 10 minutes, and five failed logins close the connection. TLS is implicit, with a certificate given on the command line.

**How:** a new `sendmock-pop3` crate with the protocol (a session state machine over a `Pop3Mailbox` trait, testable without a socket) and the listener, wired by the binary like the SMTP one; the mailbox is implemented in `sendmock-ops` over the email repository, so deletes go through the same path as the API and fire `email.deleted`.

- **Off by default:** `--pop3-addr` (`SENDMOCK_POP3_ADDR`) turns it on, bound to `127.0.0.1` unless told otherwise (Docker publishes it only when asked).
- **Login:** `--pop3-auth` takes `accept-any` (the default, as for SMTP on a local machine) or `file:<path>` with the same `user:password` lines as `--smtp-auth`.
- **Mailbox:** the username picks it, as SMTP's does: a project's key reads that project's emails ([A5](#a5-projects-multi-project-inboxes-pl-10)), any other username reads `default`. The newest 100 emails of that project, numbered oldest first as POP3 clients expect; the list is fixed at login, as RFC 1939 asks.
- **Messages:** RETR answers the stored raw message with dot-stuffing; TOP the headers and the first n body lines; UIDL the email id, which never changes, so clients that remember downloaded ids work across sessions.
- **Seen in the product:** `/api/v1/info` lists the POP3 address, Settings > Connection shows the host, port and how to log in, and the CLI's `serve --help` and the configuration docs describe the options.

**As built (2026-11-07):** A6a is the `sendmock-pop3` crate (`Pop3Session` over a `Pop3Mailbox` trait, tested with a fake, and the listener with a 512-byte line limit and a 10-minute idle timeout) and `sendmock-ops/src/pop3_mailbox.rs`; transport crates may not depend on each other, so the `user:password` file reader moved from `sendmock-smtp` to `sendmock-core` for both. A6b wires it into the binary: `--pop3-addr` and `--pop3-auth` (flags, environment and `sendmock.toml`), the listener started with the SMTP ones and stopped on shutdown, `pop3_addr` in the ready line, `pop3_address` in `/api/v1/info` (null when off; the types, the mock and the spec changed together), and a POP3 card in Settings > Connection, shown only while POP3 is on, so mock mode is unchanged. Tests: `pop3_session_tests.rs`, `pop3_listener.rs` (over a socket with SendMock's operations), `pop3_config.rs`, the live `pop3-connection.spec.ts` (the live suite now starts the binary with `--pop3-addr 127.0.0.1:0`), and `examples/smtp/python-poplib/verify.py` in the SMTP clients workflow, which turns POP3 on for the job.

**Not in this part:** STLS and implicit TLS (SendMock runs on the developer's machine or a private network; TLS follows if asked), APOP and SASL logins, IMAP.

## A7. Push notifications (PN-01)

**Why:** apps send push notifications through Firebase Cloud Messaging, Expo and OneSignal as often as they send email or SMS: sign-in codes, order updates, chat messages. Today the HTTP catcher captures those calls as raw requests (HC-03): nothing shows the notification as the phone would, and a test cannot wait for "the push to this device" or make a token fail the way an expired one does.

**How it works:** push becomes its own area beside Mail and SMS, with the same model: the app calls the provider's real API on the provider port (or under `/providers/<key>/`), SendMock stores the notification and answers exactly as the provider does, fires `push.sent`, and shows it in **Push**.

- **Providers, in code like Twilio Verify** (their answers depend on stored state and their requests are nested JSON): FCM HTTP v1 (`POST /v1/projects/{project_id}/messages:send`, answering `{ "name": "projects/<id>/messages/<id>" }`), Expo (`POST /--/api/v2/push/send`, one message or a list, answering tickets; `POST /--/api/v2/push/getReceipts`), OneSignal (`POST /notifications`). Each adapter is read from the provider's official SDK and its tests before it is written: `firebase-admin`, `expo-server-sdk`, `@onesignal/node-onesignal`. APNs needs HTTP/2 with TLS, which the provider port does not serve, and follows later.
- **What is stored:** the provider, the device token (or Expo push token, or OneSignal player or alias), the title, body, image, sound, badge and data, the platform the message targets when it says, the request as sent, the answer, and the project ([A5](#a5-projects-multi-project-inboxes-pl-10)) from the header or URL prefix.
- **Failures on purpose:** magic device tokens like SMS's magic numbers: a token containing `unregistered` answers each provider's "not registered" error (FCM `UNREGISTERED` 404, Expo `DeviceNotRegistered`, OneSignal `invalid_player_ids`), `invalid` its invalid-token error, and `throttled` its rate limit (FCM `QUOTA_EXCEEDED` 429).
- **Reading and waiting:** `GET /api/v1/push` (with `project`, `token`, `provider`), `GET /api/v1/push/{pushId}`, `DELETE`, and `GET /api/v1/wait/push`, with CLI and MCP commands from the same operations. `push.sent` and `push.failed` events reach webhook rules, which filter on `token`, `title` and `project`.
- **The Push screen:** a list of notifications and a detail with a phone-style preview (lock screen card for iOS and Android), the data payload, the request and the answer; filters by provider, token and status. Built on the mock first, as every screen is.

**Parts:** A7a the store, operations and FCM; A7b Expo and OneSignal; A7c the Push screen (mock, then live); A7d magic tokens, events and the SDK examples in CI.

**As built, A7a (2026-11-07):** a `push_notifications` table (migration 0036, pruned with the SMS count and cleared by reset and by deleting a project), `PushNotificationRepository`, and the `push` operations: list (`project`, `device_token`, `provider`, `status`), one, delete one, delete all and `GET /api/v1/wait/push`, with `sendmock push list|show|delete|clear|wait` and `sendmock_push_*` tools. The filter is `device_token`, not `token`, since `--token` is the CLI's global API token flag. FCM HTTP v1 is answered in code before the provider definitions (`push/fcm_send_api.rs`): the message name `projects/<id>/messages/0:<micros>%<hex>`, `validate_only` answered with `fake_message_id` and not stored, a message without a token, topic or condition refused with `INVALID_ARGUMENT` and an `FcmError` detail; topics and conditions are stored as `topic:<name>` and `condition:<expression>`. The title, body and image come from the cross-platform notification, then the Android, APNs and Web Push blocks, and the platform from which block the message carries. To free a line in `OperationContext::new` for the repository, the SMTP session and API request repositories became `logs: LogStores`. `firebase-admin` 14.5 hard-codes `https://fcm.googleapis.com` (HTTP/2 unless its legacy transport is on), so its CI example will redirect its requests to the provider port, as the PayPal example does (A7d). Tests: `push_fcm_api.rs` and the contract samples.

**Design, A7b (read from `expo-server-sdk` 8.0 and `@onesignal/node-onesignal` 5.20, 2026-11-07):**

- **Expo:** the SDK posts an array of messages to `${EXPO_BASE_URL}/--/api/v2/push/send` (`https://exp.host` by default, so `EXPO_BASE_URL=http://127.0.0.1:8026` points it at SendMock) and gzips any body over 1 KB with `Content-Encoding: gzip`, so the provider routes now inflate gzip request bodies (the one new dependency, `flate2` on its pure-Rust backend, also lets any other provider SDK compress). Each message's `to` is one token or a list; every recipient is a ticket, in order, and a stored notification. The answer is `{ "data": [tickets] }`, a ticket being `{ "status": "ok", "id": "<uuid>" }`; a single message object with one recipient is answered with one ticket object, as Expo does. A message without `to` refuses the whole request with `400 { "errors": [{ "code": "VALIDATION_ERROR", "message": ..., "isTransient": false }] }`, the shape the SDK turns into its error. `getReceipts` takes `{ "ids": [...] }` and answers `{ "data": { "<id>": { "status": "ok" } } }` for the ids SendMock issued (failed ones carry the ticket's error, A7d); unknown ids are left out, as Expo leaves out receipts it does not have. Title, body, `richContent.image` and `data` are read; `subtitle`, `sound`, `badge` and the rest stay in the stored request.
- **OneSignal:** the SDK posts the notification to `${baseServer}/notifications` (`https://api.onesignal.com`; `createConfiguration({ baseServer: new ServerConfiguration("http://127.0.0.1:8026", {}) })` points it at SendMock). The recipients are `include_subscription_ids`, `include_player_ids` (the older name) and `include_aliases` (each alias label with its ids, stored as `<label>:<id>`), each a stored notification sharing one notification id; a segment send (`included_segments`) is stored once as `segment:<names>`. The answer is `200 { "id": "<uuid>", "external_id": null }` (the request's `external_id` when it sent one). Title and body come from `headings` and `contents` (English first, else the first language), the image from `big_picture`, then `ios_attachments`, then `chrome_web_image`, the platform from `target_channel` or the `is_*` flags when only one is set. No recipients, or `contents` without a language when no `template_id` is given, answer `400 { "errors": ["..."] }` with OneSignal's messages.
- **Routes:** on the provider port at the real paths, or under `/providers/expo/` and `/providers/onesignal/` on the main port, with the project header or URL prefix as for every provider.

**As built, A7b (2026-11-07):** `push/expo_push_api.rs` and `push/onesignal_notifications_api.rs` beside the FCM adapter, chosen by `push_api.rs` (on the provider port each push provider is tried in turn; under `/providers/<key>/` only that one). Expo stores each recipient's message (not the whole batch) as its request and the ticket as its answer, so `getReceipts` reads the ticket back by its id. The provider routes inflate `Content-Encoding: gzip` bodies with `flate2` (pure Rust, refused past the 32 MB body limit), so the request log and every provider see the plain JSON. Tests: `push_expo_api.rs` (a gzipped batch included), `push_onesignal_api.rs` and the decoding unit tests in `sendmock-api`.

**Design, A7c (2026-11-07):** **Push** is a top-level sidebar item after SMS (`/push`, the guide at `push.md`), shown as Not available yet until the server serves `GET /api/v1/push` (UI-12). The screen follows Verify's: filter chips for the provider (All, FCM, Expo, OneSignal) and the status (Sent, Failed), a search on the device token (exact, as the API filters), a table (time, provider, device token, title, status) and a drawer kept in the URL (`?push=<id>`) with a phone preview (an iOS and an Android lock screen card with the app's title, body, image and time, chosen by the message's platform and switchable), the facts (provider, message id, token, project), the data payload as key and value rows, and the request and answer as JSON with copy buttons. Delete one from the drawer; Clear all under the filters asks first. The demo data gets a handful of FCM, Expo and OneSignal notifications (one failed) so the demo and the Deeper crawl show every part. The embedded UI is close to its 2 MB budget, so the screen reuses the Verify table, the sheet, the filter chips and `HttpBodyView` rather than adding components. The realtime refresh on `push.sent` comes with the events in A7d.

**As built, A7c (2026-11-07):** `web/src/features/push/` (page, list panel, table, drawer, phone preview, status badge, labels) over `use-push-queries.ts`; the sidebar item has the shortcut `g` then `u`, and the empty state's Connect hint gained a `push` area with the FCM, Expo and OneSignal base URLs. The demo data has four notifications (`push-fixtures.ts`). The guide page is `docs/wiki/push.md`, the Deeper page `website/lib/deeper/screens/push.ts`, and every screenshot was retaken since the sidebar changed. The live build is 2.00 MB with about 5 KB left under the 2 MB budget: the next UI change (A8) has to find room first. Tests: `push.spec.ts` (mock mode), `tests/live/push-screen.spec.ts` (an Expo push sent to the binary), the connect values unit test, and every-screen checks that now include `/push`.

**Design, A7d (read from `firebase-admin` 14.5's `messaging-errors-internal.js`, `expo-server-sdk` 8.0's types and `@onesignal/node-onesignal` 5.20's models, 2026-11-07):**

- **Magic device tokens:** a token (Expo push token, OneSignal subscription, player id or alias id) containing `unregistered`, `invalid` or `throttled`, in any case, fails the way that provider fails. The notification is still stored, as `failed` with the provider's error code as its reason and the error as its answer, so a test can assert on what the app was told.

  | Token has | FCM (whole request) | Expo (that recipient's ticket, request 200) | OneSignal |
  |---|---|---|---|
  | `unregistered` | `404 NOT_FOUND`, `FcmError` `UNREGISTERED` (the SDK's `messaging/registration-token-not-registered`) | `DeviceNotRegistered`, "`<token>` is not a registered push notification recipient" | listed under `errors.invalid_player_ids` (subscriptions, player ids) or `errors.invalid_aliases.<label>` (aliases), request 200 |
  | `invalid` | `400 INVALID_ARGUMENT`, `FcmError` `INVALID_ARGUMENT` (`messaging/invalid-argument`) | `DeviceNotRegistered`, "`<token>` is not a valid Expo push token" | as `unregistered` |
  | `throttled` | `429 RESOURCE_EXHAUSTED`, `FcmError` `QUOTA_EXCEEDED` (`messaging/message-rate-exceeded`) | `MessageRateExceeded` | the whole request `429 { "errors": ["API rate limit exceeded"] }` |

  A OneSignal send whose every recipient is refused answers `200 { "id": "", "errors": ["All included players are not subscribed"] }`, as OneSignal does. A failed Expo ticket has no id, so it has no receipt.
- **Events:** storing a notification publishes `push.sent`, or `push.failed` for a refused one, with the notification's `id`, `provider`, `device_token`, `title`, `status`, `error_reason` and `project`. Webhook rules listen to both (Push in the rule editor's events) and filter on the new fields `token`, `title` and `provider`, plus `body`, `status` and `project`, read from the stored notification. The Push screen refreshes on either event; neither raises a toast.
- **SDK examples in CI:** `examples/push/` has a Node app per provider run by the "Push SDKs" workflow against a release binary: `firebase-admin` (`messaging().send()` over HTTP/1.1, its `fcm.googleapis.com` requests sent to the provider port by wrapping Node's `https.request`, as the PayPal example wraps its client, and a credential that answers a fixed access token), `expo-server-sdk` (`EXPO_BASE_URL`, a batch large enough to be gzipped, then `getPushNotificationReceiptsAsync`) and `@onesignal/node-onesignal` (`baseServer`). Each sends a notification, waits for it with `GET /api/v1/wait/push`, sends to an `unregistered` token and checks the SDK reports the provider's error.

**As built, A7d (2026-11-08):** `push/magic_push_tokens.rs` reads the failure a token asks for; each adapter answers it in its own shape (FCM in `refuse_magic_token`, Expo per ticket in `issue_ticket`, OneSignal in `answer_recipients`) and stores the notification as failed with the provider's code (`UNREGISTERED`, `DeviceNotRegistered`, `invalid_player_ids`, ...) as its reason. `store_push_notification` publishes `push.sent` or `push.failed`; the rule subscriber reads a push event's stored notification (`build_push_rule_message`), and `token`, `title` and `provider` joined the filter fields (Rust `KNOWN_FIELDS`, the web rule builder's Push subject). The Push screen refreshes on both events. `examples/push/node/done-when.js` runs the three SDKs in the new "Push SDKs" workflow and from Release build; it passed locally against a debug build with Node 22 first. Tests: `push_failures_and_events.rs`, `magic_push_tokens.rs`'s unit test, `scripts/push-sdks-workflow.test.ts`, the rule fields and realtime unit tests.

**Not in this part:** APNs, Web Push (VAPID), topics and condition sends (FCM topics are stored as the target, with no fan-out), delivery receipts beyond Expo's `getReceipts`.

## A8. WhatsApp Business Cloud API (SM-18)

**Why:** most apps that send WhatsApp today call Meta's Cloud API directly (`graph.facebook.com`), not Twilio. SendMock answers WhatsApp only through Twilio's Messages API with `whatsapp:` addresses (SM-11), so those apps cannot point at SendMock: their sends, templates, media and the webhooks Meta sends back have nowhere to go.

**What Meta sends and answers,** read from Meta's Node SDK (`whatsapp` 0.0.5-Alpha, archived by Meta, its types and webhook handler) and the Cloud API reference, 2026-11-08:

| Request | Answer |
|---------|--------|
| `POST /{version}/{phone_number_id}/messages` with `messaging_product: "whatsapp"`, `to`, `type` and the type's object (`text`, `template`, `image`, `audio`, `video`, `document`, `sticker`, `location`, `contacts`, `interactive`, `reaction`) | 200 `{ messaging_product, contacts: [{ input, wa_id }], messages: [{ id: "wamid...." }] }`; a template send adds `message_status: "accepted"` |
| the same path with `{ messaging_product, status: "read", message_id }` | 200 `{ success: true }` |
| a request Meta refuses | Graph's error: `{ error: { message: "(#100) ...", type: "OAuthException", code, error_data: { messaging_product, details }, fbtrace_id } }` |
| `POST /{version}/{phone_number_id}/media` (multipart `file`, `type`, `messaging_product`) | `{ id }` |
| `GET /{version}/{media_id}` | `{ messaging_product, url, mime_type, sha256, file_size, id }`; `GET` on the `url` answers the bytes; `DELETE` answers `{ success: true }` |

Meta's webhooks go to the one callback URL of the app, as `{ object: "whatsapp_business_account", entry: [{ id, changes: [{ field: "messages", value: { messaging_product, metadata: { display_phone_number, phone_number_id }, contacts, messages | statuses } }] }] }`, signed with `X-Hub-Signature-256: sha256=<hex HMAC-SHA256 of the body with the app secret>`. Statuses are `sent`, `delivered`, `read` and `failed`, a failed one with `errors: [{ code, title, message, error_data: { details } }]`. Before Meta sends anything, it checks the URL with `GET ?hub.mode=subscribe&hub.verify_token=...&hub.challenge=...`, which the app answers with the challenge.

**How:** a stateful, nested-JSON API stays in code as an adapter, like Twilio and Vonage Verify ([22](22-configurable-providers.md)): `whatsapp_cloud_api.rs` beside them, listed by a built-in `whatsapp_cloud` provider definition (host `graph.facebook.com`) that holds its credentials: `access_token` (not checked, like the other providers' keys), `app_secret` (signs the webhooks), `phone_number` (the business number the messages are stored from, default `+15550783881`), `verify_token`, and `webhook_url` (Meta's callback URL). A Cloud API message is an ordinary SendMock message on the `whatsapp` channel with the API `whatsapp_cloud`, so it shows in SMS with WhatsApp styling, fires `sms.sent`, counts for OTP and links, and follows the delivery profile and the magic numbers (an `undelivered` or `failed` outcome becomes Meta's `failed` status with `131026`, "Message undeliverable"). The `phone_number_id` of the path is kept on the message.

- **Bodies:** each message type is stored with a readable body so the conversation needs no new UI: `text.body`; a template as `Template <name> (<language>)` and its body parameters on the next line; media as its caption (or `Photo`, `Video`, `Audio`, `Document <filename>`, `Sticker`) with the file attached; a location as its name, address and `<latitude>, <longitude>`; contacts as each name and phone; interactive as the body text and each button or list row title on its own line; a reaction as `Reacted <emoji>`. The request as sent is stored too.
- **Refusals:** `messaging_product` other than `whatsapp` (`(#100) Param messaging_product must be 'whatsapp'`), no `to`, an unknown `type`, or a type without its object or its required field (`(#100) The parameter text['body'] is required.`) answer 400 with Graph's error and store nothing; a template, media or reply id SendMock does not have is accepted, as Meta checks those later.
- **Webhooks:** with `webhook_url` set, each status of a Cloud API message (through the status callback queue, so it is retried and listed on the message) and each reply in a Cloud API conversation (through the reply webhook, in the new `whatsapp_cloud` format) is posted there in Meta's envelope, signed with `app_secret`. `POST /api/v1/sms/providers/whatsapp_cloud/verify-webhook` sends Meta's subscribe check to the URL and answers whether it echoed the challenge, and Settings for the provider shows it as **Verify callback URL**.
- **Read receipts:** marking an inbound message read (`status: "read"`) sets it read, as opening it in the UI does.

**Parts:** A8a the send API, read receipts, Graph errors and the definition, with an example in CI; A8b media upload, lookup, download and delete, and sends by media id; A8c the webhooks (statuses, replies, signature, the verification check) and the docs.

**Not in this part:** template management (`/message_templates`), the 24-hour customer service window (`131047`), business profile and phone number management, flows, catalogues and payments, and the on-premises API. Meta's Node SDK is archived and only speaks HTTPS to a fixed host, so the CI example calls the API with `fetch`, as most apps do.

**As built, A8a (2026-11-08):** `whatsapp_cloud_api.rs` (routing, credentials, sends), `whatsapp_cloud_content.rs` (each message type read into a body and its media), `whatsapp_graph_errors.rs` and `whatsapp_read_receipts.rs` in `sendmock-ops/src/providers/`, tried after Vonage Verify in the provider runtime; the definition is `web/src/mocks/fixtures/whatsapp-cloud-provider-fixture.ts`, exported with the others. Messages are stored from `whatsapp:<phone_number>` to `whatsapp:+<to>` with the path's `phone_number_id` in the message's metadata and the `wamid.` as its provider id. A number the outcome rules refuse answers `400` with code `131026` at once, as Meta does for a recipient it cannot reach, rather than a later `failed` status; a media link that cannot be downloaded answers `131053`. A read receipt finds the message by its `wamid` and marks its whole conversation read, as Meta marks earlier messages read too. Tests: `whatsapp_cloud_api.rs` (SM-18.1, SM-18.2), the content unit tests, `message-providers.spec.ts` (SM-18.5) and `examples/sms/node-whatsapp-cloud` in the SMS clients workflow, which passed locally against a debug build first.

**As built, A8b (2026-11-08):** uploads live in a `whatsapp_media` table (migration 0037, pruned with the SMS limit, cleared by reset and by deleting a project), reached as `sms_repository.whatsapp_media()` so the operation context gains no field. `whatsapp_cloud_paths.rs` tells the messages, upload and media object paths apart; `whatsapp_cloud_media.rs` answers them and `whatsapp_cloud_send.rs` now holds the send, attaching media named by id (unknown ids are skipped, as planned). Provider answers are text, so the download link (`/whatsapp_business/attachments/?mid=<id>`, on the address the app called) is answered by `find_whatsapp_media_download` in the provider route before the provider runtime and is not written to the request log. ## A9. System tray app (DS-08)

**Why:** most developers run SendMock on their own machine for the whole working day. Today that means a terminal window kept open, or a service set up by hand, and nothing says mail arrived until the browser tab is looked at.

**How others do it** (read 2026-11-08): Ollama's menu bar and tray app starts its server in the background, shows that it runs and offers "View logs" and "Quit"; Docker Desktop's whale menu shows the engine's state, opens the dashboard and quits. Mailpit, MailHog and smtp4dev have no tray app (smtp4dev's old Windows tray was dropped). In Rust, the Tauri team's `tray-icon` (0.26, MIT or Apache-2.0, with `muda` menus and `tao`'s event loop) is the common choice: the macOS menu bar, the Windows notification area, and on Linux an AppIndicator over GTK 3.

**How:** a new crate and binary, `sendmock-tray`, so `sendmock` itself gains no GUI dependency and keeps its size and Docker image. The crate has two halves:

- **A library with no GUI** (tested on every OS like the rest): `TrayController` decides what the menu shows and does, over a `SendmockConnection` trait (health and `GET /api/v1/stats` with a few lines of HTTP/1.1 to the local address, no HTTP client crate) and a `ServerProcess` trait (start `sendmock serve` as a child, stop it). Tests use fakes for both.
- **The tray shell** behind a `gui` feature (the binary has `required-features = ["gui"]`), so workspace builds, clippy and `cargo publish --dry-run` need no GTK. A "Tray app" workflow builds and tests it with the feature on Linux (with `libgtk-3-dev`, `libxdo-dev` and `libayatana-appindicator3-dev`), macOS and Windows.

**Behaviour:**

- On start it looks for SendMock at `--url` (`SENDMOCK_URL`, default `http://127.0.0.1:8025`). If one answers, it uses it; if not, it starts `sendmock serve` (the `sendmock` beside the tray binary, else on `PATH`, else `--sendmock <path>`).
- The menu: the status ("Running at http://127.0.0.1:8025", "Starting...", "Not running"), the unread counts ("3 unread emails, 1 unread SMS", from the stats the Overview uses), **Open SendMock** (the web UI in the default browser), **Start SendMock** or **Stop SendMock** (stop only for a server the tray started; one it found keeps running), and **Quit**, which stops the server it started. The tooltip repeats the status, and on macOS the menu bar shows the unread total next to the icon.
- It polls every 2 seconds. The icon is drawn in code (an envelope in SendMock's mint), so no image decoder is needed.

**Install:** `cargo install sendmock-tray --features gui` (the crate is published with the others), with the GTK and AppIndicator libraries on Linux; the docs give each OS's steps.

**Not in this part:** a native notification per message, starting at login, signed installers and a macOS `.app` bundle (they need the owner's signing identities, so they follow the release runbook), and Linux packages.

**As built, A9 (2026-11-08):** `crates/sendmock-tray`: the library (`TrayController`, `LocalHttpConnection` reading `GET /api/v1/stats` over plain HTTP/1.1, `ChildServerProcess` running `sendmock serve --http-addr <the URL's address>`, `TrayOptions`, the icon drawn in `tray_icon_image.rs`, and `open_in_browser` with `open`, `cmd /C start` or `xdg-open`) and the shell (`main.rs`, `tray_menu.rs`) on `tray-icon` 0.26 and `tao` 0.37, with the macOS app set to an accessory so it has no Dock icon. The crate sits in the application layer of `scripts/rust-crate-layers.ts` and, like `sendmock`, is not a workspace dependency. A server the tray starts keeps running if the tray is killed rather than quit, as Ollama's does. Before CI, the GUI binary was built on macOS and started against a free port: it found no server, started `sendmock serve` beside itself, and the API answered. Tests: the library's unit tests (DS-08.1 to DS-08.3, with fake connections and processes, a one-request local server and a missing binary), the "Tray app" workflow (DS-08.4) and `scripts/tray-app-workflow.test.ts` (DS-08.4, DS-08.5).

## A12. Monitoring: Prometheus metrics, OpenTelemetry and log files (PL-11, PL-12, PL-13)

**Why (owner request, 2026-11-08):** SendMock that a team runs in Docker, Kubernetes or CI is a service like any other, and the people running it want it on the dashboards and log searches they already have. Today it has a health check (`sendmock health`, `GET /api/v1/health`, the Docker HEALTHCHECK and the Helm probes), JSON logs on stdout (`SENDMOCK_LOG_FORMAT=json`) and the Overview's counts (`GET /api/v1/stats`), but nothing a monitoring system collects by itself.

**How others do it** (read 2026-11-08):

- **Mailpit** ([Prometheus metrics](https://mailpit.axllent.org/docs/configuration/prometheus/)): `--enable-prometheus` (`MP_ENABLE_PROMETHEUS`), off by default; `true` serves `/metrics` on the web UI port behind the UI's TLS and login, an address runs a separate server without either. Eleven metrics: stored and unread messages (gauges), messages deleted and SMTP messages accepted, rejected, ignored and their bytes (counters), database size, uptime and memory (gauges), and messages per tag.
- **Prometheus** ([writing exporters](https://prometheus.io/docs/instrumenting/writing_exporters/), [OpenMetrics](https://github.com/prometheus/OpenMetrics/blob/main/specification/OpenMetrics.md)): one prefix per application, the unit in the name (`_bytes`, `_seconds`), counters end in `_total` and only rise, the `process_` prefix is for process facts with their standard meaning, and labels never hold unbounded values.
- **OpenTelemetry** ([environment variables](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/)): the vendor-neutral standard for logs, metrics and traces. Every collector and most vendors (Grafana Alloy, the OpenTelemetry Collector, Datadog, New Relic, Honeycomb, Elastic, SigNoz, Dynatrace) accept OTLP, and a program is pointed at one with the standard variables `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_SERVICE_NAME`, so nothing SendMock-specific is needed.
- **Logs** ([twelve-factor](https://12factor.net/logs)): a service writes one event per line to stdout and lets the platform collect it (Docker's logging drivers, the Kubernetes node agent, the systemd journal, Fluent Bit, Vector, Loki's agents). That already holds for SendMock; native installs without such a platform want a log file that rotates.

**The three parts:**

**A12a Prometheus metrics (PL-11).**

- **On and off:** `--metrics` (`SENDMOCK_METRICS`, `metrics = true` in `sendmock.toml`), off by default as in Mailpit, so a public port does not answer a path scanners look for. When on, `GET /metrics` on the HTTP port answers the Prometheus text format (`text/plain; version=0.0.4`), behind the same `--ui-auth` or `--api-token` as the API (Prometheus scrapes with `basic_auth` or `authorization`). A separate metrics listener is not in this part.
- **One operation, every surface:** `getMetrics` (`GET /api/v1/metrics`, `sendmock metrics`, the MCP `sendmock_stats` tool with `view: metrics`) answers the metric families as JSON and is always available, as the Overview's stats are; `/metrics` renders that same answer as text in the transport layer (a `PrometheusTextRenderer`), so the numbers cannot differ. The text format is written by hand: it is a few lines per family, and no client library is needed.
- **Gauges, what is stored now** (read with the Overview's count queries on read connections, never the writer queue): `sendmock_emails`, `sendmock_emails_unread`, `sendmock_sms`, `sendmock_sms_unread`, `sendmock_verifications_pending`, `sendmock_http_requests`, `sendmock_push_notifications`, `sendmock_payments`, `sendmock_webhook_deliveries_queued` (waiting for a retry) and `sendmock_database_size_bytes`. They fall after a delete, a reset or retention pruning.
- **Counters, since the process started:** `sendmock_events_total{type="email.received"}`, one series per event type, counted inside `EventBus::publish` (exact; a subscriber can fall behind and miss events), and `sendmock_smtp_rejected_total`, counted where the SMTP session log already records a refused message.
- **Process:** `sendmock_build_info{version}` (always 1), `process_start_time_seconds`, and on Linux `process_resident_memory_bytes` from `/proc/self/statm` (left out on macOS and Windows rather than adding a dependency).
- **Safety:** labels hold only event type names and the version: never an address, a number, a project name a user typed, message content or a secret.
- **UI:** Settings > Connection shows a Metrics card while metrics is on, with the scrape URL and a copyable `prometheus.yml` job (with its `basic_auth` or `authorization` lines when auth is set); `/api/v1/info` gets `metrics_path` (null when off), as POP3 did.
- **Deployments:** the Helm chart's `metrics.enabled` sets `SENDMOCK_METRICS` and adds the `prometheus.io/scrape`, `port` and `path` pod annotations, and `metrics.serviceMonitor.enabled` renders a ServiceMonitor for the Prometheus Operator. `examples/monitoring/` holds a Docker Compose file with SendMock and Prometheus, and a CI job sends an email and finds `sendmock_events_total{type="email.received"}` at 1 through Prometheus's query API.

**A12b OpenTelemetry export (PL-12).**

- **On and off:** off until `OTEL_EXPORTER_OTLP_ENDPOINT` (or a per-signal endpoint) is set, as every OpenTelemetry SDK does; `OTEL_SDK_DISABLED=true` turns it off again. The standard variables are read as the specification says (`OTEL_SERVICE_NAME`, default `sendmock`; `OTEL_RESOURCE_ATTRIBUTES`; `OTEL_EXPORTER_OTLP_HEADERS` for a vendor's API key, masked wherever SendMock shows its settings). OTLP over HTTP with protobuf (`http/protobuf`), the specification's default, through the `reqwest` client SendMock already has; gRPC is not offered, since it would add `tonic` and its stack for no extra reach (every collector takes HTTP).
- **Logs:** every log line goes to the collector as an OpenTelemetry log record with its level, target and fields, through the `tracing` bridge, as well as to stdout.
- **Metrics:** the same families as `/metrics` (A12a), sent every 60 seconds (`OTEL_METRIC_EXPORT_INTERVAL`), so a team on OpenTelemetry needs no Prometheus.
- **Traces:** one span per SMTP session, REST and provider API request, webhook delivery attempt, status callback and outgoing release, with the operation id and outcome as attributes (never message content, addresses or secrets); an incoming `traceparent` header continues the caller's trace, so a test can follow its request into SendMock. Sampling follows `OTEL_TRACES_SAMPLER` (default: always on, since SendMock's traffic is test traffic).
- **Cost:** the crates (`opentelemetry`, `opentelemetry_sdk`, `opentelemetry-otlp` without default features, `opentelemetry-appender-tracing`, `tracing-opentelemetry`) are measured before merging against the 20 MB binary and idle memory budgets of [09](09-distribution.md#performance-budget-checked-in-ci-on-linux-x64); if they do not fit, OpenTelemetry becomes a cargo feature built into the Docker image and an `-otel` binary only, and the plan records the numbers either way. Nothing runs, and no memory is taken, while it is off.
- **Proof:** a CI job runs the OpenTelemetry Collector with its file exporter next to SendMock, sends an email and an SMS and a webhook, and finds the log records, the metric points and the spans (with a caller's `traceparent` kept) in the collector's output.

**A12c Log files and readiness (PL-13).**

- **Log files:** `--log-file <path>` (`SENDMOCK_LOG_FILE`, `log_file` in `sendmock.toml`) also writes the logs to a file in the chosen format, rotated daily or at `--log-file-max-size` (default 10 MB), keeping `--log-file-keep` files (default 7), for native installs without a log collector; the tray app starts its server with a log file in its data folder, since it has no terminal to show stdout. Stdout stays as it is.
- **JSON log fields:** `SENDMOCK_LOG_FORMAT=json` lines keep their shape and add `trace_id` and `span_id` when a span is active (A12b), so a log search can jump to the trace. The fields are listed in the docs, so a Loki, Elastic or Datadog pipeline can be written against them.
- **Readiness:** `GET /api/v1/health/ready` (and `sendmock health --ready`) answers 200 once the listeners are bound and the database answers a read, and 503 while starting and once shutdown has begun, so a load balancer or Kubernetes stops sending traffic before SendMock stops. `GET /api/v1/health` stays the liveness check. The Helm chart's readiness probe moves to the new path; the Docker HEALTHCHECK stays on liveness.
- **Docs:** a new Monitoring page in the guide covers the health and readiness checks, logs (stdout, JSON fields, the log file, and collecting them with Docker's logging drivers, the systemd journal, Fluent Bit, Vector and Grafana Alloy), every Prometheus metric with its type and meaning, the Prometheus and OpenTelemetry setups for Docker Compose and Helm, and a starter Grafana dashboard (`examples/monitoring/grafana-dashboard.json`). The configuration reference and the skill list every option.

**Order:** A12a, then A12c (small and independent), then A12b (the largest, and it reuses A12a's families and A12c's log fields).

**Not in this part:** a separate metrics listener, StatsD and Graphite (the OpenTelemetry Collector translates OTLP to both), OTLP over gRPC, histograms of SMTP and API latency (traces carry durations; added if asked), per-project metric labels, and alerting rules (left to each team; the docs give two examples).

## A13. Accounts, login and roles: Admin, Developer, Viewer (PL-14, PL-15)

**Why (owner request, 2026-11-08, for later):** a team that shares one SendMock (in Docker, on Kubernetes, or a CI box everyone can open) today has one shared login: `--ui-auth` (one or more `user:password` lines, all equal) and one `--api-token`. Everyone can change everything, from the relay allowlist to retention, and nobody can tell who did what. Teams want each person to sign in as themselves, and to give QA or a product owner a read-only seat.

**How others do it** (read 2026-11-08):

- **Grafana** ([roles and permissions](https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/access-control/), [service accounts](https://grafana.com/docs/grafana/latest/administration/service-accounts/)): every user has one basic role (Admin, Editor or Viewer); machines use service accounts that carry a role, and their tokens inherit it, so a token keeps working when the person who made it leaves.
- **Mailtrap** ([user management](https://help.mailtrap.io/article/65-user-management)): account Owner, Admin and Viewer, where a Viewer sees every project and inbox but cannot add, edit or remove anything; inbox-level Admin and Viewer roles on top.
- **Mailpit, MailHog, smtp4dev:** one shared HTTP basic auth login, no users or roles. SendMock is the same today.
- **OWASP** ([password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)): Argon2id with at least 19 MiB of memory, 2 iterations and 1 lane; session ids in `HttpOnly`, `Secure` (over HTTPS) and `SameSite` cookies, renewed at sign-in, with an idle and an absolute timeout.
- **Jenkins** (first start): the first admin is created with a one-time setup code printed in the server's log, so whoever reaches an open port first cannot take the instance.

**A13a Accounts and login (PL-14).**

- **Off by default:** a developer's own SendMock stays open with no login, as today. `--auth accounts` (`SENDMOCK_AUTH`, `auth = "accounts"` in `sendmock.toml`) turns accounts on; `--ui-auth` keeps working unchanged as the simple shared login, and the two cannot be set together.
- **The first admin:** given by `SENDMOCK_ADMIN_USERNAME` and `SENDMOCK_ADMIN_PASSWORD` (or `_FILE` variants for Docker and Kubernetes secrets) on an instance with no users; otherwise the first visit shows a setup page that asks for the one-time setup code SendMock prints in its log at start, as Jenkins does. `sendmock users reset-password <username>` run on the host against the data file (with the server stopped) recovers a lost admin password.
- **Users:** username, display name, role and password, kept in SQLite. Passwords are hashed with Argon2id at OWASP's parameters, at least 12 characters, and never leave the server, not even as hashes in seed exports (the seed file lists users and roles; their passwords are set again on import).
- **Sign in and sessions:** a sign-in page in the web UI; a random session id in a `HttpOnly`, `SameSite=Lax` cookie (`Secure` behind HTTPS), renewed at sign-in, ending after 12 hours idle or 7 days at most (`--session-idle-timeout`, `--session-max-age`), and on sign-out or a password or role change. Failed sign-ins are slowed per username and address (five a minute, then a growing wait), and the answer never says whether the username exists. Requests that change something from the browser must carry the UI's own header and a same-origin `Origin`, against cross-site requests.
- **Tokens:** each user can make personal access tokens that act as them; an Admin can make service tokens that carry a role and belong to no one, for CI and agents (as Grafana's service accounts). A token is shown once, stored as a SHA-256 hash, has an optional expiry and a last-used time, and is revoked on its own. `--api-token` keeps working as a service token with the Admin role.
- **Every surface:** the REST API, the WebSocket stream and MCP over HTTP take the session cookie or `Authorization: Bearer <token>`; the CLI uses `SENDMOCK_TOKEN`, and `sendmock login` stores a token for a server in the user's config folder. Provider APIs keep checking the provider's own credentials and SMTP its own AUTH, since apps under test cannot sign in to SendMock.
- **Audit log:** sign-ins, failed sign-ins, user, role and token changes, and every destructive operation are recorded with the user or token, time and address, shown in a new Audit tab on the Logs screen (Admins only) and kept under the retention limits.
- **Managing users:** Settings > Users and tokens for Admins; Settings > Account for everyone (display name, password, personal tokens, sign out everywhere). The same through REST, `sendmock users ...` and `sendmock tokens ...`, and MCP.

**A13b Roles: Admin, Developer, Viewer (PL-15).**

| Role | Can |
|---|---|
| **Viewer** | Read everything: emails, SMS, verifications, push, payments, HTTP requests, webhook deliveries, logs, stats and settings (secrets stay masked, as for everyone). Change nothing; opening an email or SMS does not mark it read for a Viewer, since read state is shared. |
| **Developer** | Everything a test run needs: send and simulate messages and payments, delete and clear traffic, reset traffic, release email within the configured allowlist, and create, edit and delete webhook endpoints, rules, templates, variables, HTTP bins, scenarios, providers, virtual numbers and projects. |
| **Admin** | Everything a Developer can, plus the instance: users, roles and tokens, the audit log, retention, the relay and release servers and their allowlist, SMTP chaos and auth settings, the update check, seed import and a full reset that also clears configuration. |

- **One rule in one place:** every operation in the `sendmock-ops` registry declares the role it needs. The default comes from the existing flags (a read-only operation needs Viewer, anything else Developer), and Admin operations say so explicitly. The check runs in the operations layer before the handler, so REST, the CLI, MCP and the WebSocket enforce exactly the same thing; the transport edge maps it to 403, a CLI exit code or an MCP error naming the role needed. A registry snapshot test lists every operation with its role, so a new operation is a deliberate choice that shows up in review.
- **UI:** controls the role cannot use are shown disabled with "Needs the Developer role" (or Admin), rather than hidden, so people know the feature exists and whom to ask; the top bar shows who is signed in and their role.
- **MCP:** an agent's tool list only holds the tools its token's role may call, so it does not try the rest.
- **Changing a role** takes effect on the user's next request; the last Admin cannot be removed or demoted.

**Order:** A13a, then A13b; A13a alone treats every user as an Admin, so it is usable before roles land.

**Not in this part:** single sign-on (OpenID Connect, then SAML) and LDAP, two-factor sign-in, roles per project (a Developer on one project and a Viewer on another, as Mailtrap's inbox roles), custom roles, and email invitations (an Admin sets the first password and shares it).

## A14. Real forwarding: provider connections and routing rules for email and SMS (PL-16, PL-17)

**Why (owner request, 2026-11-08, for later):** SendMock catches everything, which is what tests need, but some messages should still reach a real person: the staging app's password reset to the developer's own inbox, every OTP SMS to the tester's phone, a client's newsletter preview to their real Outlook. Email has part of this today: **Release** (one email, by hand) and **auto-forward rules** (Settings > Email), both through one SMTP relay and only to allowed recipients. SMS has nothing, and neither can pick the provider a message goes out through.

**How others do it** (read 2026-11-08):

- **Mailpit** ([SMTP relaying](https://mailpit.axllent.org/docs/configuration/smtp-relay/)): one relay. Manual release is limited by `allowed-recipients`; `--smtp-relay-all` relays every message to its original recipients, `--smtp-relay-matching` only recipients matching a regular expression; `blocked-recipients` applies everywhere, including automatic relaying, and silently drops those recipients.
- **Mailtrap** ([automatic forwarding](https://docs.mailtrap.io/email-sandbox/management/automatic-email-forwarding)): per sandbox, forward to addresses whose owners confirmed they want the mail, or to a whole domain verified by a DNS TXT record; it matches To and Cc, ignores Bcc, and sends from its own `forward.mailtrap.info` address.
- **The providers themselves** (Twilio, Vonage, SendGrid, Mailgun, Amazon SES, Postmark, Resend): each has its own send API, credentials, error codes and rate limits; Twilio and others offer test credentials and magic numbers that never send.

**A14a Real provider connections (PL-16).**

- **Connections:** named, reusable connections to real services, managed in Settings > Connections: for email SMTP (the existing relay becomes the first connection, named `relay`, and its settings keep working), SendGrid, Mailgun, Amazon SES, Postmark and Resend; for SMS Twilio, Vonage, Plivo, Telnyx, Infobip and Amazon SNS. Each provider is a sending adapter (`TwilioSendClient`, `SendGridSendClient`, ...) registered in a real-provider registry beside the emulation adapters, so a new provider is a new type and existing ones are not touched; each translates SendMock's stored message to that provider's request and its answer and errors back.
- **Who may receive:** every connection has its own allowed recipients (addresses and `*@domain` patterns for email, numbers and `+44*` prefixes for SMS) and blocked recipients, which win everywhere, as in Mailpit. A real send to anyone outside the allowed list is refused before any request leaves. A connection with an empty allowed list sends nothing.
- **Secrets:** API keys, tokens and passwords are stored on the server, masked in the UI, API answers, logs and MCP results, and written to seed exports only as an environment reference such as `${TWILIO_AUTH_TOKEN}`, never in plain text.
- **Check before use:** **Test connection** checks the credentials with the provider without sending where its API allows that, and **Send a test** sends one message to an allowed recipient. A connection shows its last success and last error.
- **One switch for everything real:** `--real-delivery off` (`SENDMOCK_REAL_DELIVERY`) stops every real send from connections, release and rules, whatever is configured, for CI and shared demos; the UI shows a banner while it is off.
- **By hand:** **Send for real** on any email or SMS (Release, extended to SMS and to every connection) picks a connection and recipients from its allowed list; the message's timeline records it.

**A14b Forwarding rules for email and SMS (PL-17).**

- **Rules:** the existing email auto-forward rules gain the connection they send through and become one rule list with SMS (Settings > Forwarding, with Email and SMS tabs). A rule has a name, an order, on or off, and a filter built with the webhook rules' filter operators (equals, contains, matches, in): project, direction (outgoing or inbound), from, to, subject or body, the provider API the message came in through, tags and headers for email, and the extracted OTP's presence.
- **Where it goes:** **to the original recipients** (only those on the connection's allowed list; the rest are dropped and noted, as Mailpit does), or **redirect to** fixed recipients, such as "every SMS to +8801XXXXXXXXX" or "every email for `*@client.com` to qa@ourcompany.com". Options: a subject or text prefix (`[SendMock]`), a From address or sender ID the provider accepts, and whether to keep the original Message-ID.
- **First match or all:** rules run in order; **stop at this rule** ends the list for a matching message, otherwise every matching rule sends.
- **Limits, against floods and bills:** each rule has a per-minute and per-day cap (defaults 30 and 500), and each connection a per-day cap; past a cap the forward is skipped and recorded, not queued. **Dry run** on a rule shows which of the last 100 messages it would have forwarded, and to whom, without sending.
- **Reliability:** each forward is an attempt with its status, the provider's message id and its error, retried on network errors and the provider's rate-limit or server errors with the webhook retry policy, never on a refused recipient or bad credentials. Attempts show in the message's timeline and in a Forwards tab on the Logs screen, and fire `email.forwarded`, `sms.forwarded` and `forward.failed` events for webhooks and the event stream.
- **No loops:** a forwarded email carries `X-SendMock-Forwarded` and is never forwarded again if it comes back, and a rule cannot send to SendMock's own SMTP address or provider APIs.
- **Every surface:** connections and rules through REST, `sendmock connections ...` and `sendmock forward-rules ...` (the existing `sendmock email forward-rules` commands stay as aliases), MCP and the seed file. With roles ([A13](#a13-accounts-login-and-roles-admin-developer-viewer-pl-14-pl-15)), connections and rules are the Admin's, and Send for real is the Developer's within the allowed lists.
- **Proof without real sends:** CI runs a second SendMock as the "real" provider and forwards to it through each adapter (SendMock emulates every one of these provider APIs), so every adapter is tested against the provider's wire format; an optional workflow, run only when the owner sets the secrets, sends through Twilio's test credentials and a sandbox email account.

**Order:** A14a (connections, starting with SMTP, SendGrid and Twilio, plus Send for real), then A14b (rules), then the remaining providers one by one.

**Not in this part:** receiving real inbound messages from providers (a real Twilio number posting to SendMock is the inbound routes' job), WhatsApp and push to real devices, recipient confirmation by email as Mailtrap does (allowed lists are set by whoever manages the instance), and per-project connections.

## A15. Docs traffic analytics with Google Analytics (WS-11)

**Why (owner request, 2026-11-08, for later):** know how many people read the docs, which pages they read and where they come from, to decide what to write and improve next.

**How others do it:** documentation sites usually load Google Analytics 4 with its `gtag.js` tag (Next.js has `@next/third-parties`, whose `GoogleAnalytics` component loads it after the page is interactive). Visitors in the EU and UK must agree before analytics cookies are set, which Google supports through Consent Mode v2: every storage type starts as `denied` and turns `granted` only on consent. Cookie-free tools (Plausible, Umami, GoatCounter, Cloudflare Web Analytics) need no banner; the owner chose Google Analytics, and they stay the fallback if the banner proves a burden.

**How:**

- **Only where it belongs:** the tag loads only when the build has a measurement ID (`NEXT_PUBLIC_GA_MEASUREMENT_ID`, a repository variable the Website workflow passes to the build), so local builds, pull request previews and forks send nothing. The owner creates the GA4 property and sets the variable.
- **Consent first:** Consent Mode v2 starts `denied`; a small banner (shadcn, the site's design tokens, respecting reduced motion) asks once, the choice is remembered, and a footer link reopens it. Do Not Track and Global Privacy Control count as a no.
- **What is sent:** page views with the path and the docs version (`/`, `/next/`, `/v0.x/`), including client-side navigation between pages, and outbound clicks on install commands' copy buttons as events. Nothing typed into the live demo or the API playground (bodies, tokens, addresses) is ever sent, and IP addresses are not stored beyond what GA4 does by default.
- **Cost:** the script loads after the page is interactive and must keep the website's Lighthouse scores and budgets; the dependency is justified in the pull request.
- **Privacy page:** a short page says what is collected, by whom, for how long and how to opt out; the footer and the README link it.

**Not in this part:** analytics in the SendMock app itself (the web UI on users' machines never phones home), heatmaps and session recordings, and A/B tests.

## A16. Code examples on every docs page, for every task (WS-12)

**Why (owner request, 2026-11-08, for later):** readers copy code. Today every top-level menu page has one "From your code" section with the screen's most common task in nine languages (WS-08.2), but the 25 sub-pages under them have none: Mail's outcomes, release, replies and forwards, reading and checks, providers and Mailpit pages; SMS's verify, providers, WhatsApp and test numbers pages; Payments' checkout page, flows, gateways, methods and subscriptions; the seven Webhooks pages; HTTP responses; and Providers. Push, a top-level page added after WS-08, has plain snippets instead of the language tabs.

**How others do it:** API-first products (Stripe, Twilio, SendGrid) show a runnable example beside every task, in the reader's chosen language, remembered across pages, with the request and the answer side by side.

**How:**

- **Every page, every task:** each menu and sub-page gets a "From your code" section with one example per task the page explains (not only the most common one), as tabs in the same nine languages: CLI, PHP (Laravel), JavaScript (Node), Python, Go, Java, Rust, Ruby and C#. A page about a provider API shows that provider's own SDK against SendMock where one exists, as the Connect pages do.
- **Short and complete:** each example runs as written against a default SendMock (`127.0.0.1`, ports 1025 and 8025), with its imports, and shows the answer it gets back; long flows link to the recipe instead of repeating it.
- **Kept true:** the existing contract check (WS-08.3) covers the new examples: every method, path, JSON key, query name and `sendmock` command must exist. A test lists every page under a menu and fails when one has no "From your code" section or misses a language.
- **Run for real:** the examples join the cross-language matrix (WS-08.5), so CI runs them against a real `sendmock` binary in every language.
- **Order:** Push first (it lacks the tabs), then Webhooks, SMS, Mail, Payments, HTTP and Providers, one menu per pull request.

**Not in this part:** examples for languages beyond the nine, and interactive "run in the browser" examples (the API playground covers that).

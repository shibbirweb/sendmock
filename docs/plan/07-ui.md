# 07. Web UI

Built with Bun, Vite, React, TypeScript, Tailwind CSS v4 and shadcn/ui. Served from the binary at `http://localhost:8025`.

**The UI is built first, against mock data**, before any backend work (Stage A in [11-roadmap.md](11-roadmap.md)). An MSW-based mock API with realistic fixtures and simulated realtime events lets every screen be previewed (published at `/demo/` on the GitHub Pages website) and signed off; the backend then implements the API contract the UI already uses.

## UX principles

1. **Instant.** Realtime updates over WebSocket, optimistic actions, no full page reloads.
2. **Keyboard first.** `j`/`k` navigate, `Enter` open, `d` delete, `/` search, `g m` mail, `g s` SMS, `g w` webhooks, `?` shortcut help, `Cmd/Ctrl+K` command palette.
3. **Copy friendly.** One-click copy for OTP codes, links, IDs, raw payloads, cURL of a webhook request.
4. **Calm and dense.** Information-dense lists like a mail client, but generous whitespace in detail views. Dark and light themes following the OS, with manual override.
5. **Responsive.** Usable on a laptop split screen and on a phone on the same network.
6. **Accessible.** Radix primitives, visible focus, WCAG AA contrast, reduced-motion support.

## Screens

### Overview

Home dashboard, updated live from `/api/v1/stats` (refreshed on every realtime event):

- **KPI row:** stat tiles for emails, SMS, verifications (pending ones called out), HTTP requests and webhook success rate, each with its total and today's count, linking to its screen.
- **Activity, last 24 hours:** stacked columns per hour for emails, SMS and HTTP requests (three categorical colours validated for both themes, a legend, a 2px gap between segments, columns at most 24px wide). Hover or arrow keys show one tooltip with every series for that hour, and a "Show as table" switch gives the same numbers as a table.
- **Webhooks by endpoint:** deliveries in the last 24 hours, a success-rate meter, p50 and p95 latency, retries and the most common failure codes per endpoint.
- **Recent failures:** the last failed or exhausted deliveries (time, endpoint, event, status code or error), each linking to the delivery.
- **Latest messages:** the newest emails and SMS with links.
- **Connect your app:** the SMTP address and API base URL with copy buttons, and a link to Settings > Connection.

### Mail

- List: sender, subject, snippet, time, unread dot, attachment icon, tags, source badge (SMTP / SendGrid / Resend / ...), delivery outcome badge (bounced, complained). Infinite scroll.
- Search bar with filter chips (`from:`, `to:`, `has:attachment`, `is:unread`, `tag:`, `source:`).
- Detail tabs:
  - **HTML** (sandboxed iframe, device width toggles, load images toggle, "Screenshot" to PNG).
  - **Text**, **Source** (syntax highlighted), **Headers** (table, with List-Unsubscribe validation warnings).
  - **Attachments** with image thumbnails.
  - **MIME** tree inspector (part types, encodings, sizes, per-part download).
  - **Checks**: HTML compatibility score per client, link check results, spam score (when SpamAssassin is configured).
  - **Timeline**: received (with link to SMTP session or API request log), opened, delivered/bounced/complained, released/forwarded, webhooks sent.
  - **Template data** (provider HTTP sends with template ID and dynamic data).
- Extracted panel: OTP codes and links with copy/open buttons.
- Opened indicator: "Opened N times, first at ..." with an open history popover.
- Actions: mark read/unread, simulate open, **Simulate** menu (delivered, bounce hard/soft, complaint, unsubscribe), tag, download `.eml`, send to webhook, **release** to real SMTP, delete.
- Bulk select and "Delete all" with confirm dialog.
- **Reply and forward as recipient** (simulates the person your app emailed answering it; the result is an incoming email that inbound routes deliver to your app, see [05-webhooks.md](05-webhooks.md#simulating-replies-and-forwards)):
  - **Buttons:** Reply, Reply all (only when the email has more than one recipient) and Forward in the detail header, next to Simulate; shortcuts `R`, `Shift+R` and `F`. Shown only on emails your app sent.
  - **Composer:** opens inline under the header, like a mail client, with a heading "Reply as recipient" or "Forward as recipient". Fields: From (one of the original recipients, picked from a list, or any address), To (Reply: the original `Reply-To` or `From`, read only; Forward: an address input, required, with the inbound domains from Settings as suggestions), Cc (Reply all only, read only), Subject (`Re:` / `Fwd:` prefilled, editable) and a message box. Like Gmail, the message box opens with the original already in the body, below an empty first line where the cursor starts: the quoted original for Reply ("On ... wrote:" and `>` lines), the "---------- Forwarded message ---------" block for Forward. It can be edited or trimmed like any text, so there is no separate preview. Forward also has "Include attachments" (when the email has any), on by default. A hint under the buttons says "Creates an incoming email (`email.inbound`). Inbound routes deliver it to your app."
  - **Keys:** `Ctrl/Cmd+Enter` sends, `Esc` closes the composer (asking first when the message box has text).
  - **After sending:** the composer closes and a toast offers "Open" to jump to the new email.
  - **On the original:** a "Replies and forwards" row under the header lists each one (icon, sender, time) as links; the Timeline tab shows "Replied by recipient" and "Forwarded by recipient".
  - **On the incoming email:** an Inbound badge with a reply or forward icon, a "Reply to: <subject>" or "Forward of: <subject>" link back to the original, and a note that inbound routes deliver it (link to Webhooks > Inbound routes). Reply, Forward and the delivery outcome simulations are hidden, as they only apply to mail your app sent.
  - **In the list:** incoming emails show the Inbound badge with the same icon; the search supports `is:inbound`.
- Browser notifications toggle (with optional filter) in the list header.

### SMS

- Thread list grouped by `from`/`to` pair, phone-style avatars, last message preview, channel badge (SMS / WhatsApp).
- Conversation view: chat bubbles (outbound right, inbound left; WhatsApp styling for that channel), status ticks (queued / sent / delivered / read / failed) with error code tooltip, segment and encoding badges, API badge (`native`, `twilio`, ...), Messaging Service badge. "Read" (blue double tick) appears once `sms.opened` has fired.
- "Simulate read" action on outbound bubbles.
- Per-message drawer: status timeline, original request JSON (link to the API request log), callback attempts.
- Composer at the bottom: "Reply as recipient" to simulate an inbound SMS / WhatsApp message, with format picker and an attach button for media.
- Media (MMS and WhatsApp): image thumbnails and file chips in bubbles, an "MMS" or "Media" badge, a Media list in the message drawer ([04-sms.md](04-sms.md#mms-and-media)).
- Manual profile: buttons to set status (Delivered / Undelivered / Failed) with error code picker.
- Reply webhook: inbound bubbles show the result of the number's reply webhook (status code or Twilio error code), replies created from TwiML carry a "TwiML reply" badge, and the drawer has a Reply webhook tab with request, response, parsed TwiML and "Resend reply webhook" ([04-sms.md](04-sms.md#reply-webhook-twilio-style)).
- **Verify tab** (`/sms/verify`, two tabs kept in the URL: Verifications and Services):
  - **Verifications:** a table with To, channel (SMS / WhatsApp / Email / Call icon), service, code (monospace, copy button), status badge, check attempts ("2 / 5") and a live expiry countdown for pending ones ("Expires in 9:41", turning into "Expired" when it runs out). Status chips above it (All, Pending, Approved, Failed for canceled / expired / max attempts) and a search on To. On phones the service and attempts columns hide. Empty state explains how to start a verification with the Twilio Verify API.
  - **Detail drawer** (row click, `?verification=<sid>` so it can be linked; Esc closes): the code large with copy, status, To, channel, service, attempts, created and expiry times, a link to the captured SMS or email that carried the code, the timeline (started, code sent, failed checks, approved, canceled, expired, max attempts reached, forced), and the force buttons (Approve, Cancel, Expire, Max attempts), shown while the verification is pending.
  - **Services:** a table with name, SID (copy), code length, fixed code (or "Random"), TTL and actions. "New service" and Edit open a dialog: friendly name (required), code length 4 to 10, fixed code (optional, digits only, exactly the code length), TTL in minutes (1 to 1440). Delete asks for confirmation.

### Payments

Payments list and detail (timeline, method, line items, redirects, IPN/webhook deliveries), Simulate menu (succeed, decline, refund, dispute, expire, resend IPN), the hosted **test checkout page** at `/pay/{sessionId}` with provider themes (Stripe-like card form, PayPal approve, SSLCommerz method picker, bKash wallet with OTP and PIN) and a permanent TEST MODE banner. See [17-payments.md](17-payments.md#ui).

### HTTP (catcher)

Bins list with counts and presets, request list, request detail (pretty/raw body, headers, query, mock response sent), Slack/Discord/push previews, "Copy as cURL", "Forward to URL", "Send to webhook", response rule editor. See [15-http-catcher.md](15-http-catcher.md).

### Webhooks

- **Endpoints:** table with name, URL, template, enabled switch, success rate sparkline. Create/edit sheet with headers editor, secret (`whsec_...`, masked, rotate with overlap), retry policy, "Send test".
- **Inbound routes:** Mailgun-style routes (priority, `match_recipient` / `match_header` / `catch_all` expression, `forward` / `store` / `stop` actions) with a "matches N of the last 50 incoming emails" preview.
- **Rules:** list with event chips and filter summary. Visual rule builder (field / operator / value rows, all/any groups) with a live "matches N of last 50 messages" preview.
- **Deliveries:** live log table (time, event, endpoint, trigger auto/manual/replay, status code, duration, attempt). Detail view with request/response side by side, "Copy as cURL", "Replay", "Edit and replay", "Cancel retries", "Save" (bookmark).
- **Templates:** gallery of built-in service templates (Twilio, Mailgun, SendGrid, Slack, ...) and custom templates; see [13-webhook-templates.md](13-webhook-templates.md).
- **Variables:** table of global variables (name, kind badge, value or masked secret, scope), create/edit sheet per kind, "Regenerate" for fixed random values. Endpoint edit sheet has its own Variables tab.
- **Saved:** named saved deliveries with re-send, "Save as template", export with seed.
- **Request editor:** URL, params, headers and body (Template / Fields / Raw / None) with CodeMirror, `{{` autocomplete, live preview against a chosen message, and inline render errors.
- **Composer:** manual request builder with provider format presets, Prompt variable form and per-send overrides.

### Numbers

Two tabs kept in the URL (`/numbers`, `/numbers?tab=services`):

- **Numbers:** a table with number (E.164, copy), label, channel badges (SMS, WhatsApp), webhooks (inbound method and URL, or "Rules only" when none is set, with the default status callback below), Messaging Service, and Edit / Delete. "Add number" and Edit open a side sheet:
  - Number (E.164, unique) and label.
  - Channels: SMS and / or WhatsApp (at least one).
  - Inbound webhook: URL, method (POST or GET), fallback URL and format (the inbound SMS templates: Twilio, Vonage, Plivo, ..., or native JSON). Leaving the URL empty means only webhook rules receive inbound messages. When a webhook rule on `sms.inbound` also exists, the sheet notes that both will receive them ([reply webhook](04-sms.md#reply-webhook-twilio-style)).
  - Default status callback URL.
  - Messaging Service: none or one service; a number belongs to at most one.
  - URLs must be `http` or `https`. Delete asks for confirmation and removes the number from its service.
- **Messaging Services:** a table with name, SID (copy), sender pool (number chips), inbound handling and actions. Create and Edit open a sheet with the friendly name, the sender pool (checkboxes for every number; picking one already in another service moves it, and the list says so) and the inbound handling: "Send a webhook" (request URL and fallback URL), "Defer to sender's webhook" (each number's own inbound URL) or "Drop the message". Delete asks for confirmation and leaves the numbers unassigned.

### Logs

Two tabs kept in the URL (`/logs`, `/logs?tab=http`); each row opens a wide side drawer, linked by `?session=<id>` or `?request=<id>` (the SMS drawer's "Open in request log" uses the latter). Logs grow large, so both tables page with the API cursor: 50 rows at a time, the next page loading when the end of the table scrolls into view (with a "Load more" button as fallback) and a "Showing 50 of 5,021" count. Filters and search run on the server, so they cover every row, not just the loaded ones.

- **SMTP:** a table with time, client address, EHLO name, TLS (version or "Plain"), AUTH (user and mechanism), result badge (Delivered, Rejected, Aborted), stored email count and duration. Failed sessions are highlighted with their reason under the result. Chips (All, Delivered, Failed) and a search on client, EHLO name and AUTH user.
  - **Drawer:** the session facts, the failure reason in a callout, and the transcript viewer: one line per command or reply, client commands and server replies told apart by colour and a C / S marker, reply codes coloured by class (2xx, 3xx, 4xx and 5xx), masked AUTH secrets and the DATA line kept as a placeholder that links to the stored email. "Copy transcript" and "Open email" buttons.
  - **Mail link:** the email detail's source badge links to the SMTP session that delivered the email (EM-09.3).
- **HTTP:** a table with time, API (Native, Twilio, Vonage, SendGrid, ...), method, path, status code and duration. Rejected requests (4xx and 5xx) are highlighted. Chips by status class (All, 2xx, 4xx, 5xx), an API picker and a search on the path.
  - **Drawer:** method, full path, status, duration and time; request headers (credentials masked), the request body (JSON pretty-printed, form bodies as a field table, anything else as text) and the response body the same way; "Open message" for the SMS or email the request created.

### Settings

One page with a section nav (a side list on desktop, a picker on phones), the section kept in the URL (`/settings?section=sms`). Each section is its own form: changes are applied with **Save changes** (disabled until something changed, **Discard** resets), take effect without a restart, and invalid values show a message under the field (PL-05). Validation is shared with the API.

- **General:** retention (max emails, max SMS, max age in days or "Keep forever"). Danger zone: **Delete all emails**, **Delete all SMS** and **Reset to seed**, each behind a confirmation that says what is lost.
- **Seed:** status card (seed file path or "No seed file", when it was applied, and the items added or changed since, with a hint to export them). **Export** downloads `sendmock.seed.toml` (secrets written as `${ENV_VAR}` references, never literal). **Apply** takes an uploaded or pasted file, **Validate** lists errors with line numbers and a summary of what would change, then applies after a confirmation.
- **Email:** plus-address auto-tagging, delivery outcome profile (off, auto-delivered, realistic with bounce and complaint rates), inbound email domains (chip editor), relay SMTP URL (password masked) and recipient allowlist (release stays off until it has an entry), SpamAssassin address (empty means off), the **Magic addresses** switch, **Custom outcome addresses** (same table, dialog and "Test an address" box as the SMS rules), and the magic addresses reference table. Tag rules and auto-forward rules use the visual rule builder, so they are edited with the webhook screens (U2); this section links there.
- **SMS:** simulation profile (instant, realistic, manual, each with what it does), failure rate (0 to 100%), strict Twilio test mode, the **Magic numbers** switch, **Custom outcome numbers** (a table with order, match, pattern, outcome and code, note, an enabled switch, move up / down, edit and delete; Add and Edit open a dialog that only asks for the code or delay when the outcome needs it), a "Test a number" box that shows which rule, magic number or profile applies, and the magic numbers reference (Twilio `To` and `From` test numbers and the SendMock after-send extensions, from [04-sms.md](04-sms.md#delivery-simulation)).
- **Opened events:** "Fire opened events when I view messages" (default on), and "First open only" or "Every open".
- **Chaos:** reject the next N SMTP messages with a chosen code (421, 450, 550, 552), reject recipients matching a pattern with `550`, added latency per SMTP command, and drop the connection during `DATA`. While any chaos option is on, the section nav shows a "Chaos on" badge.
- **OTP patterns:** an ordered list of regular expressions (first capture group is the code) with add, remove and "Restore defaults", invalid patterns flagged, and a tester: paste a message and see which pattern matched and the code it found.
- **Connection:** copy-ready snippets for SMTP, the email API, SMS and the HTTP catcher, with a language picker (Laravel / PHP, Node.js, Python, Go, Java, Ruby, .NET, cURL) and a "Where does your app run?" picker that fills in the right host: this machine (`127.0.0.1`), a container talking to SendMock on the host (`host.docker.internal`), or the same Docker Compose project (`sendmock`). Same content as [08-integrations.md](08-integrations.md); ports come from `/info`.
  - **Customize the request:** a request headers editor (name and value rows, with a quick "Add Authorization header" for when API auth is on) and a JSON body editor for the email and SMS calls, prefilled with the sample and with "Add field" chips for the optional fields (`/send`: `cc`, `bcc`, `text`, `tags`, `headers`, `attachments`; `/sms`: `status_callback`, `metadata`). In a body, `"{{file:invoice.pdf}}"` as a value stands for "this file, base64 encoded": each snippet then reads and encodes the file the way its language does it (`base64_encode(file_get_contents(...))` in PHP, `fs.readFileSync(...).toString("base64")` in Node.js, `base64 < file` in cURL, and so on) and puts it in the body. Every language's snippet updates as you type, written the way that language does it (for example `Http::withHeaders()` in Laravel, `headers=` and a Python dict in Python, `req.Header.Set` in Go, `-H` in cURL). Invalid JSON is flagged and the snippets keep the last valid body. A **Reset** button (disabled until something changed) removes the added headers and puts both bodies back to the sample.
- **About:** version and channel, uptime, listeners (SMTP, HTTP, provider port), database path and size, links to the changelog and docs for this version, and the opt-in update check: off by default, and "Check for updates" only calls GitHub Releases when it is on (stable installs are offered stables, beta installs betas and stables).

### Empty states / onboarding

Every list tells "no data yet" apart from "nothing matches":

- **Nothing matches** (a search, chip or filter is active): a short line saying so and a **Clear filter** button. No onboarding card.
- **No data yet:** an icon, one line on what shows up here, a **how to connect** card and a **sample** button, so the screen can be explored at once.

The how to connect card shows the values the app needs, each with a copy button, and a "More snippets" link to Settings > Connection:

- Ports come from `/info`. The host follows the same **Where does your app run?** choice as Settings > Connection (this machine `127.0.0.1`, a container talking to SendMock on the host `host.docker.internal`, the same Compose project `sendmock`), shown as a compact switch on the card. The choice is remembered in the browser and shared by every card and Settings > Connection. When `/info` says SendMock runs in a container, the default is the Compose host.

| Screen | How to connect shows | Sample button |
|--------|----------------------|---------------|
| Mail | SMTP host and port, "no auth or TLS needed" | **Send a sample email** (over SMTP, so it also shows in Logs > SMTP) |
| SMS | native `POST /api/v1/sms` URL, Twilio and Vonage base URLs | **Send a sample SMS** |
| Verify > Verifications | Twilio Verify base URL and the start call | **Start a sample verification** (on the first Verify service, or a new "Sample" service when there is none; the code goes out by SMS) |
| Numbers | none (numbers are optional, any From is accepted) | **Add a sample number** (`+15550001111`) |
| Logs > SMTP | SMTP host and port | **Send a sample email** |
| Logs > API requests | API base URL | **Send a sample SMS** |
| Overview > Latest messages | SMTP address and API base URL (the connect card) | **Send a sample email** and **Send a sample SMS** |

Samples go through `POST /api/v1/samples/{kind}` ([06-api.md](06-api.md#test-automation-helpers)), so they fire the same events, webhooks and notifications as real traffic. The HTTP catcher and Webhooks screens get their empty states with those screens in Phase U2.

## Frontend structure

```
web/
├── package.json            # bun scripts: dev, build, lint, typecheck, test
├── vite.config.ts          # proxy /api and /ws to :8025 in dev
├── components.json         # shadcn/ui config
├── src/
│   ├── main.tsx
│   ├── routes/             # TanStack Router file routes: mail, sms, webhooks, numbers, settings
│   ├── components/ui/      # shadcn generated components
│   ├── components/         # app components: MessageList, EmailPreview, SmsThread, RuleBuilder...
│   ├── lib/api/            # API types (source of the contract in Stage A) + TanStack Query hooks
│   ├── mocks/              # MSW handlers, in-memory mock DB, fixtures, realtime generator, dev toolbar
│   ├── lib/realtime.ts     # WebSocket client, pushes into the query cache
│   ├── lib/shortcuts.ts
│   └── styles/
└── tests/                  # Vitest (bun) unit tests, Playwright smoke tests
```

## Bundle budget

- Initial JS under 250 KB gzipped; Shiki and the rule builder are lazy-loaded.
- Fonts: system font stack (no web font download), optional Inter bundled if it fits the budget.
- Total embedded `dist/` under 2 MB so the binary stays small.

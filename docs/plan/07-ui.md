# 07. Web UI

Built with Bun, Vite, React, TypeScript, Tailwind CSS v4 and shadcn/ui. Served from the binary at `http://localhost:8025`.

**The UI is built first, against mock data**, before any backend work (Stage A in [11-roadmap.md](11-roadmap.md)). An MSW-based mock API with realistic fixtures and simulated realtime events lets every screen be previewed (published at `/demo/` on the GitHub Pages website) and signed off; the backend then implements the API contract the UI already uses.

## UX principles

1. **Instant.** Realtime updates over WebSocket, optimistic actions, no full page reloads.
2. **Keyboard first.** `j`/`k` navigate, `Enter` open, `d` delete, `/` search, `g m` mail, `g s` SMS, `g w` webhooks, `?` shortcut help, `Cmd/Ctrl+K` command palette.
3. **Copy friendly.** One-click copy for OTP codes, links, IDs, raw payloads, cURL of a webhook request.
4. **Calm and dense.** Information-dense lists like a mail client, but generous whitespace in detail views. Dark and light themes following the OS, with manual override.
5. **Responsive.** Usable on a laptop split screen and on a phone on the same network.
6. **Accessible.** Radix primitives, visible focus, WCAG AA contrast, reduced-motion support.

## Screens

### Overview

Home dashboard, updated live from `/api/v1/stats` (refreshed on every realtime event):

- **KPI row:** stat tiles for emails, SMS, verifications (pending ones called out), HTTP requests, webhook success rate and payments (count, success rate and test revenue per currency), each with its total and today's count, linking to its screen.
- **Activity, last 24 hours:** stacked columns per hour for emails, SMS and HTTP requests (three categorical colours validated for both themes, a legend, a 2px gap between segments, columns at most 24px wide). Hover or arrow keys show one tooltip with every series for that hour, and a "Show as table" switch gives the same numbers as a table.
- **Webhooks by endpoint:** deliveries in the last 24 hours, a success-rate meter, p50 and p95 latency, retries and the most common failure codes per endpoint.
- **Recent failures:** the last failed or exhausted deliveries (time, endpoint, event, status code or error), each linking to the delivery.
- **Latest messages:** the newest emails and SMS with links.
- **Connect your app:** the SMTP address and API base URL with copy buttons, and a link to Settings > Connection.

### Mail

- List: sender, subject, snippet, time, unread dot, attachment icon, tags, source badge (SMTP / SendGrid / Resend / ...), delivery outcome badge (bounced, complained). Infinite scroll.
- Search bar with filter chips (`from:`, `to:`, `has:attachment`, `is:unread`, `tag:`, `source:`).
- Detail tabs:
  - **HTML** (sandboxed iframe, device width toggles, load images toggle, "Screenshot" to PNG).
  - **Text**, **Source** (syntax highlighted), **Headers** (table, with List-Unsubscribe validation warnings).
  - **Attachments** with image thumbnails.
  - **MIME** tree inspector (part types, encodings, sizes, per-part download).
  - **Checks**: HTML compatibility score per client, link check results, spam score (when SpamAssassin is configured).
  - **Timeline**: received (with link to SMTP session or API request log), opened, delivered/bounced/complained, released/forwarded, webhooks sent.
  - **Template data** (provider HTTP sends with template ID and dynamic data).
- Extracted panel: OTP codes and links with copy/open buttons.
- Opened indicator: "Opened N times, first at ..." with an open history popover.
- Actions: mark read/unread, simulate open, **Simulate** menu (delivered, bounce hard/soft, complaint, unsubscribe), tag, download `.eml`, send to webhook, **release** to real SMTP, delete.
- Bulk select and "Delete all" with confirm dialog.
- **Import .eml** (list toolbar, U3 W14): upload or paste a raw message and store it as **Sent by your app** (`POST /send/raw`, as the `sendmail` shim does) or **Incoming to your app** (`POST /emails/inbound`, run through the inbound routes); a toast offers **Open**.
- **Reply and forward as recipient** (simulates the person your app emailed answering it; the result is an incoming email that inbound routes deliver to your app, see [05-webhooks.md](05-webhooks.md#simulating-replies-and-forwards)):
  - **Buttons:** Reply, Reply all (only when the email has more than one recipient) and Forward in the detail header, next to Simulate; shortcuts `R`, `Shift+R` and `F`. Shown only on emails your app sent.
  - **Composer:** opens inline under the header, like a mail client, with a heading "Reply as recipient" or "Forward as recipient". Fields: From (one of the original recipients, picked from a list, or any address), To (Reply: the original `Reply-To` or `From`, read only; Forward: an address input, required, with the inbound domains from Settings as suggestions), Cc (Reply all only, read only), Subject (`Re:` / `Fwd:` prefilled, editable) and a message box. Like Gmail, the message box opens with the original already in the body, below an empty first line where the cursor starts: the quoted original for Reply ("On ... wrote:" and `>` lines), the "---------- Forwarded message ---------" block for Forward. It can be edited or trimmed like any text, so there is no separate preview. Forward also has "Include attachments" (when the email has any), on by default. A hint under the buttons says "Creates an incoming email (`email.inbound`). Inbound routes deliver it to your app."
  - **Keys:** `Ctrl/Cmd+Enter` sends, `Esc` closes the composer (asking first when the message box has text).
  - **After sending:** the composer closes and a toast offers "Open" to jump to the new email.
  - **On the original:** a "Replies and forwards" row under the header lists each one (icon, sender, time) as links; the Timeline tab shows "Replied by recipient" and "Forwarded by recipient".
  - **On the incoming email:** an Inbound badge with a reply or forward icon, a "Reply to: <subject>" or "Forward of: <subject>" link back to the original, and a note that inbound routes deliver it (link to Webhooks > Inbound routes). Reply, Forward and the delivery outcome simulations are hidden, as they only apply to mail your app sent.
  - **In the list:** incoming emails show the Inbound badge with the same icon; the search supports `is:inbound`.
- Browser notifications toggle (with optional filter) in the list header.

### SMS

- Thread list grouped by `from`/`to` pair, phone-style avatars, last message preview, channel badge (SMS / WhatsApp).
- Conversation view: chat bubbles (outbound right, inbound left; WhatsApp styling for that channel), status ticks (queued / sent / delivered / read / failed) with error code tooltip, segment and encoding badges, API badge (`native`, `twilio`, ...), Messaging Service badge. "Read" (blue double tick) appears once `sms.opened` has fired.
- "Simulate read" action on outbound bubbles.
- Per-message drawer: status timeline, original request JSON (link to the API request log), callback attempts.
- Composer at the bottom: "Reply as recipient" to simulate an inbound SMS / WhatsApp message, with format picker and an attach button for media.
- Media (MMS and WhatsApp): image thumbnails and file chips in bubbles, an "MMS" or "Media" badge, a Media list in the message drawer ([04-sms.md](04-sms.md#mms-and-media)).
- Manual profile: buttons to set status (Delivered / Undelivered / Failed) with error code picker.
- Reply webhook ([04-sms.md](04-sms.md#reply-webhook-twilio-style)):
  - Under an inbound bubble, a result line: "Reply webhook 200" (with "1 TwiML reply" when the app answered), "Reply webhook failed: 11205 HTTP connection failure", "Fallback 200 after 11205" when the fallback answered, or "Rules only" when the number has no inbound URL.
  - Replies created from TwiML carry a "TwiML reply" badge that scrolls to the inbound message they answer.
  - The drawer of an inbound message has a **Reply webhook** tab: where it went (Messaging Service or number, primary or fallback), each attempt with the request (form fields and headers, `X-Twilio-Signature` included), the response (status, content type, body) or the error with its Twilio code, the parsed TwiML verbs (Message with body, to, from, statusCallback and media; Redirect), and **Resend reply webhook**.
- **Verify tab** (`/sms/verify`, two tabs kept in the URL: Verifications and Services):
  - **Verifications:** a table with To, channel (SMS / WhatsApp / Email / Call icon), service, code (monospace, copy button), status badge, check attempts ("2 / 5") and a live expiry countdown for pending ones ("Expires in 9:41", turning into "Expired" when it runs out). Status chips above it (All, Pending, Approved, Failed for canceled / expired / max attempts) and a search on To. On phones the service and attempts columns hide. Empty state explains how to start a verification with the Twilio Verify API.
  - **Detail drawer** (row click, `?verification=<sid>` so it can be linked; Esc closes): the code large with copy, status, To, channel, service, attempts, created and expiry times, a link to the captured SMS or email that carried the code, the timeline (started, code sent, failed checks, approved, canceled, expired, max attempts reached, forced), and the force buttons (Approve, Cancel, Expire, Max attempts), shown while the verification is pending.
  - **Services:** a table with name, SID (copy), code length, fixed code (or "Random"), TTL and actions. "New service" and Edit open a dialog: friendly name (required), code length 4 to 10, fixed code (optional, digits only, exactly the code length), TTL in minutes (1 to 1440). Delete asks for confirmation.

### Payments

See [17-payments.md](17-payments.md#ui).

- **List** (`/payments`): amount in the currency's own format (minor units; JPY has no decimals), provider badge, status badge, customer and time, newest first, 50 at a time, new and changed payments appearing live. Status chips (All, Succeeded, Pending, Failed, Refunded, Disputed), a provider picker and a currency picker narrow it; all three and the open payment are kept in the URL (`?status=&provider=&currency=&payment=`). Empty state: what the screen shows, the native API and checkout endpoints, and a link to Settings > Payments.
- **Detail** drawer (opened by a row or `?payment=`):
  - Amount, status, provider and the provider's ids (session, intent, order, transaction), customer (email, name, phone), payment method (card brand, last 4 and expiry, or a masked wallet number; never a full card number), failure or decline reason, refunded amount, and the dispute state.
  - **Line items** (name, quantity, unit price, line total) and metadata.
  - **Timeline**: created, 3-D Secure, authorized, captured, succeeded or failed, refunds, disputes, redirects and notifications, oldest first.
  - **Redirects**: the success, fail and cancel URLs, which one was used, with the method (GET or POST) and the fields sent.
  - **Notifications**: each IPN or webhook sent for the payment (provider event name, native event, status code, time), linking to the delivery in the webhook log.
- **Simulate** menu on the detail, offering only what the payment's status allows: Succeed and Decline (insufficient funds, expired card, incorrect CVC, generic decline, fraud) while it waits for payment; Capture and Void when authorized; Refund (a dialog with the amount, full by default, never more than what is left) and Open dispute when paid; Resolve dispute (won or lost) when disputed; Expire checkout while a checkout waits; and Resend notification whenever one was sent. The result shows at once in the status, timeline and notifications, and a new notification goes through the webhook engine (delivery log, retries, replay).
- **Methods** (`/payments/methods`): a table of payment methods (name, flow, gateways offering it, test values count, Built-in or Custom, Modified, enabled switch). **Add method** asks for a flow and a name. The edit sheet has name, key and flow (fixed after creation), accent colour and the test values the flow's steps need: test cards (number and outcome; only numbers from the documented test ranges that pass the Luhn check), test numbers with outcomes, the OTP, the PIN, the test account, or the default outcome. A built-in shows **Reset to default** (asks first); a custom one can be deleted while no payment uses it.
- **Flows** (`/payments/flows`): a table of flows (name, steps in order such as "Account number, OTP, PIN", picker tab, methods using it, Built-in or Custom, Modified). **Add flow** asks for a name, a key and the picker tab. The edit sheet lists the steps in order: add a step from the catalogue (card form, account number, voucher code, OTP, PIN, signed-in account, QR code, reference code, confirm), move up / down, remove, and edit each step's title, field label, hint and button text; a **Variables** reference above the steps lists every label variable with what it becomes and an example, each label field has an **Insert variable** menu, and a preview line under each step shows its labels filled with example values; problems (no step, two deciding steps) show before saving. Built-ins (Card, Wallet, Bank, Account, QR, Bank transfer, Voucher) show **Modified** once edited and **Reset to default** (asks first); a custom one can be deleted while no method uses it.
- **Gateways** (`/payments/gateways`): a table of gateways (name, key, methods offered, notification endpoint, Built-in or Custom, Modified, enabled switch). **Add gateway** asks for a name, a key and what to start from (a built-in or blank). The edit sheet, in tabs:
  - **General:** name, key (fixed after creation), accent colour, enabled.
  - **Checkout:** the methods offered, in order (add from the method list, move up / down, remove), and **Open a test checkout**, which creates a test payment for the gateway and opens its checkout page.
  - **Merchant:** credentials as name / value rows, secrets masked with reveal behind a confirmation, and the notification endpoint.
  - **Redirect:** GET or POST and the field rows (name, template, sent always or only on success).
  - **Notification:** JSON or form, the event name for each native event (blank sends nothing), the body template in the code editor and header templates, with `{{` suggestions for `payment`, `event` and `merchant`.
  - A live preview beside Redirect and Notification renders them against a chosen payment and event, with problems under each part; a save with template errors is refused.
  - A built-in shows **Modified** once edited and **Reset to default** (asks first); a custom one can be deleted while no payment uses it.
- **Test checkout page** at `/pay/{sessionId}`, a standalone page without the app shell, as a gateway's page would be:
  - A permanent **TEST MODE: no real payment** banner, the merchant and order summary (line items, total), and the customer's email.
  - The gateway's methods: one method shows its flow directly, several show a picker grouped by each flow's picker tab (Cards, Mobile banking, Net banking, Accounts, or a custom tab). The flow's steps run in order with their own labels. Card a form (number, expiry, CVC, name) whose outcome follows the method's test cards; Wallet the number, then the OTP, then the PIN, with the test values shown; Bank pick and confirm; Account sign in as the test account and **Approve**. With the built-in setup that is a card form for **Stripe** and **Native**, PayPal's approve for **PayPal**, the picker for **SSLCommerz** and the wallet flow for **bKash**. The page uses the gateway's accent colour.
  - **Test controls** beside it: Pay successfully, Decline (with a reason), Cancel, Require 3-D Secure and Delay. The 3-D Secure card (or control) opens a challenge with **Approve** and **Fail**.
  - A card number that passes the Luhn check but is not a test card is refused with "Use a test card" and never stored or logged; an invalid number is refused as invalid.
  - After paying, declining or canceling, the result shows where SendMock sends the browser (the success, fail or cancel URL with the method and fields) and a **Return to merchant** button (a link, or a form for providers that POST). Delay leaves the payment pending, to settle later with Simulate.
  - A completed, failed, canceled or expired session shows that it is closed and cannot be paid again.
  - Keyboard: every control is reachable in order with visible focus, and Enter submits the current step.

### HTTP (catcher)

Three columns like Mail (bins, requests, detail), stacked on phones; the bin, tab and request are kept in the URL (`/http?bin=<id>&tab=responses&request=<id>`). See [15-http-catcher.md](15-http-catcher.md).

- **Bins:** "All requests" plus each bin with its preset badge, request count and last request time. **New bin**: a name (lowercase letters, digits, `-` and `_`) and a preset (Slack, Discord, Microsoft Teams, Google Chat, Telegram, Firebase Cloud Messaging, Expo push, OneSignal, Generic JSON, or none), which sets the default reply. Bins are also created on first use. The bin header shows its catch URL (`http://127.0.0.1:8025/catch/<name>`) with a copy button, **Clear requests** and **Delete bin** (both ask first). Empty state: the catch URL, a cURL example and **Send a sample request**.
- **Requests** tab: newest first, 50 at a time, new ones appearing live: method badge, path, the status code returned (error codes highlighted) and time.
- **Request detail:** method and full URL, time, client IP and duration, then tabs:
  - **Preview** (when recognised, by the bin's preset or the payload's shape): Slack Block Kit (text with basic mrkdwn, header, section with fields, divider, context and buttons) as a Slack message, Discord content and embeds (colour bar, author, title, description, fields, footer) as a Discord message, and FCM, Expo and OneSignal pushes as phone notification cards.
  - **Body:** pretty (JSON indented, form and multipart fields as rows) or raw, with uploaded files listed to download.
  - **Headers** and **Query** as name / value rows.
  - **Response:** the status, headers and body SendMock answered with, and which rule produced it ("Default reply" otherwise, "Simulated failure" when the failure rate hit).
  - Actions: **Copy as cURL**, **Forward to URL** (a dialog remembering the last URL; shows the status and duration it got) and **Send to webhook** (the Send to webhook dialog, with the request as `data` of an `http.captured` event).
- **Responses** tab: the bin's response rules in order (first match wins) with move up / down, an enabled switch, a summary ("POST /v1/* when header x-env is test: 429 after 0.5 to 2 s, 10% fail with 500"), edit and delete, and the **Default reply** with Edit. **Add rule** and Edit open a sheet:
  - Name; match on method (any or one), a path glob relative to the bin (`/v1/*`) and header / body conditions with the webhook rule filter builder.
  - Response: status code, headers and body as templates (`request.method`, `request.path`, `request.query`, `request.headers`, `request.body`, `request.json`, `vars`, plus functions and filters), in the code editor.
  - Delay: fixed or a random range in milliseconds (up to 30 s); failure rate (0 to 100%) with the status code a failure returns.
  - **Preview** against a captured request of the bin (the latest by default): whether this rule matches it (and why not), and the rendered status, headers and body with any template problems.

### Webhooks

- **Overview** (`/webhooks/overview`, the first Webhooks screen; range and endpoint in the URL): delivery health from `/api/v1/webhooks/metrics`, updated live.
  - **Filters** in one row: **24 hours** (hourly) or **7 days** (daily), and **All endpoints** or one endpoint.
  - **Stat tiles:** deliveries, success rate, p50 / p95 latency, retries and render failures for the range.
  - **Deliveries over time:** stacked columns per hour or day for succeeded, retrying and failed (the status colours, each named in the legend), the same hover and arrow-key tooltip as the Overview chart with p50 and p95 latency added, and a "Show as table" switch.
  - **By endpoint:** deliveries, success-rate meter, p50 / p95 latency, retries and top failure codes per endpoint; a row narrows the screen to that endpoint.
  - **Top failure codes:** each code or error with its count and share as a bar, linking to the deliveries log filtered to failures.
  - **Recent failures:** as on the Overview, each linking to its delivery.
  - Empty state: no deliveries yet, with links to add an endpoint and to send a test.
- **Endpoints:**
  - **Table:** name, method and URL (monospace), template, an enabled switch that applies at once, deliveries in the last 24 hours, and a success-rate sparkline (24 hourly points) with the rate as text beside it. A `localhost` or `127.0.0.1` URL shows a `host.docker.internal` hint when SendMock runs in Docker. Row actions: Send test, Edit, Delete (the confirmation says how many rules go with it). Empty state: "Add endpoint" and "Add a catcher endpoint" (native JSON to `/catch/webhooks`, so test sends land in the HTTP catcher).
  - **Edit sheet**, in tabs:
    - **General:** name, method, URL (accepts `{{ }}` templates), timeout (1 to 60 s), enabled.
    - **Template:** searchable picker grouped by category, "Based on <template> rev N", link mode Linked / Detached (built-in templates are always linked; edit them on the Templates screen), and **Overrides** layered on top: extra headers and extra body fields as name / value rows.
    - **Security:** the secret masked (`whsec_••••3f9a`), **Reveal** behind a confirmation (the reveal is logged) with a copy button, **Rotate secret** with an overlap (1 hour, 24 hours by default, 7 days) that then shows until when the old secret stays valid, and which signing scheme the template uses (Standard Webhooks or the provider's).
    - **Retries:** max attempts (1 to 10), the delay before each retry as chips (1 s to 24 h, the last one repeats), "Retry on 4xx" switch, and a preview of the attempt schedule ("attempts at 0 s, 1 s, 6 s, 36 s, 2 m 36 s").
    - **Variables:** the endpoint's variables (name, kind badge, value or masked secret), the template's required variables with a **Missing** badge and an input until they are set on the endpoint or globally (a global one shows "Set globally"; names with token, secret, key or password are stored as secrets), add, edit and delete for text and secret variables. All variable kinds come with the Variables screen.
  - **Send test** (row action and sheet footer) sends `test.ping` and shows the result in a dialog: status code, duration, response body, the signed request headers, and a link to the delivery.
- **Inbound routes** (`/webhooks/inbound-routes`): Mailgun-style routes ([05-webhooks.md](05-webhooks.md#inbound-routes)).
  - **List:** routes by priority (lower first) with move up / down, description, the expression in Mailgun syntax, the actions as chips, and edit and delete. Empty state explains routes and offers **Add route**.
  - **Editor sheet:** priority, description, the filter (Match recipient with a regex, Match header with a header name and regex, or Catch all) shown as the Mailgun expression it builds, and the actions in order (Forward to URL, Forward to email, Store and notify, Stop) shown as Mailgun actions; named groups like `(?P<token>...)` can be used in actions as `\g<token>`.
  - **Preview:** "Matches N of the last 50 incoming emails" with the matching emails (from, recipient, subject) and the named groups each one captured, updated as the filter changes; invalid regexes show a message under the field.
  - Incoming emails run the matching routes: each forward appears in the email's timeline ("Forwarded by route <description> to <url>") and as a delivery in the delivery log.
- **Rules:**
  - **List:** rules in firing order with move up / down, name, endpoint, event chips, a plain-language filter summary ("to matches \*@support.local and subject contains Ticket"), an enabled switch that applies at once, edit and delete. An endpoint filter at the top (also opened from `?endpoint=`). Disabled rules are dimmed. Empty state: "Add rule".
  - **Editor sheet:** name, endpoint, events as checkboxes grouped by area (Email, SMS, Verify, HTTP, Webhooks), and the **filter builder**:
    - A group says "Match **all** / **any** of these"; each row is field / operator / value with a "not" toggle; "Add condition" and "Add group" (one nested level). No conditions means every selected event fires.
    - Fields follow the selected events: email fields for `email.*` events, SMS fields for `sms.*`, both when both are selected (a condition on a field the event does not have never matches). `header:<name>` asks for the header name. Value inputs follow the field: free text, true / false, an SMS status or an SMS API picker. `exists` needs no value.
    - Rows are checked as you type (missing value, invalid regex, missing header name); the same rules are applied by the API.
  - **Preview:** "Matches N of the last 50 messages", updated as the filter changes, listing the messages (subject and sender, or SMS body and number) with matching ones marked and a "Show non-matching" switch. Events without filter fields (Verify, HTTP, Webhooks) skip the preview and say so.
- **Deliveries:**
  - **Log:** live table, newest first, 50 rows at a time with "Load more": time, event, endpoint, trigger (auto / manual / replay), status (the status code, or failed / exhausted / render failed / pending / cancelled with the error on hover), duration and attempt ("2 / 5"). New deliveries appear as they happen. Status chips (All, Succeeded, Failed, Pending), an endpoint picker and an event picker narrow it; the Failed chip and the endpoint can be preset from the URL (`?status=failed&endpoint=<id>`).
  - **Detail drawer** (opened by a row or by `?delivery=`): status, event, endpoint, trigger, attempt "N of M", duration, time, the next attempt time while it will retry, the event id, and a link to the email or SMS that caused it. Every attempt of the same event is listed and opens its own detail. Request and response sit side by side on wide screens (stacked on phones): method and URL, headers, and the body formatted when it is JSON, each with a copy button, and a "Body truncated at 64 KB" note when the response was cut. A `render_failed` delivery shows the template error instead of a request, with a link to the endpoint.
  - **Actions:** "Copy as cURL"; **Replay** as-is or re-rendered with fresh variable values; **Edit and replay** (a dialog with the body and headers of the stored request, JSON checked before sending); **Cancel retries** for a delivery that will retry (asks first, then marks it cancelled); **Save** with a name, as a bookmark for the Saved screen.
- **Templates:** gallery of built-in service templates (Twilio, Mailgun, SendGrid, Slack, ...) and custom templates with category tabs, search and an event filter; a detail sheet with the request shape, provider doc link, live preview against a recent message or the sample, Edit (built-in templates too, with Reset to default), Use in new endpoint, Clone, Export and Delete. Details in [13-webhook-templates.md](13-webhook-templates.md#ui).
- **Variables:**
  - **Table:** global and endpoint variables: name (as `vars.name`), kind badge, value (secrets masked; the expression for Dynamic, Random and Computed; the current value of a Fixed random), scope (Global or the endpoint, linked) and description. Filters: scope (all, global, one endpoint; also `?endpoint=`), kind chips and a name search. Row actions: Edit, Delete, and **Regenerate** for Fixed random variables. The endpoint sheet's Variables tab keeps its quick text and secret form and links here for the other kinds.
  - **Add / edit sheet:** name, scope (Global or an endpoint), description, and the **kind** as cards (Text, Number, Boolean, JSON, Secret, Dynamic, Random, Computed, Prompt), each with its own fields:
    - Text: a value. Number: a number. Boolean: a switch. JSON: a JSON editor, checked as you type.
    - Secret: a password field; after saving it is never shown again, and leaving it empty while editing keeps the stored secret.
    - Dynamic: a path or expression against the event (`data.to[0].address | lower`), with the same suggestions as templates.
    - Random: a generator expression (`random_string(16)`), with suggestions, and **Per send** or **Fixed**; a Fixed variable shows its current value and Regenerate.
    - Computed: a template combining other variables (`{{ vars.tenant_id }}-{{ vars.nonce }}`), with suggestions.
    - Prompt: a default value; manual sends ask for it, automatic sends use the default.
  - **Resolves to:** every kind shows what it becomes against the sample message, with the same errors (which block saving) and warnings as template previews.
- **Saved:** saved deliveries (bookmarks made with "Save" on a delivery), newest first, with a search by name. Each row shows the name, method and URL, the endpoint and template it came from, and when it was saved; it opens to the stored headers and body. Actions:
  - **Send:** pick the endpoint (the original one by default; the request goes to the picked endpoint's URL), optionally re-render with fresh values, and see the result (status code, duration, link to the new delivery).
  - **Rename**, **Delete** (asks first).
  - **Save as template:** turns the stored request into a custom template with a name, ready on the Templates screen.
  - Saved deliveries survive pruning and reset and are written to the seed export (signature headers are left out; they are made fresh on every send). Empty state: how to save one from a delivery.
- **Request editor** (the endpoint sheet's **Request** tab, which replaces the Template tab; the template editor's body uses the same code editor):
  - **Query params** and **headers** as name / template rows, with `{{` suggestions.
  - **Body mode** as a segmented control: **Template** (the template picker, link mode and extra fields, as before), **Fields** (name, type text / number / boolean / JSON, and a template value per row; encoded as JSON or form, so the body is always valid), **Raw** (a content type and the code editor) or **None**.
  - **Render mode:** Strict (an undefined value stops the delivery as `render_failed`) or Lenient (it renders empty with a warning).
  - **Code editor** (CodeMirror 6, lazy loaded): `{{ }}` highlighted, JSON highlighting for JSON bodies, `{{` autocomplete from the template reference, hover over a value to see its example (secrets masked), line numbers, and an **Insert** menu (event type, recipient, subject, OTP, random id, timestamp).
  - **Live preview:** pick the sample or a recent email or SMS and see the rendered method and URL, headers and body as you type. Errors and warnings show under the part they come from (URL, a query param, a header, a field, the body), and in the code editor they are underlined at their line and column.
- **Template reference and suggestions:** every template field has a reference panel (searchable tree of `event`, `data`, `vars`, `endpoint`, `delivery`, ..., functions and filters, each with type, description and example; click to insert) and suggestions while typing inside `{{ }}`. See [12-webhook-variables.md](12-webhook-variables.md#template-reference-and-suggestions).
- **Send to webhook** (Mail detail "More" menu and the SMS message menu): a dialog that sends one message on demand.
  - **Endpoint** (enabled ones, starting with the first whose template fits the message: an SMS starts on an SMS endpoint) and **Format**: "As the endpoint sends it" or any template, used for this send only.
  - **Prompt variables:** one input per Prompt variable in scope (global ones and the chosen endpoint's), prefilled with its default.
  - **Override variables:** name / value rows; a value wins over the endpoint and global value of that name for this send only.
  - **Preview:** method and URL, headers and body rendered from the inputs as they change, with problems under each part. **Edit body** puts the rendered body in the code editor; an edited body is sent as written.
  - **Send** records a `manual` delivery and shows the result: status, duration, **Open delivery** and **Save** with a name. A render error (an undefined value in Strict mode, an unknown function) blocks sending.
- **Composer** (`/webhooks/composer`): a request written by hand, like a small Postman.
  - **Send to:** an endpoint, which supplies the secret and signing, and the URL unless another one is typed; the method is chosen on the composer.
  - **Preset:** blank or any template; a template fills the method, headers, content type and raw body with its templates, ready to edit.
  - The same request editor as the endpoint sheet (query params, headers, body mode, Strict or Lenient), the same Prompt variables and overrides as Send to webhook, and the live preview against the sample or a recent email or SMS.
  - **Send** and the result work as in Send to webhook.

### Numbers

Two tabs kept in the URL (`/numbers`, `/numbers?tab=services`):

- **Numbers:** a table with number (E.164, copy), label, channel badges (SMS, WhatsApp), webhooks (inbound method and URL, or "Rules only" when none is set, with the default status callback below), Messaging Service, and Edit / Delete. "Add number" and Edit open a side sheet:
  - Number (E.164, unique) and label.
  - Channels: SMS and / or WhatsApp (at least one).
  - Inbound webhook: URL, method (POST or GET), fallback URL and format (the inbound SMS templates: Twilio, Vonage, Plivo, ..., or native JSON). Leaving the URL empty means only webhook rules receive inbound messages. When a webhook rule on `sms.inbound` also exists, the sheet notes that both will receive them ([reply webhook](04-sms.md#reply-webhook-twilio-style)).
  - Default status callback URL.
  - Messaging Service: none or one service; a number belongs to at most one.
  - URLs must be `http` or `https`. Delete asks for confirmation and removes the number from its service.
- **Messaging Services:** a table with name, SID (copy), sender pool (number chips), inbound handling and actions. Create and Edit open a sheet with the friendly name, the sender pool (checkboxes for every number; picking one already in another service moves it, and the list says so) and the inbound handling: "Send a webhook" (request URL and fallback URL), "Defer to sender's webhook" (each number's own inbound URL) or "Drop the message". Delete asks for confirmation and leaves the numbers unassigned.

### Scenarios

`/scenarios` (U3 W14, [20](20-surface-parity.md#scenarios-screen)): the shared code editor with a scenario file, **Load example** (three that pass in Demo mode), **Upload** and **Download**; **Validate** lists problems by step; **Run** shows a summary ("Passed: 5 of 5 steps in 120 ms" or "Failed at step 2: ...") and each step with its operation, status (Passed, Failed, Skipped), time, saved name, and its input and answer. Nothing is stored.

### Logs

Two tabs kept in the URL (`/logs`, `/logs?tab=http`); each row opens a wide side drawer, linked by `?session=<id>` or `?request=<id>` (the SMS drawer's "Open in request log" uses the latter). Logs grow large, so both tables page with the API cursor: 50 rows at a time, the next page loading when the end of the table scrolls into view (with a "Load more" button as fallback) and a "Showing 50 of 5,021" count. Filters and search run on the server, so they cover every row, not just the loaded ones.

- **SMTP:** a table with time, client address, EHLO name, TLS (version or "Plain"), AUTH (user and mechanism), result badge (Delivered, Rejected, Aborted), stored email count and duration. Failed sessions are highlighted with their reason under the result. Chips (All, Delivered, Failed) and a search on client, EHLO name and AUTH user.
  - **Drawer:** the session facts, the failure reason in a callout, and the transcript viewer: one line per command or reply, client commands and server replies told apart by colour and a C / S marker, reply codes coloured by class (2xx, 3xx, 4xx and 5xx), masked AUTH secrets and the DATA line kept as a placeholder that links to the stored email. "Copy transcript" and "Open email" buttons.
  - **Mail link:** the email detail's source badge links to the SMTP session that delivered the email (EM-09.3).
- **HTTP:** a table with time, API (Native, Twilio, Vonage, SendGrid, ...), method, path, status code and duration. Rejected requests (4xx and 5xx) are highlighted. Chips by status class (All, 2xx, 4xx, 5xx), an API picker and a search on the path.
  - **Drawer:** method, full path, status, duration and time; request headers (credentials masked), the request body (JSON pretty-printed, form bodies as a field table, anything else as text) and the response body the same way; "Open message" for the SMS or email the request created.

### Settings

One page with a section nav (a side list on desktop, a picker on phones), the section kept in the URL (`/settings?section=sms`). Each section is its own form: changes are applied with **Save changes** (disabled until something changed, **Discard** resets), take effect without a restart, and invalid values show a message under the field (PL-05). Validation is shared with the API.

- **General:** retention (max emails, max SMS, max age in days or "Keep forever"). Danger zone: **Delete all emails**, **Delete all SMS** and **Reset to seed**, each behind a confirmation that says what is lost.
- **Seed:** status card (seed file path or "No seed file", when it was applied, and the items added or changed since, with a hint to export them). **Export** downloads `sendmock.seed.toml` (secrets written as `${ENV_VAR}` references, never literal). **Apply** takes an uploaded or pasted file, **Validate** lists errors with line numbers and a summary of what would change, then applies after a confirmation.
- **Email:** plus-address auto-tagging, delivery outcome profile (off, auto-delivered, realistic with bounce and complaint rates), inbound email domains (chip editor), relay SMTP URL (password masked) and recipient allowlist (release stays off until it has an entry), SpamAssassin address (empty means off), the **Magic addresses** switch, **Custom outcome addresses** (same table, dialog and "Test an address" box as the SMS rules; the box asks `POST /outcome-rules/email/test`), and the magic addresses reference table. **Tag rules** and **Auto-forward rules** (U3 W14; they had only linked to the webhook rules before) are two cards with an ordered table (name, filter summary, tag or addresses, enabled switch, move, edit, delete) and a sheet with the name, the tag or the addresses (chip input), the webhook rule filter builder over email fields, its "matches N of the last 50" preview, and enabled.
- **SMS:** simulation profile (instant, realistic, manual, each with what it does), failure rate (0 to 100%), strict Twilio test mode, the **Magic numbers** switch, **Custom outcome numbers** (a table with order, match, pattern, outcome and code, note, an enabled switch, move up / down, edit and delete; Add and Edit open a dialog that only asks for the code or delay when the outcome needs it), a "Test a number" box that shows which rule, magic number or profile applies, and the magic numbers reference (Twilio `To` and `From` test numbers and the SendMock after-send extensions, from [04-sms.md](04-sms.md#delivery-simulation)).
- **Payments:** merchant name shown on checkout pages, default currency, automatic outcome profile (interactive, auto-success, auto-decline, random with a success rate), and the test values of the enabled methods read through each method's flow (test cards; test numbers or codes with the OTP and PIN only when the flow asks for them; other methods with their test account or fixed outcome), each row with the gateways offering it, linking to Payments > Gateways (merchant credentials) and Payments > Methods.
- **Opened events:** "Fire opened events when I view messages" (default on), and "First open only" or "Every open".
- **Chaos:** reject the next N SMTP messages with a chosen code (421, 450, 550, 552), reject recipients matching a pattern with `550`, added latency per SMTP command, and drop the connection during `DATA`. While any chaos option is on, the section nav shows a "Chaos on" badge.
- **OTP patterns:** an ordered list of regular expressions (first capture group is the code) with add, remove and "Restore defaults", invalid patterns flagged, and a tester: paste a message and see which pattern matched and the code it found.
- **Connection:** copy-ready snippets for SMTP, the email API, SMS and the HTTP catcher, with a language picker (Laravel / PHP, Node.js, Python, Go, Java, Ruby, .NET, cURL) and a "Where does your app run?" picker that fills in the right host: this machine (`127.0.0.1`), a container talking to SendMock on the host (`host.docker.internal`), or the same Docker Compose project (`sendmock`). Same content as [08-integrations.md](08-integrations.md); ports come from `/info`.
  - **Customize the request:** a request headers editor (name and value rows, with a quick "Add Authorization header" for when API auth is on) and a JSON body editor for the email and SMS calls, prefilled with the sample and with "Add field" chips for the optional fields (`/send`: `cc`, `bcc`, `text`, `tags`, `headers`, `attachments`; `/sms`: `status_callback`, `metadata`). In a body, `"{{file:invoice.pdf}}"` as a value stands for "this file, base64 encoded": each snippet then reads and encodes the file the way its language does it (`base64_encode(file_get_contents(...))` in PHP, `fs.readFileSync(...).toString("base64")` in Node.js, `base64 < file` in cURL, and so on) and puts it in the body. Every language's snippet updates as you type, written the way that language does it (for example `Http::withHeaders()` in Laravel, `headers=` and a Python dict in Python, `req.Header.Set` in Go, `-H` in cURL). Invalid JSON is flagged and the snippets keep the last valid body. A **Reset** button (disabled until something changed) removes the added headers and puts both bodies back to the sample.
- **AI agents** (its own card under Connection, U3 W14): an agent picker (Claude Code, Codex, Cursor, Gemini CLI, VS Code) showing the install command and the MCP configuration with copy buttons, where they are written, and **Download the skill** (`GET /ai/agents`, `GET /ai/skill`). Under the request bodies, **Send this request** runs the edited email or SMS call against this SendMock with the edited headers and shows the stored id or the error.
- **About:** version and channel, uptime, listeners (SMTP, HTTP, provider port), database path and size, links to the changelog and docs for this version, and the opt-in update check: off by default, and "Check for updates" only calls GitHub Releases when it is on (stable installs are offered stables, beta installs betas and stables).

### Notifications

- **Settings > Notifications** picks how events are announced:
  - **Pop-up toasts** (default, as today): a toast per notable event (new email, new SMS, inbound SMS, failed webhook), grouped with "Clear all".
  - **Bell only:** no pop-ups. A bell in the header's top right shows the unread count.
  - **Toast position:** where toasts appear (top right by default, or top center, top left, bottom right, bottom center, bottom left).
- **Notification bell** (both modes): clicking it opens a popover list, newest first, each with an icon, title, short description, relative time and a link to the email, SMS or delivery. Opening the list marks them read; "Clear all" empties it. In toast mode the bell keeps the history of toasts already shown.
- The choice is a per-browser preference (like the theme), not a server setting, and is not written to the seed.

### Empty states / onboarding

Every list tells "no data yet" apart from "nothing matches":

- **Nothing matches** (a search, chip or filter is active): a short line saying so and a **Clear filter** button. No onboarding card.
- **No data yet:** an icon, one line on what shows up here, a **how to connect** card and a **sample** button, so the screen can be explored at once.

The how to connect card shows the values the app needs, each with a copy button, and a "More snippets" link to Settings > Connection:

- Ports come from `/info`. The host follows the same **Where does your app run?** choice as Settings > Connection (this machine `127.0.0.1`, a container talking to SendMock on the host `host.docker.internal`, the same Compose project `sendmock`), shown as a compact switch on the card. The choice is remembered in the browser and shared by every card and Settings > Connection. When `/info` says SendMock runs in a container, the default is the Compose host.

| Screen | How to connect shows | Sample button |
|--------|----------------------|---------------|
| Mail | SMTP host and port, "no auth or TLS needed" | **Send a sample email** (over SMTP, so it also shows in Logs > SMTP) |
| SMS | native `POST /api/v1/sms` URL, Twilio and Vonage base URLs | **Send a sample SMS** |
| Verify > Verifications | Twilio Verify base URL and the start call | **Start a sample verification** (on the first Verify service, or a new "Sample" service when there is none; the code goes out by SMS) |

| Logs > SMTP | SMTP host and port | **Send a sample email** |
| Logs > API requests | API base URL | **Send a sample SMS** |
| Overview > Latest messages | SMTP address and API base URL (the connect card) | **Send a sample email** and **Send a sample SMS** |

Samples go through `POST /api/v1/samples/{kind}` ([06-api.md](06-api.md#test-automation-helpers)), so they fire the same events, webhooks and notifications as real traffic. The HTTP catcher and Webhooks screens get their empty states with those screens in Phase U2.

## Bundle budget

- Initial JS under 250 KB gzipped; Shiki, the rule builder and the CodeMirror code editor are lazy-loaded.
- Fonts: system font stack (no web font download), optional Inter bundled if it fits the budget.
- Total embedded `dist/` under 2 MB so the binary stays small.

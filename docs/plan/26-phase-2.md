# 26. Phase 2: SMS and Verify backend

Phase 2 makes SMS real: apps send through the native API, the Twilio Messages API or Vonage, SendMock stores each message with its encoding and segments, simulates delivery with Twilio's own test numbers, calls status callbacks, and emulates Twilio Verify so OTP logins work. The SMS, Verify, Numbers and SMS > Providers screens switch from Not available yet to live data ([11](11-roadmap.md#phase-2-sms-backend-about-2-weeks)).

## Goal and done-when

**Done when** (from [11](11-roadmap.md#phase-2-sms-backend-about-2-weeks)): an app using the Twilio REST shape sends an SMS, sees it in the UI, and receives `queued`, `sent` and `delivered` status callbacks; and an app using Twilio Verify completes an OTP login against SendMock. In full:

- every Phase 2 item in [PROGRESS.md](PROGRESS.md) is ticked and the criteria below have passing tests that name them;
- the official Twilio SDKs for Node and Python send an SMS and run a Verify login against the binary in CI;
- the live UI suite shows SMS, Verify, Numbers and SMS > Providers with real data and no failing calls.

## As built

- **W1:** `sendmock-sms` has `phone_number` (separators dropped, `00` read as `+`, 7 to 15 digits without a leading zero become E.164, sender IDs and short codes stay as sent), `encoding` (`count_segments`: GSM 03.38 table and extension table, else UTF-16 units) and `sms_thread` (`channel-app-contact`, alphanumerics only, so it is safe in a URL). `0005_sms.sql` stores both numbers twice (normalised and raw) and the thread's app and contact numbers, so conversations need no parsing; `SmsRepository` lists conversations with one grouped query and counts unread inbound messages. Extraction and events stay in the operations layer, which can use the mail crate's extractors (the domain crates do not depend on each other).

- **W2:** the operations live in `sendmock-ops/src/sms/` (inputs, views answering the contract, `store_sms` for every path, media intake, read and change operations, lookups for `/otp`). Media links are fetched through a `MediaFetcher` trait the binary implements with reqwest, so tests run without a network. `GET /api/v1/sms/send` is `get_alias_path` on `postSms`: the REST adapter routes it to the same operation with the query string as input, logs it in the API request log, and leaves it out of OpenAPI, which allows one operation id per operation. Form bodies (`application/x-www-form-urlencoded`) work for every operation, converted by the input schema like query strings; the Twilio emulation in W5 relies on that. Delivery simulation (W3) moves messages on from `queued`.

- **W3:** the decision is pure domain code in `sendmock-sms/src/simulation/` (`magic_numbers`, `outcome_pattern`, `outcome_resolver`, `delivery_plan`), so every rule is unit tested with a seeded random source. Order: a rejection by the recipient (custom rule, then magic number), then by the sender, then strict test mode (a sender that is neither a custom `from` rule nor a Twilio test `From` number gets `21606`); otherwise the recipient's after-send outcome, the sender's, or the profile with its failure rate (half `undelivered` `30003`, half `failed` `30008`). Rule outcomes in the `manual` profile use the realistic timings so they still play out, as the mock does. The operations apply the steps due at once before answering, so `instant` answers `delivered`, and play the rest from one tokio task per message, which also sends the callbacks in status order; a `StatusScheduler` trait was not needed, because the timings are unit tested in the domain. Callbacks are sent through a `StatusCallbackSender` trait the binary implements with reqwest (10-second timeout, redirects off, 64 KB of the answer kept); tests use a recording fake. The REST API cannot tell which surface created a rule yet, so `created_by` is `api` for now. Outcome rules are configuration, so reset keeps them.

- **W4:** migration `0007_numbers.sql` stores `virtual_numbers` (number unique) and `messaging_services`. A number's service is a column on the number (`ON DELETE SET NULL`), so a number is in at most one pool by construction: saving a service with `number_ids` moves those numbers in and frees the ones it no longer lists, and deleting a service keeps its numbers outside any pool. `VirtualNumberRepository` and `MessagingServiceRepository` hold the SQL; the operations check what the form checks (E.164, not registered, a label, a channel, http(s) URLs, a webhook URL for `webhook` inbound mode) plus that a service SID or pool number exists. Service SIDs are `MG` and 32 hex digits from the random source. `sendmock_number_upsert` serves `postNumbers` and `patchNumbersByNumberId`, told apart by whether `number_id` is given: `OperationSelector` now has `by_value` and `by_presence`, and the CLI reference writes the latter as `{input, isGiven}` like the surface catalogue. Sending from a pool (SM-03.1, SM-03.2) comes with the Twilio API in W5; the reply webhook that reads `inbound_url` (SM-12.2) is Phase 3. `POST /samples/number` is dropped: the signed-off contract and UI have no number sample.

- **W5 (a, provider runtime and Twilio Messages):** providers are answered from their definitions, as [22](22-configurable-providers.md#13-stage-b) asks, not from fixed adapters. `web/scripts/export-builtin-definitions.ts` exports the mock's shipped SMS providers and webhook templates to `crates/sendmock-ops/builtin/`, which the binary embeds, and a repository test fails when the two drift. `sendmock-core` gains the template engine (`{{ path | filter | default("x") }}`, the functions `uuid`, `random_hex`, `random_string`, `now_iso`, `now_unix`, the filters `json`, `urlencode`, `lower`, `upper`), which escapes values for JSON string context when the answer is JSON, so a body with quotes stays valid. `sendmock-ops/src/providers/` matches a request to an operation (`{name}` path parts, `Host` when two providers share a path), reads the query and a JSON or form body (the `Content-Type` wins over the declared format), applies the field mapping and validation rules, checks credentials (a secret anywhere in the request, Basic auth decoded), and runs the kind: `send` stores the message through the same simulation as the native API and answers it as `queued`; `fetch` and `cancel` answer the stored message (SendMock never schedules, so nothing is left to cancel); `list` answers Twilio's page shape. Magic and custom rejections use the provider's own code from `outcome_error_codes`; the Twilio definition gains `missing_to`, `missing_from` and `missing_body` there, a fuller message resource and error bodies that take the code and message from the check. `/providers/<key>/...` is served on the main port without UI auth, since provider requests carry the provider's credentials, and every provider request is logged under the provider's key with its secrets masked and the SMS it created.

- **W5 (b, callback formats and Vonage):** a provider message's status callback renders the provider's `callback_template_key` from the exported webhook templates (`twilio.status_callback`, `vonage.dlr`) with the provider's status names, its credentials as `vars.<key>_<credential>` (the message's account as `vars.twilio_account_sid`) and the rendered form fields as `body_fields`; `twilio_signature(url, fields, token)` signs it as Twilio does (HMAC-SHA1 over the URL and the sorted fields, checked against Twilio's documented example). A status the provider's names do not list is not reported, so Vonage sends no receipt for `queued`. Native messages keep SendMock's JSON callback. Vonage `POST /sms/json` answers from its definition for form and JSON bodies; its definition gains an `invalid_value` answer (status `3`) for magic and custom rejections, and a secret sent in the body is masked in the request log. New dependency `sha1` 0.11 (the version `hmac` 0.13 needs; the tree only had 0.10 through tungstenite).

- **W5 (c, Messaging Services):** a Twilio send with `MessagingServiceSid` and no `From` takes a number from the service's pool that works on the recipient's channel (picked with the random source), or Twilio's test sender `+15005550006` when the pool is empty, and answers `accepted` as Twilio does. An unknown SID creates the service in lenient mode (its pool empty, inbound deferred to the sender) and is refused with `21701` when strict Twilio test mode is on. Twilio's Messaging Services API (`/v1/Services`: create, list, fetch, update, delete, with Twilio's resource and `meta` paging shapes) is served in code with the Twilio provider, over the same services as the Numbers screen, since it is not one of the definition's operation kinds. `MediaUrl` goes through the same media intake as the native API.

- **W5 (d, provider port):** `--provider-addr` (`SENDMOCK_PROVIDER_ADDR`, `provider_addr` in `sendmock.toml`, off by default) serves every provider at its real paths, routed by path and then `Host`; `--provider-port twilio=8027` (repeatable or comma-separated, `SENDMOCK_PROVIDER_PORTS`, `[provider_ports]` in the file) gives one provider its own port on the provider address's host (the HTTP host without one), where only that provider answers. The listeners are bound before anything is announced, stop with the server, appear in the ready line as `provider_addr` and in `/info` as `provider_address`. `/providers/<key>/...` keeps working on the main port.

- **W6 (Twilio Verify):** migration `0008_verify.sql` stores Verify services, verifications (keeping the service's name) and each verification's timeline; `VerifyServiceRepository` and `VerificationRepository` hold the SQL. The rules are domain code in `sendmock-sms/src/verify/` (a fixed or random code, five wrong checks end it, an expired or finished verification cannot be checked). The operations start a verification or resend the pending one's code (the sixth send gets `60203`), deliver the code as a captured SMS or WhatsApp message through the delivery simulation, a captured email (source `verify`), or a timeline entry for `call`, check codes (`60202` on the fifth wrong one), expire overdue ones on read, force states, and fire `verify.started`, `verify.checked` and `verify.expired`. Native REST, CLI and MCP serve the seven Verify operations; `POST /samples/verification` and `GET /otp?channel=verify` use the same flow. Twilio's `/v2/Services` API (services, Verifications, VerificationCheck, update with `Status`) is served in code under the `twilio_verify` provider, since its state machine stays code ([22](22-configurable-providers.md#14-open-points)). Reset now deletes SMS (it said so, but did not) and verifications, and keeps numbers, services and rules. VF-01.2's global defaults are not in the signed-off contract, so codes are set per service until the contract adds them.

- **W7 (SMS provider definitions in the database):** migration `0009_message_providers.sql` stores only what differs from the shipped definitions: a built-in kept as shipped has no row (so an upgrade brings its new default), a removed one keeps a row with `is_removed` and no definition, and an edited one stores its definition as JSON. `crates/sendmock-ops/src/providers/provider_catalog.rs` merges the shipped built-ins with the stored rows; the provider runtime and status callbacks read the providers through it, so a saved change applies to the next request. `sendmock-ops/src/message_providers/` serves eight of the nine `/api/v1/sms/providers` operations (list, show, update, delete as remove, restore, reset, preview, credential reveal) over REST, CLI and MCP from the registry; adding a provider (`POST`) comes with custom providers in Phase 4. Saves follow the Providers screen's rules (name, `#rrggbb` accent, credential names, paths that start with `/` and avoid `/api/` and `/providers/`, closed `{name}` parts, no route clash with another enabled provider unless the hosts differ, one source per mapped part, no template errors) and answer `400` with the reason; restore of a provider that is not removed and reset of one that is not built in answer `409`. Secrets are masked as `••••` and the last four characters, and a masked or empty secret sent back keeps the stored value. The preview runs a sample request (the provider's example send when none is given) through the unsaved settings exactly as the runtime would, and lists each template problem by its part. The credential operation sets the new `revealed_secret_field` on its definition: MCP leaves it out, and the CLI masks the value unless `--reveal` is given. All five shipped SMS definitions are listed, Plivo and MessageBird included, since the runtime already answers them; their fixture tests stay in Phase 4.

- **W8 (surfaces and screens):** the CLI commands and MCP tools for SMS, Verify, Numbers, Messaging Services, SMS outcome rules and SMS providers come from the operation registry, so they were served as each operation landed in W2 to W7; W8 adds end-to-end tests against the binary (`crates/sendmock/tests/sms_commands.rs`, and an `sms,verify,numbers,extract` session in `mcp_stdio.rs`): send, wait, threads and the SMS code, numbers and a service pool, a custom outcome number against a magic one, a verification shown and forced, and a provider secret that the CLI masks unless `--reveal` is given and MCP never returns. The screens needed no change to go live, since they follow `available_operations` (UI-12): the live UI suite (`web/tests/live/sms-screens.spec.ts`) sends real messages and checks SMS, the message drawer, Verify, Numbers and SMS > Providers with no failing calls. The one Phase 2 catalogue entry not served, adding an SMS provider, is Phase 4 (custom providers), so the catalogue now says so and the Add provider button is an `OperationButton`. The tests found that `#[schemars(required)]` on an `Option` field drops its `null`, so the binary's schemas said "required string" where the contract says "required, may be null": the CLI demanded every nullable flag (`numbers add` needed an inbound URL) and MCP showed agents no way to leave one out. Such fields now use `schema_with = "crate::nullable_schema::<T>"`, which keeps them required and nullable as in the contract, and the CLI makes a flag required only when its input cannot be null.

- **W9 (a, Twilio SDKs):** `examples/sms/` has the official Twilio SDKs for Node (twilio 6.2.0) and Python (twilio 9.12.0). Each keeps the SDK's real base URL and passes a custom HTTP client, the SDK's own extension point, that sends every request to the provider port with the same path and query; it sends an SMS from Twilio's test sender with a status callback to a local handler and waits for `queued`, `sent` and `delivered` in that order, then creates a Verify service, starts a verification, reads the code from `/api/v1/otp?channel=verify` and checks it to `approved`. `.github/workflows/sms-clients.yml` runs both against a release binary started with `--provider-addr 127.0.0.1:8026`, on changes to the SMS, Verify and provider code or the examples, and Release build runs it before publishing. VF-03.4 ticked. SM-02.4 also names PHP, Go, Java, C# and Ruby; they come with the per-SDK recipes in Phase 4 ([08](08-integrations.md#provider-sdks-twilio-vonage-)), so it stays open. Testcontainers modules (DS-06.1) are W9b.

- **W9 (b, Testcontainers modules):** `testcontainers/` holds one small module per language, each a thin wrapper over that language's Testcontainers library, with the same shape everywhere: a `SendMockContainer` that starts the image (default `ghcr.io/shibbirweb/sendmock:beta` while SendMock is in beta, any image by argument), exposes SMTP `1025`, HTTP `8025` and the provider port `8026` (set with `SENDMOCK_PROVIDER_ADDR=0.0.0.0:8026`), waits for `/api/v1/health`, and answers `smtp host and port`, `http url` and `provider url`. Java (`io.github.shibbirweb:sendmock-testcontainers`, Testcontainers 2.0.5), Node (`sendmock-testcontainers`, testcontainers 12.2.1, TypeScript run by Node 24), Go (`github.com/shibbirweb/sendmock/testcontainers/go`, testcontainers-go 0.44.0), Python (`sendmock-testcontainers`, testcontainers 4.15.0) and .NET (`SendMock.Testcontainers`, Testcontainers 4.16.0). Each has one test that starts the container and checks all three addresses: the health answer, the SMTP greeting, and a Twilio send through the provider URL answered `201`. `.github/workflows/testcontainers.yml` builds the image from the commit once and runs the five tests against it, on changes to the modules, the Dockerfile or the binary. Publishing the packages to Maven Central, npm, the Go proxy, PyPI and NuGet is release work for Phase 5; seed files and wait or OTP helpers come when the seed apply operation and the language SDKs do.

## Design notes

- **Crates:** the domain lives in `sendmock-sms` (layer 2): `phone_number`, `encoding`, `ingest`, `simulation` (Strategy per profile, a resolver over custom rules, magic numbers and the profile), `media`. Provider wire formats are Adapters in `sendmock-sms/src/providers/` (`TwilioMessagesAdapter`, `VonageSmsAdapter`), each translating to and from the internal model; the routes that serve them are generated by the REST adapter like other operations, so they reach the request log, CLI and MCP the same way. Verify is a domain module in `sendmock-sms` (`verify/`), with its own repository in `sendmock-store`.
- **Status transitions** run on a scheduler in the binary that the operations feed through a trait (`StatusScheduler`), so tests drive it with a fake clock; each transition writes history, publishes `sms.status` and enqueues the status callback.
- **Status callbacks** are plain HTTP calls in Phase 2 (the provider format, one attempt, logged on the message); Phase 3 moves them onto the persistent webhook queue with retries.
- **Media by URL** is fetched with the same reqwest client as the update check, with a 10-second timeout and the 5 MB total limit; a failed fetch fails the message with Twilio error `11200`.
- **Provider port:** `--provider-addr` (default off) serves the provider paths at their real roots, routed by path first and `Host` when two providers share one, so an SDK whose base URL is swapped works unchanged.
